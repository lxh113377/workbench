# 模型池：多接口统一纳管 · 自动轮询 · 故障转移

> 对应目标：把 DeepSeek Harness Desktop 已集成的 **our free model（OFM）** 扩展成一条
> 「所有可用模型统一纳管 + 自动轮询 + 实时探活 + 无感故障转移 + 可视化管理」的模型队列。
> 代码：`workbench/internal/modelpool/`（13 个文件，纯标准库）＋ `workbench/internal/web/pool_*.go`。

## 1. 它解决什么问题

改造前工作台只有三件事是"写死"的：

| 问题 | 改造前 | 改造后 |
|---|---|---|
| 模型从哪来 | `config.DefaultConfig()` 里硬编码 3 条 `ModelRoute` | 从 OFM 渠道网关 `/v1/models`（28 个）+ OFM `catalog.json/availability.json`（免费/Kilo/EAC 车道）自动发现，实测纳管 **35 个** |
| 什么时候换模型 | 任务失败 → 退避 5/20/60 秒 → 换下一个（用户看到空窗与失败） | 一次尝试内部**串行切换**（`FailoverRunner`），主模型失败立刻换下一个，成功即返回，上层只看到"成功" |
| 怎么知道模型挂了 | 只能靠任务失败反推（`models-health.json` 里 consecFail 10-12 才发现） | **探测循环**每 3 分钟跑一轮端点/清单校验 + OFM 逐模型可用性，失败自动冷却、到期半开恢复 |

```

                    │ 概览 · 车道水位 · 模型清单 · 添加兼容接口 · 状态日志                     │
                    └───────────────▲──────────────────────────────────────────────────────────┘
                                    │ REST /api/pool/*
┌───────────────┐   ┌───────────────┴──────────────┐   ┌──────────────────────────┐
│ Discover      │   │ Service（编排）               │   │ Store（账本）             │
│ catalog/avail │──▶│ SyncNow → ProbeNow → 周期循环 │──▶│ pool.json（原子写）       │
│ + Gateway     │   │                              │   │ model-status.jsonl（追加）│
└───────────────┘   └───────┬───────────┬──────────┘   └──────────────────────────┘
                            │           │
                   ┌────────▼───┐  ┌────▼─────────┐   ┌────────────────────────┐
                   │ Scheduler  │  │ Manager      │   │ FailoverRunner          │
                   │ 4 种策略    │  │ 健康状态机    │◀──│ 包住真实 executor       │

                                        │ Routes()                │ Run()
```

各文件职责：

| 文件 | 职责 |
|---|---|
| `types.go` | `Spec`（模型定义）、`Health`（健康度）、`State`/`Lane`/`Format` 枚举 |
| `store.go` | `pool.json` 原子读写 + `model-status.jsonl` 追加（16MB 滚动两代） |
| `discover.go` | 只读 OFM 数据面：`catalog.json`（entries/sealIds/kiloRows）＋ `availability.json` |
| `gateway.go` / `gateway_check.go` | 发现 OFM 渠道网关（地址 + 多份 api-key 轮试），**HTTP 层验证**才算连通 |
| `probe.go` | 端点级 + 清单级探测；`gateway_off`/`gateway_unauthorized` 属环境态不判死模型 |
| `manager.go` | 增删改、健康状态机（degraded→down→半开恢复）、路由投影 |
| `scheduler.go` | priority / round-robin / weighted / least-loaded 四种策略 + 兜底链 |
| `failover.go` | `FailoverRunner`：一次尝试内切换，只有可归因到模型的失败才计入健康度 |
| `service.go` | 后台编排：启动同步 → 首轮探测 → 3 分钟探测 / 10 分钟同步循环 |
| `sync.go` | 网关清单 → 池子的增量合并（保留用户改过的优先级/权重/启停） |
| `seed.go` | 首次启动兜底清单（实测可用的 4 个模型） |

## 3. 五条目标逐条落地

### 3.1 适配接入更多兼容模型接口，统一纳管

三个来源合流：

1. **OFM 渠道网关**（`127.0.0.1:8326`，OpenAI 兼容）：`GET /v1/models` 广播 28 个模型，
   id 带车道前缀（`our-free-model/`、`our-free-model-region/`、`deepseek-official/`）；
2. **OFM 数据面**：`catalog.json` 的 `entries`（免费车道 13）、`kiloRows`（Kilo 免费池 17）、
   `sealIds`（EAC 协付 5）；`availability.json` 提供逐模型上游判定；
3. **用户自填端点**：面板「添加兼容模型接口」支持三种线协议（`openai-chat` /
   `openai-responses` / `anthropic-messages`），任意 BaseURL + API Key。

统一成同一张 `Spec` 表，持有：优先级、权重、tier、启停、失败阈值、冷却秒数、上下文窗口、
视觉能力、来源标记。**真实结果：35 个模型入池，25 个可调度**（其余是地区受限/网关专属车道，保留可见但默认不路由）。

> 车道区分 `Routable`：DSH 的执行器只认 `our-free-model` provider，
> 网关专属车道（`deepseek-official/*`）与未接通 aggregate 的自定义端点只能经 OpenAI 网关调用，
> 不能写进 overlay（写进去会被判「未知 provider」而必然失败），因此标记为不可路由 ——
> 面板仍显示，但绝不派给任务。
>
> **这道约束在两个地方都要生效**：账本侧 `Manager.Routes()`（投影给 modelroute 的路由表）
> 与选择器侧 `Scheduler.Pick/PickChain`。2026-10-19 活体面板复验发现后者漏了这道过滤 ——
> 只按 `Enabled`+健康筛，于是 `FailoverRunner` 的兜底链仍会把不可路由模型派出去
> （实测：面板新增一个 `routable:false` 的模型后它被顶到链首）。已补齐并加回归
> `TestSchedulerSkipsNonRoutable`（四种策略逐个断言，且「全池不可路由→返回空」走等待逻辑）。
> 面板「可调度（DSH 车道）」这一栏就是 `Routable` 计数，与 `Routes()` 口径一致。

### 3.2 自动轮询调度

`Scheduler` 四种策略（面板下拉切换，立即生效）：

| 策略 | 语义 | 适用 |
|---|---|---|
| `priority`（默认） | 按优先级取第一个可用，天然「主用 + 兜底」 | 想固定首选模型 |
| `round-robin` | 轮转起点，均匀分摊 | 多模型平摊免费额度 |
| `weighted` | 按权重加权轮盘 | 快模型多跑、慢模型兜底 |
| `least-loaded` | 按 Acquire/Release 维护的**在飞任务数**取最闲模型，并列时回落到调度序（Priority↑ Weight↓ ID） | 高并发分摊负载 |

`PickChain()` 额外返回完整兜底链，供单次任务内快速切换：`priority/weighted` 按调度序，
`round-robin` 轮转起点，`least-loaded` 按在飞负载升序（FailoverRunner 用的就是这条链，
所以高并发下兜底也会先给最闲的模型，而不是继续压给最忙的）。

> 2026-10-19 缺陷修复：`least-loaded` 此前与 `round-robin` 共用同一分支，`inflight`
> 计数只出现在 Acquire/Release 与 `/api/pool` 快照里，从未参与选择 —— 面板与本文都写着
> 「在飞任务少的优先」，实跑却是轮转，策略名存实亡。活体面板复验（真启实例 + 真调 API）
> 发现并修复，回归测试 `TestSchedulerLeastLoaded*` 三条锁住契约，并用行为级变异验证
> 这三条测试对修复前的代码必然翻红。同时删掉了从未被读取的 `sticky` 死字段。

### 3.3 实时可用性检测 + 故障转移

**检测**（每 3 分钟，面板可一键触发）：

- 端点级：同一 BaseURL 只探测一次 `GET /v1/models`（不烧模型额度）；
- 清单级：确认该模型确实在网关广播清单里（自动匹配 `our-free-model/<id>` 等三种前缀形态）；
- 上游级：读 OFM `availability.json` 逐模型判定（插件自己探测的结果，不再重复花钱）；
- 本机网关 `gateway_off` / `gateway_unauthorized` → 判 `unknown`（**环境问题不判死模型**），
  因为 DSH 走 OFM provider 不依赖 8326 端口。

**状态机**：

```
unknown ──探测成功──▶ healthy ──失败──▶ degraded ──连续达阈值──▶ down（冷却）
   ▲                                                                  │
   └──────────────── 冷却到期（半开恢复，下次调用验证）────────────────┘
```

**故障转移**：`FailoverRunner` 包在真实执行器外层，在一次 `Run` 内部按兜底链切换，
不 sleep、不返回中间失败，只有整条链都失败才把最后错误交给引擎重试策略。
**只有可归因到模型的失败**（`model_unavailable` / `missing_credential` / `upstream_failed` /
`timeout` / `stalled` / `unreachable`）才计入模型健康度；`bad_exit`（任务无最终答案）属任务级，
只记 `skip` 日志，避免把任务问题算到模型头上把整池打进冷却（现场踩过：6 个模型同时 down）。

### 3.4 无感切换 + 状态日志

- 切换发生在一次尝试内部，用户界面的任务状态不会出现中间"失败"；
- `model-status.jsonl` 逐行记录：`probe`（状态变化）、`switch`（from→to + 原因）、
  `failure`（失败计数与冷却）、`recover`（半开恢复）、`sync`（清单同步）、`crud`（面板增删改）、
  `skip`（任务级失败不计模型）；
- 面板「模型状态日志」实时显示最近 120 条，便于排查"刚才为什么换了模型"。

### 3.5 可配置的模型管理界面

`/modelpool` 独立控制台（管理面板右上角「模型池」直达），五块：

1. **总览**：可用/总数、可调度数、调度策略下拉、探测轮次、网关连通状态；
2. **车道水位**：OFM 免费 / Kilo / EAC / 聚合 各车道的 总数-可用-下线-停用；
3. **模型清单**：按调度顺序排列，每行可 上移/下移（调优先级）、停用/启用、恢复（清冷却）、编辑、删除；
4. **添加兼容模型接口**：就地展开表单（模型 ID/显示名/上游模型名/BaseURL/Key/线协议/车道/Tier/优先级/权重/失败阈值/冷却秒数）；
5. **模型状态日志**：新→旧 120 条。

API（全部要求面板 token，密钥只回显 `…后四位` 指纹）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/pool` | 全量视图（模型/健康/车道/策略/网关/日志） |
| POST | `/api/pool/sync` | 立刻同步网关清单 |
| POST | `/api/pool/probe` | 立刻探测一轮 |
| GET/POST | `/api/pool/models` | 列出 / 新增模型 |
| PUT | `/api/pool/models/<id>` | 编辑模型 |
| DELETE | `/api/pool/models/<id>` | 删除模型 |
| POST | `/api/pool/models/<id>/{enable,disable,restore,probe}` | 单模型操作 |
| POST | `/api/pool/reorder` | 调整优先级（`{"ids":[最高在前]}`） |
| GET/POST | `/api/pool/strategy` | 查看 / 切换调度策略 |
| GET | `/api/pool/log?tail=200` | 状态日志 |

CLI（无需 GUI，便于脚本与排障）：

```powershell
workbench.exe --model-pool status        # 全量状态 JSON（无可用模型退出码 2）
workbench.exe --model-pool sync          # 同步网关清单
workbench.exe --model-pool probe         # 探测一轮
workbench.exe --model-pool routes        # 打印投影出的调度路由表
workbench.exe --model-pool log 50        # 最近 50 条状态日志
workbench.exe --model-pool reset <id>    # 解除冷却
workbench.exe --model-pool enable|disable <id>
workbench.exe --model-pool strategy weighted
```

## 4. 配置项（`config.json` 的 `pool` 段）

```json
"pool": {
  "enabled": true,
  "probeSeconds": 180,
  "syncSeconds": 600,
  "strategy": "priority",
  "deepProbe": false
}
```

`Normalize()` 钳制：`probeSeconds` 30..3600、`syncSeconds` 60..7200、策略非法回落 `priority`。

## 6. 已知边界

1. **8326 端口属主会轮换**：该端口由"当前跑着 OFM 渠道网关的那个 DSH 任务进程"持有，
   每个任务隔离 HOME 各有一把 api-key。池子会扫描所有候选 key 并验证，但不保证 100% 追上；
   网关不可用时**退回 catalog.json 数据面**，模型照常纳管（DSH 走 OFM provider 不依赖 8326）。
2. **Kilo 车道模型名带 `:free` 后缀**：部分模型 DSH provider 是否接受取决于 OFM 版本，
   探测能通过但实际执行可能失败；这类失败归 `bad_exit`，不计入模型健康度。
3. **探测不消耗额度**：默认只做端点+清单校验；需要模型级真实补全时把 `deepProbe` 打开。
4. **面板自填端点：对账与投影已就绪，只差执行器两行接线**（2026-10-19 推进）：
   `lane=custom` 的模型能被池子登记、能被真实 HTTP 探测（`GET <BaseURL>/v1/models` 带 Key 校验）。
   池子现在还会**逐条对账**它到底能不能被 DSH 调用：`registry.go` 读插件的
   provider 清单（实测 75 个），`ProjectAggregate` 按 OFM 的 aggregate 契约投影，
   四条注定不通的路径（providerId 不在清单 / oauth·adc 登录型 / 缺 API Key /
   BaseURL 含 `{占位符}`）一律**拒绝并附原因**，面板 `/api/pool` 的 `aggregate`
   字段直接展示（活体实测：添加 `open_router/openrouter/free` → `enabled=True`、
   `providers=1`、`overlayModel=open_router/openrouter/free`、密钥只回显 `…ABCD` 指纹）。
   **仍未闭环的一步**：执行器每任务隔离 HOME 的 `settings.json` 还把 aggregate
   硬编码成 `{"enabled":false,"providers":{}}`，所以 DSH 子进程暂时不会真打这个端点。
   接线只剩两行（`internal/executor/executor.go` 的 `taskHome`，Lead 写入口、在途脏）：
   `modelpool.AggregateForDSHHome(dshHome, mgr.Specs())` 的返回值替换那行硬编码，
   并按返回的 `modelIDs` 把真可投影的模型标 `Routable=true`。
   验收判据与反假绿（providerId 写错必须报错、不得静默回落免费车道）见
   `docs/模型池-聚合车道接通补丁.md` §3。
   清单读不到时 `AggregateForDSHHome` 返回 `enabled:false` + 空映射 —— 与改造前等价，
   **绝不静默改道**（静默改道最坏：用户以为在用自建端点，实际在烧免费额度）。
5. **不修改 OFM 插件本体**：池子只读 `catalog/availability/settings`，不改插件文件
   （插件是那些文件的唯一写者）。
