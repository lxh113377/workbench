# 经验固化：给"活系统"加闭环时，闭环一定会断在没人写判据的那一段（2026-10-21）

> 触发：老大立规「思考模型只出方案，agent 模型负责执行，不然只出方案没有执行落地的模型无法闭环」。
> 落地过程中，真正花时间的不是写方案层，而是**发现闭环断在哪儿** —— 两次都断在
> "我以为做了、其实没生效"的接缝上，且两次都是测试先喊出来的。
> 本件不写过程，只固化可复用判据。

---

## 一、主判据（P0，可迁移）

> **一个多阶段的自动闭环，其可靠性等于"每一段接缝都有判据"的最小值。
> 没有判据的那一段，断裂是静默的 —— 系统照常返回 200、面板照常显示 running。**

本会话两次断裂都符合这个形状：

| # | 断裂点 | 表象 | 如果没写判据会怎样 |
|---|---|---|---|
| 1 | `store.Update` 的 mutator 里调 `store.Get` | 测试挂 120s 超时，栈停在 `RWMutex.RLock` | 生产上表现为"偶发卡死一个任务槽"，日志里啥也没有，重启就好 → 永远不会被当成缺陷 |
| 2 | `NormalizePlan` 漏补 `ReplanRounds` 零值 | 老安装升级后 `shouldReplan` 恒 false | 新功能对**所有存量用户**不生效，只有全新安装能跑 → 自测全绿、老板机器上就是没反应 |

第 2 条尤其值得记：**它的受害面正好是"没有跑测试的那批环境"**。
写代码的人用默认配置（新装）验证，永远不会撞上。

## 二、四条从本会话长出来的具体判据

### 2.1 迁移必须断言"迁移后字段非零"，而不是断言"迁移函数跑过了"

`TestNormalizePlanEnablesForOldSchema` 断言的是 schema<6 → `Enabled=true` 且 
`AppendPlanToPrompt=true` 且 tier/minutes 是默认值，**逐字段**。
而 `ReplanRounds` 一开始没在断言清单里 —— 于是它漏了整整一轮才被抓到。

**做法**：迁移函数的测试用"表驱动 + 覆盖每个新增字段"，而不是抽一个代表性的字段验一下。
新增字段忘了补默认值时，只有逐字段断言会红。

### 2.2 锁内调用必须能被静态识别："mutator 里不许读回自己"

Go 的 `sync.RWMutex` 不可重入。`store.Update(id, func(t *Task){ ... })` 的 mutator 
运行在写锁内，**在里面调 `store.Get` 就是自锁**，而且不会有任何编译期提示。

**做法**：把"Update 的 mutator 只做字段赋值"当成硬约束写进注释（本会话已写进 engine.go:922 附近）。
需要读最新值就在 Update **之后**再 Get 一次。契约测试里另有一条：
`TestScheduleReplanResetsToQueuedAndCountsRound` 会在自锁时直接超时挂掉。

### 2.3 新增"中间档"后，原有终态契约的前置条件会过期 —— 要改前置，不许改断言

新增 replan 分支后，`TestCompleteTaskDegradedOnVerifyFail` 与 
`TestRepairExhaustedFallsToDegraded` 变红：它们只设满 `RepairRounds` 就期望 degraded，
但现在"用尽"是**两维**的（RepairRounds + PlanRounds）。

**做法**：补前置条件（把 PlanRounds 也设满），断言（degraded / Verified=false / 
FailReason 含退出码 / 不计今日产出）**一条都不动**。
若改了断言，"契约测试"就退化成"跟随实现的快照"，失去告警能力。

另外**必须补一条新用例锁住新增的中间档**（本会话：`TestRepairExhaustedButReplanAvailableGoesQueued`），
否则新分支只是"碰巧没破坏老用例"，没有任何东西保证它自己是对的。

### 2.4 双角色（思考/执行）拆分后，要能证明"两个角色真的是两次调用、两个模型"

光把代码拆成两段不够 —— 完全可能拆完后两次调用用的是同一个模型、或者第二段拿到的还是原 prompt，
而系统"看起来"在跑双角色。

**做法**：用**记录型桩执行器**（recordRunner）断言四件事：
1. 调用次数 ≥ 2；
2. 第 1 次的 prompt 是方案提示词；
3. 第 2 次的 prompt 含"执行指令"且 **≠ 原 prompt**；
4. 两次的 model id 不同（当显式指定了 plannerModels 时）。

这四条已固化进 `--plan-selftest`（离线，不耗额度，12/12 PASS），可随时复验。

## 三、"离线自检"这件事本身是一条经验

本会话最后加的是 `--plan-selftest`，不是又一个单测。理由是：

> **判据如果只能靠"跑真实外部依赖"来验证，它就等于没有 —— 因为没人会天天跑。**

双角色闭环的真实验证需要跑真模型（几分钟 + 会撞 429）。一旦验证成本高到那个程度，
结果必然是"上线时验一次，之后靠信仰"。用桩执行器把整条链（方案解析 → 渲染指令 → 
真实验收 → 失败回灌 → 重规划入队）在临时目录里跑一遍，成本降到几秒。

同款范式仓库里已有先例（`--autonomy selftest`），本会话是**补上同一水准**，不是发明新东西。

配套一条守卫：`TestMainDispatchKeepsPlanSelftestFlag` 用真实二进制黑盒验证 
`--plan-selftest` 没被从 CLI 分发表里吞掉 —— 照抄 `--ui-probe` 那次事故的教训
（分发表整格消失、源码能编译、测试全绿、但参数静默回落成 GUI 启动）。

## 四、防复发清单

### 4.1 给系统加"多阶段闭环"时
- [ ] 每一段接缝是否都有独立判据？（不是"端到端跑通一次"，而是每段可单独证伪）
- [ ] 新增的中间档是否有对应用例？（否则它只是碰巧没破坏老用例）
- [ ] 终态契约用例的前置条件是否需要更新？（只改前置，不改断言）
- [ ] 新增配置字段是否在迁移测试的**逐字段**断言清单里？
- [ ] 是否存在"只有全新安装才生效"的风险？（老配置零值路径必须实测）

### 4.2 写涉及锁的持久化代码时
- [ ] `Update(mutator)` 的 mutator 里有读操作吗？有 ⇒ 自锁，挪到 Update 之后
- [ ] 需要读回最新值时，是"Update 完再 Get"还是"Get 完再 Update"？后者会丢并发写

### 4.3 判据的可执行性自检
- [ ] 这条判据需要真实外部依赖吗？需要 ⇒ 有离线桩版本吗？
- [ ] 它挂在哪个入口上？CLI 参数类的有没有黑盒分发测试守护？
