# 性能基线口径（perf-baseline.json 的取证说明）

> 配套数据件：[perf-baseline.json](./perf-baseline.json)
> 消费方：[tests/check_perf.ps1](../../tests/check_perf.ps1) → `.github/workflows/ci.yml` 的 `Perf baseline gate` 步骤
> 立档：2026-10-20 19:45–20:05（Asia/Shanghai）· 取证机 LIUXINGHUI（Win11 / 32 逻辑核 / PowerShell 5.1.26100.9168 / FullLanguage）
> 起因：对标报告 §3.5 的四项读数（首页 11ms、EXE 7.74MB、内存 28.9MB、句柄 464）是**手工单次读数**，
> 没进 CI，防不住回归（知识盲区 B8 / 学习计划 L8）。本件把读数变成**带口径的机器判据**。

---

## 1. 一句话口径

**只登记本会话实测到的数值；测不到的一律写 `null` 并说明原因。**
`check_perf.ps1` 对 `null` 字段输出 `SKIP + 原因` 且**不计入 PASS**；一项判定都没做成时判 `rc=2 UNVERIFIED`，
绝不与 `rc=0 PASS` 混同。「没测成」在三门退出码里是独立一档。

## 2. 每个字段的取证方式

| 字段 | 值 | 取证命令（可复算，见 §7） | 实测读数 |
|---|---|---|---|
| `exeMaxBytes` | 20971520 | `Get-Item dist/workbench.exe` → `Length`；`Get-FileHash -Algorithm SHA256` | 14,199,296 B（=13.54MiB）→ ×1.48 取整到 20MiB |
| `homeP95Ms` | 250.0 | 起 `--ui-probe` 实例，预热 5 次后 `Measure-Command { Invoke-WebRequest -UseBasicParsing }` 取 60 样本/轮 × 3 轮 | P95 = 77.53 / 1.20 / 1.18 ms |
| `residentMBMax` | 64.0 | 同进程 `Get-Process` 的 `WorkingSet64/1MB`，每轮 8 次 × 4s | 12.41 MB（全轮稳定） |

> **该字段的适用范围（2026-10-23 两轮实测校准，2026-10-23 已自我更正一次）**：
>
> 64MB 取自 `--ui-probe` **空闲探针**实例（12.41MB × 余量）。
>
> **第一版更正写错了（留此记录防重犯）**：本轮曾在 CHANGELOG 断言「基线口径被证伪」，
> 依据是 `--silent` 长驻实例实测 RSS 86~170MB、峰值 752MB。
> 复测后确认**那是误判** —— `check_perf.ps1:173` 起的是 `--ui-probe --expect-idle --seconds 120`
> **空闲探针**，取数窗口约 10 秒；本轮用同一命令实测 RSS **13.3 / 13.3 / 13.4 MB（3 轮）**，
> 与基线 12.41MB 吻合。**基线没错，判据与口径一致**。
>
> 真正缺的是**另一种形态的判据**，两者不可混用：
>
> | 形态 | 启动方式 | 记录规模 | 实测 RSS | 现有判据 |
> |---|---|---|---|---|
> | 空闲短生命周期·**空数据根** | `--ui-probe --expect-idle` | 0 条（fresh temp） | **13.3 MB**（3 轮） | `residentMBMax=64`（CI 走这条） |
> | 空闲短生命周期·**带当前记录数** | 同上 + 拷入裁后 queue.json | 5,006 条 | **52.9 / 52.8 / 53.0 MB**（3 轮，±0.1） | 见 §8 重取记录 |
> | 服务化长驻·**刚启动空闲** | `--silent` | 5,006 条 / 9.8MB | **46.9 MB**（10 次采样**完全恒定**） | `check_resident_longrun`（上界 96MB） |
> | 服务化长驻·**跑过任务后空闲** | `--silent` | 5,006 条 | 73 → 98.3 → **95.5~107.4 MB 来回**（GC 周期波动，5 分钟观察） | 同上（96MB 上界**偏紧**，见下） |
> | 服务化长驻·任务执行期 | `--silent` | 5,006 条 | 86~115 MB | 不判（随并发数变化属预期） |
> | 服务化长驻（裁剪前） | `--silent` | 33,740 条 / 69.3MB | 170 MB / 峰值 752 MB（6 任务并发） | 已由记录数上限约束 |
>
> 结论（两轮实测后最终版）：
> ① 基线字段**保持 64 不变** —— 它对自己的形态（空闲探针）是准确的；
> ② 长驻实例需要**新增**判据。而且本轮进一步证伪了「稳态波动 2 倍」这个说法：
>    对**同一状态**（空闲活实例）连续 10 次采样得到 `46.9, 46.9, ... 46.9` **完全恒定**；
>    先前看到的 46~99MB「波动」其实是**空闲态 vs 任务执行期**两种状态之差，不是抖动。
> ③ 故新判据必须**按「空闲定义」细分**。2026-10-23 进一步实测发现「空闲」本身有两档：
>    - **刚启动空闲**：46.9MB（10 次采样完全恒定）—— 可设固定上界；
>    - **跑过任务后空闲**：73 → 98.3 → **95.5~107.4 MB 来回**（5 分钟观察）——
>      Go 的 GC 有内存池保留策略，不随任务结束归还，且随「累计跑过多少任务」抬升。
>    结论：`check_resident_longrun` 的 **96MB 上界对「跑过任务的实例」偏紧**（实测峰值 107.4），
>    当前取 `-BoundMB` 参数化（默认 96，可按现场调高）；真正稳定的判据需要
>    「相对增长」而非「绝对上界」—— 记为待办，不硬编一个会误判的数字。
| `handleMax` | 512 | 同上 `HandleCount` | 139（全轮恒定） |
| `taskDurationSecMax` | `null` | — | 需外部模型网关凭据 + 真实额度，CI 内不可复现且会消耗额度 |
| `readyMsMax` | `null` | — | 本会话只测到「HTTP 轮询首次成功 <0.25s」，未单独计时进程创建→面板可服务的端到端冷启动 |
| `idleGrowthMBPerHourMax` | `null` | — | 需 ≥1h 长跑（`tests/soak_*.ps1` 那条通路）；本次资源采样窗口每轮仅约 32s，外推「每小时增长」即编造 |

P95 口径：样本升序后取第 `ceil(0.95 × n)` 个（n=60）。**不是**平均值、**不是**最大值。

## 3. 实测原始读数（同机同产物，三轮 + 一份不同启动方式的存档）

| 轮 | n | P50 | P95 | MAX | 常驻峰值 | 句柄峰值 | 线程 |
|---|---|---|---|---|---|---|---|
| r1 | 60 | 1.57ms | **77.53ms** | 87.14ms | 12.41MB | 139 | 8 |
| r2 | 60 | 0.98ms | 1.20ms | 1.33ms | 12.41MB | 139 | 9 |
| r3 | 60 | 0.97ms | 1.18ms | 1.22ms | 12.41MB | 139 | 7–9 |
| run0（存档，不并入基线） | 25 | 9.89ms | 23.62ms | 26.44ms | 35.86MB | 132 | 9 |

- **r1 是干扰轮**：取证时本机另有会话在跑（前 38 个样本 1.2–2.6ms，后 22 个跳到 16–87ms）。
  它是取证环境噪声而非产品退化，所以如实保留，不用 r2/r3 冒充「干净基线」把差异抹平。
- **上界为什么是 250ms**：干净轮 P95 ≈ 1.2ms，干扰轮 max 87ms。250ms ≈ 干扰轮 max 的 2.9 倍，
  只能保证抓到**量级塌方**（首页退化到秒级、事件循环卡死、监听失败走慢路径），
  **不宣称能抓 2× 退化**。这是当前证据能支撑的最大结论，写得更狠就是虚报。
- **run0 不并入**：它用 `Win32_Process.Create` 启动，WorkingSet 35.86MB ≈ r1–r3 的 3 倍。
  不同启动方式读数不可混用；留档是为了记下「同机不同启动方式差 3 倍」这个事实本身。
- **资源序列稳定 ≠ 无泄漏**：8 次 × 4s ≈ 32s 窗口内 WorkingSet/句柄零变化，只说明短窗口无增长，
  故 `idleGrowthMBPerHourMax` 仍为 null。

## 4. 与对标报告 §3.5 旧读数的差异（如实记账）

| 指标 | §3.5（2026-10-18 手工） | 本件（2026-10-20 探针） | 归因 |
|---|---|---|---|
| EXE 体积 | 7,747,072 B | **14,199,296 B（+83.3%）** | 真实增长：两天内新增 web / autonomy / modelpool 等代码与资产 |
| 首页体积 | 710 B | 1,363 B | 真实增长：界面简化后的新首页 |
| 首页响应 | 11ms（单点） | P50 0.97–1.57ms / P95 1.18–77.53ms | §3.5 是单次读数、本件是 60 样本分布；口径不同**不判谁对** |
| 常驻内存 | 28.9MB（生产实例） | 12.41MB（探针实例） | **口径不同**：`--ui-probe` 关掉托盘/自启/池探测/治理，不等于生产实例 |
| 句柄 | 464（生产实例） | 139（探针实例） | 同上 |

所以 `residentMBMax=64` 与 `handleMax=512` 是按「两个口径都要覆盖」定的**宽松**上界
（探针 12.41 / 生产 28.9 → 64；探针 139 / 生产 464 → 512）。它们能拦泄漏级别的膨胀（句柄上千、常驻上百 MB），
拦不住生产实例的中等退化。**生产口径的本会话复测值缺失**，这是本基线最大软肋（§6）。

## 5. 为什么 `Perf baseline gate` 在 CI 里不跑运行期检查

`check_perf.ps1` 默认只判**体积**，运行期检查要显式加 `-Runtime`：

1. §3 的读数是**本机**读数。GitHub `windows-latest` runner 的机型、核数、磁盘、防扫描软件都不同，
   把 1.2ms 级 P95 当 runner 判据会把 CI 判红在无关因素上——护栏判据的第一属性是**不误报**，
   一次性误红就把整个护栏的信任打掉。
2. 运行期检查要在 runner 上拉起真实进程并监听端口。本机 3 轮 `--ui-probe` 都 READY，
   但 headless runner 上未验证，不冒充已知。
3. 因此该步骤只做「体积上界 + 逐条运行期 SKIP 声明」。`-Runtime` 留作本机/自托管 runner 的第二条通路。

## 6. 仍然没被护栏覆盖的缺口

| 缺口 | 现状 | 要补什么 |
|---|---|---|
| **没有趋势历史** | 只有「上界判定」，没有把每次读数写成时间序列，看不到「缓慢涨到贴边」 | CI 里把 verdict + 读数控件化（`actions/upload-artifact` 或写进 issue 评论）才担得起「趋势护栏」四字 |
| **生产实例口径未复测** | 内存/句柄上界靠 §3.5 的历史手工读数撑着 | 在装机实例上跑 `--diagnose` + `Get-Process`，用实测替换 64/512 |
| **缺体积下界** | 只判 ≤20MiB。产物被截断/换成空壳时 `Verify artifact` 的 3MB 下界在基线之外（且截断判据已单列为 rc=1） | 加 `exeMinBytes` 让 `check_perf.ps1` 双向判，并让 3MB 也进基线 |
| **单点取证** | 3 轮 × 60 样本，一台机、一个产物 | 跨机/跨 runner 复测后才能收紧 P95 上界 |
| **`--ui-probe` 回落风险** | 若 CLI 分发表缺 `--ui-probe` 这一格，探针静默回落成 GUI 启动 → 运行期读数取不到。已由 `main_dispatch_test.go` 守护，`-Runtime` 也会判 UNVERIFIED 而非通过 | 保持那条 Go 测试在册 |
| **`dist/SHA256SUMS` 已过期** | 清单记 `C81CA500…BFA1`，产物本体实测 `BEC437CE…66DA1`（§3.8 预警的文档一致性风险已发生） | 产物重建后刷新清单；本基线不引用该清单 |

## 7. 复算步骤

```powershell
# 1) 体积与哈希
Get-Item 'D:/workdesktop/dist/workbench.exe' | Select-Object Length
(Get-FileHash 'D:/workdesktop/dist/workbench.exe' -Algorithm SHA256).Hash

# 2) 起探针（端口须空闲；--expect-idle 保证引擎未跑任务）
$dir = Join-Path $env:TEMP 'perf-baseline-probe'
$p = Start-Process -FilePath 'D:/workdesktop/dist/workbench.exe' -ArgumentList `
  @('--ui-probe','--dir',$dir,'--port','20777','--seconds','300','--expect-idle') `
  -WindowStyle Hidden -PassThru

# 3) 就绪 + 预热 5 次 + 60 个延迟样本 → P95
while ($true) { try { $null = Invoke-WebRequest 'http://127.0.0.1:20777/' -UseBasicParsing -TimeoutSec 2; break } catch { Start-Sleep -Milliseconds 250 } }
$s = 1..60 | ForEach-Object { (Measure-Command { $null = Invoke-WebRequest 'http://127.0.0.1:20777/' -UseBasicParsing -TimeoutSec 5 }).TotalMilliseconds }
($s | Sort-Object)[[int]([math]::Ceiling(0.95*60))-1]

# 4) 资源
Get-Process -Id $p.Id | Select-Object @{n='WS_MB';e={$_.WorkingSet64/1MB}}, HandleCount, @{n='Threads';e={$_.Threads.Count}}
Stop-Process -Id $p.Id -Force

# 5) 门禁三态自证（2026-10-20 实测：rc 依次为 0 / 2 / 1）
pwsh -File tests/check_perf.ps1 -Exe dist/workbench.exe                       # rc=0 PASS
pwsh -File tests/check_perf.ps1 -Exe dist/nope.exe                            # rc=2 UNVERIFIED
pwsh -File tests/check_perf.ps1 -Exe dist/workbench.exe -MaxBytesOverride 1   # rc=1 FAIL（变异自证）
```

## 8. 裁剪后基线重取（2026-10-23，记录在案）

取证方式与 §2 完全一致（`--ui-probe --expect-idle`、预热 5 次 + 60 样本），
唯一差别：数据根**拷入线上裁剪后的 queue.json（5,006 条 / 9.8MB）**再启动。

| 项 | 数值（3 轮） | 备注 |
|---|---|---|
| 产物 | 10,295,808 B，sha256 `61CB6C86…`（1.7.x 构建，mtime 10-22 21:33） | 在 exeMin/Max 界内 |
| 首页 P95 | 10.72 / 10.60 / 10.79 ms | 干净轮（基线字段 250ms 不动） |
| 常驻（带记录） | **52.93 / 52.81 / 53.02 MB**（±0.1，极稳） | 记录贡献 ~40MB |
| 常驻（空数据根） | 13.3 MB（见 §4 表） | CI check_perf 走的形态 |
| 句柄 | 180 / 185 / 197 | 基线 handleMax=512 不动 |

**两个诚实结论**：
1. **`residentMBMax=64` 不改** —— check_perf 的 CI 探针用全新空 temp 目录（实测 13.3MB），
   64 对该形态仍是 ~5× 余量；把带载读数混进同一字段会让上界对两种形态都失去意义。
2. 此前「探针 13.3MB 与基线 12.41MB 吻合」的说法**不完整**：那吻合的是空数据根形态；
   带当前记录数（5,006 条）的真实常驻是 ~53MB。这解释了 §4 表里「刚启动长驻空闲 46.9MB」
   的量级来源（同为加载了记录），也再次印证：**内存判据必须先声明数据规模形态**，
   脱离记录数谈常驻上界没有意义。
