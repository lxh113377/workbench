# 容器门禁 · 五阶段固化管理（2026-10-19）

> 入口：`tests/container-gate.ps1` ｜ 实测状态：**五阶段全绿（GATE_RC=0）**
> 由来：老大 2026-10-19 指令「用 Docker 虚拟机模拟，别乱折腾了」

---

## 一、为什么需要

宿主是 Windows。**本机 `go test` 全绿并不等于交付绿**——已实测到三类"本机绿、容器红"：

1. **平台耦合**：硬编码 PowerShell、盘符概念、Windows 危险路径表、增量落盘差异；
2. **跨平台构建断裂**：`shortcut.Guard()` 只定义在 `_windows.go`，而主程序无条件调用 ⇒ Linux 构建直接不通过；
3. **行为回归**：**能编译、单测全绿，闭环仍跑不到终点**（判据声明了却没实现，恒 false ⇒ 目标永不完成）。

同时上游免费车道按出口 IP 封禁，真实模型 e2e 在宿主上做不了 —— 容器里的**确定性通道替身**正好补上这一段。

---

## 二、五阶段与判据

| 阶段 | 跑什么 | 判据 |
|---|---|---|
| **VET** | `go vet ./...` | 退出码 0 |
| **TEST** | `go test ./... -count=1` | 退出码 0 |
| **BUILD** | `go build -trimpath ./cmd/workbench` | 退出码 0 |
| **CRITERIA** | 判据「声明 vs 实现」交叉校验 | `CRITERIA_COVERAGE_OK` |
| **LOOP** | 容器内确定性通道跑完整自主闭环 | `E2E_PASS` |

### 三态判据（禁止把"取不到数"洗成通过）

- **PASS** —— 该阶段退出码 0
- **FAIL** —— 退出码非 0 且可归因到源码（打印原始输出）
- **UNVERIFIED** —— 前置条件缺失（源码树不存在/为空、本地无镜像、缺验收脚本）

**退出码：0 全 PASS ｜ 1 有 FAIL ｜ 2 有 UNVERIFIED 且无 FAIL。**

## 三、用法

```powershell
# 全链（默认对 src-backup 跑，因为 workbench/ 尚在重建）
pwsh tests/container-gate.ps1

# 指向源码树
pwsh tests/container-gate.ps1 -Source workbench

# 只跑单项
pwsh tests/container-gate.ps1 -Only LOOP
```

### 作用域守卫

- 容器名统一 `wb-gate-<时间戳>-<阶段>`，**只删自己建的**；LOOP 阶段 RunId 唯一（固定名会与残留容器撞名，实测 exit 137）
- **不发布宿主端口**；宿主**只读挂载**源码；一切写入限容器 `/tmp`
- 本地无镜像时记 **UNVERIFIED**，**不自动拉取**（避免网络噪音污染判据）

## 五、已知的时序陷阱（实测踩到，必须记录）

**并发会话改源码会让门禁产生假失败。** 实测两例：

1. LOOP 阶段报 `undefined: artifact.CountWords` / `undefined: itoaEngine` —— 当时另一会话正把该调用改成
   `countWordsEngine`（`artifacts.go` mtime 11:38:13）。等待 75 秒后**同一命令 rc=0** ⇒ 不是真缺陷。
2. `CRITERIA` 阶段首次报 `invalid reference format` —— 真 bug：挂载串 `$mount` 定义在函数局部作用域，
   后续阶段取不到；已提到脚本作用域修复。

**处置原则**：门禁报 FAIL 时，**先看失败文件的 mtime 是否在最近几分钟内**，是则等稳定后复跑一次再定论。

## 六、与既有工作流的关系

| 工作流 | 触发 | 跑什么 | 判据 |
|---|---|---|---|
| `.github/workflows/ci.yml` | push/PR | windows-latest: vet + test -race + build.ps1（覆盖率门禁） | 源码质量 |
| `.github/workflows/autonomy-e2e.yml` | push/PR | ubuntu: 交叉编译 → 容器内闭环端到端 | 运行时行为 |
| **`tests/container-gate.ps1`（本地）** | 手动 | 上述两者的**超集**（含判据交叉校验与闭环行为） | 一站式 |

本地门禁是**宿主侧的快速预检**，CI 是最终保护面；两者判据一致，本地先绿能大幅减少无效 CI 轮次。

**双向都测过才算判据成立**：只测正向会漏掉「取不到数却报绿」这类假通过。

## 八、基础设施失败 vs 行为失败（LOOP 专用归类）

LOOP 阶段把容器退出码分三档，**禁止把「没测成」当「测得差」**：

| 退出码 | 归因 | 记录为 |
|---|---|---|
| 0 且输出含 `E2E_PASS` | 闭环真的跑到终点 | PASS |
| 125 / 126 / 137 | **基础设施失败**：137=容器被 `docker rm -f` 杀掉（并发争抢同名容器）；125/126=docker 拒绝执行 | **UNVERIFIED**，附原因与复核方式 |
| 其余非 0 | 行为不合格（判据未达） | FAIL |

实测由来：门禁首次跑 LOOP 偶发 exit 137，而单独跑 `docker-run.ps1` 是 E2E_PASS，
连跑两次 LOOP 也均 PASS ⇒ 判定为并发争抢的偶发，非行为缺陷。
