# 硬约束的机器保障缺口 —— 五轴审查报告（2026-10-25 · round 116-118）

> 范围：`CONTRIBUTING.md` 的「不可违反的硬约束」6 条 ⟷ `.github/pull_request_template.md`
> 的「硬约束自查」6 项 ⟷ `tests/check_*.ps1` 41 个门禁 ⟷ Go 测试面。
> 按 `review-five-axis` 模板格式产出，可直接贴 PR。所有数字为实测（含测量方法）。

## 0. 为什么审这个

objective 的原话是把「硬约束」落到可机器判定上。本仓的治理形态是**三层**：

| 层 | 载体 | 数量 |
|---|---|---|
| 声明 | CONTRIBUTING 硬约束表 | 6 条 |
| 自查 | PR 模板 checkbox | 6 项 |
| 强制 | tests/check_*.ps1 + Go 测试 | 41 门禁 |

**三层不重合就是缺口**：声明了但没人强制的约束，等于靠人自觉 —— 正是报告 §2
在册的失效形态「硬约束写在文档里」。

## 1. 正确性

- **P0 无。** 三层里没有任何一层给出错误结论（不存在"门禁说绿其实红"）。

## 2. 架构（本次主发现）

- **P1｜硬约束 #4「不挂 dsh-web-app」是「一律不合并、没有例外」级，但三层里只有一层提到它。**
  实测（`git grep -rn dsh-web-app`，逐 pathspec 查 rc）：

  | 位置 | 命中 |
  |---|---|
  | 全仓 `dsh-web-app` 字符串 | **1 处** —— `dshprofile/bootstrap.go:8` 的**注释** |
  | `tests/`（41 个门禁）| **0 处** |
  | `.github/pull_request_template.md` | **0 处** |
  | CONTRIBUTING | 有（约束表 #4 + 「违反 1 或 2/4 一律不合并」）|

  今天这条约束**只靠 `Bundles` 白名单的写法**成立 —— 白名单里没有它，就挂不上。
  但 `dshprofile` 包两个受跟踪测试文件（13 个 Test）**没有一个断言 Bundles 的内容**。

  **为什么它是 P1 而不是 P2**：违反的后果不是崩溃，是 headless 进程永不退出
  （CONTRIBUTING 记的实测：卡死 150s+）。在 7×24 无人值守里表现为「任务不再推进」——
  **难归因、难发现**，且这是本仓最核心的运行形态。

  **已落地修法**（本轮）：新增 `workbench/internal/dshprofile/bundles_contract_test.go`，
  两面判据 —— ① 黑名单（Bundles 任一项含 `web-app` 即 Errorf）；② 白名单快照
  （必须恰为 base/headless/our-free-model 三项，增减要显式改测试与 CONTRIBUTING）。
  CI 的 `go test -race ./...` 自动覆盖（无需单独挂载）。
  双向变异验证见「合并结论」。

- ~~P2｜硬约束 #6 缺自查项~~ —— **已实施（2026-10-25 round 120）**：
  原实测：`config` 包 9 个受跟踪测试文件里，BuildLayout / DataRoot / workbench-output
  三个词出现 **0 次** —— 硬约束 #6 只靠 `paths.go` 一行 Join 成立，改那一行不会让任何测试变红，
  却会让 10 个派生路径整体搬家（面板读不到 queue.json、导出目录消失、恢复找不到 state.json）。
  新增 `workbench/internal/config/layout_contract_test.go`（TestBuildLayoutContract）钉三条：
  ① 数据根名字必须是 workbench-output；② Layout 每个字符串字段按其归类挂在
  Root/DataRoot/RuntimeDir 之一之下（**反射遍历 + 显式归类映射，两层**）；
  ③ DSHHome 绝不落进用户 ~/.dsh（与硬约束 #2 同源）。
  三向变异均判红并精确点名：数据根改名 / TasksDir 改挂 Root / DSHHome 挪进用户 profile；
  还原 ⇒ rc=0，且全部在临时 worktree 内完成，主仓 `paths.go` 未被污染（已复验 clean）。
  **为什么必须两层（本轮第二次栽在同一处，见附节）**：反射单独用会漏 reparenting ——
  我第一版把显式归类映射删掉、只要求「落在三大根之一」，于是「TasksDir 从 DataRoot
  改挂到 Root」直接漏过（root 下的 tasks 当然以 root 为前缀）。反射保证「新增字段不会
  静默漏守」，显式映射保证「改挂别处会被发现」，缺一不可。

- **P2｜约束 #5「删除走回收站」：阀本体覆盖良好；缺的是"新增删除路径是否都过安全阀"——
  本轮（round 119-121）已逐点核对完毕，结论见 §6：三类删除语义不同，不建门禁，改抓出 1 个真缺陷并补行为测试。**
  实测：`refuseDangerousPath` 实现 3 文件 + 测试 1 文件（跨平台纯字符串判定，不碰文件系统）；
  但 `trash` 相关实现 2 文件、测试 0 文件，且无 `tests/check_*.ps1` 门禁。
  **我一度把这条写成「无任何门禁覆盖」—— 偏严了**，准确说法是"有 Go 单测覆盖安全阀函数本身，
  但没有判据校验新增删除路径是否经过它"。两者不同，已按准确表述记录。

## 6. 约束 #5 的逐点核对结果（round 119-121 执行）

按 §5 门禁建议 #3 的前提「先定义删除路径的可机判形态」，本轮把全仓删除原语逐点过了一遍
（`git grep -nF os.Remove / os.RemoveAll`，排除测试与 retention 包本体）：**12 个生产文件、15 处调用**。
按语义分类，不是一刀切要求「都走回收站」：

| 类别 | 调用点 | 是否应过安全阀/回收站 | 结论 |
|---|---|---|---|
| A 用户数据删除 | `retention` 包 3 处 Trash | 必须 | 已覆盖（`refuseDangerousPath` + 跨平台同序）|
| B 自有临时文件清理 | docx / atomic / modelpool 日志滚动 / shortcut / selftest / probeWrite | 不该进回收站 | 语义正确，但有实现缺陷（见下）|
| C 链接/junction 摘除 | workspace_guard 2 处（**2026-10-25 round 158：该 CLI 自证件因零引用被作为死代码删除**；其断言与 internal/workspace 的 ResolveWriteSymlinkEscape / IsWithinBoundaries / AuditAppendReadTail 重复，且自身含两处「SKIP 记成 PASS」。本行记录的是当时的取证来源，判据结论不因该件删除而失效）、dshprofile 1 处、executor linkDir 1 处 | 摘链非删数据 | 探针实测确认不伤 target |
| D 单文件标志清理 | engine user-quit.flag、queue 无关 | 无风险 | 无需动作 |

**B 类抓到 1 个真缺陷（已修）**：`web/writeDocx` 自制原子写 —— 固定后缀 `.tmp` +
先删目标再 rename。探针实测并发导出同一目标必有一方失败：

    RESULTS=[B-ERR:rename …export.docx.tmp → export.docx:
             The process cannot access the file because it is being used by another process. A-OK]

修法按 #39 选最优而非折中：zip 写内存 buffer 后交统一的 `config.WriteFileAtomic`
（同函数 md/txt 分支本就走它）—— 消除「固定后缀互踩 / 删目标丢失窗口 / 双实现并存」，
并新增 `web/docx_atomic_test.go` 做行为级锁定（旧实现在 worktree 里 3/3 稳定判红）。
**更正（2026-10-25 round 123，CI 证伪）**：此处原写「一次消除三缺陷」，含「并发已解决」
的含义，属 over-claim。并入 `config.WriteFileAtomic` 只解决了临时文件互踩；同一路径的
目标与 `.bak` 仍是共享名，四个并发 writer 会因 rename 交错**全部失败**（CI run
40127263998 实测，本机复现率约 1/30）。已在 config 层加 `pathLocks` 串行化修复，
详见 docs/原子写同路径并发-五轴审查-2026-10-25.md。

**C 类推翻了我自己的怀疑（这条比修 bug 更值钱）**：`linkDir` 在 Stat 失败后
`os.RemoveAll(dst)`，我初判像经典「rd /s 删穿 junction」风险面。一次性探针实测结论相反 ——
Go 把 junction 认成普通目录、Stat 成功即早退，即便 RemoveAll 也只是摘链，target 内容完好；
另用控制组（直接毁 target 内容 ⇒ 判红）证明断言不是空转，并直测出
`rd /s /q` 在本机同样只摘链（「删穿」是 XP 时代行为，Vista+ 已修）。
据此新增 `executor/linkdir_target_safety_test.go` 把两层锁进 CI。

**为什么不建「必经安全阀」门禁**：逐点核对后确认三类删除语义根本不同 ——
要求 B 类（临时文件）走回收站反而是错的（7×24 会把回收站灌满、且违反「可再生即删」的
设计）；而「新增删除路径」无法用文本判据区分 A/B/C，做成门禁必然对 B/C 误报。
正解是本轮做的这种**低频人工逐点审计 + 对被抓到的缺陷补行为测试**，
而不是养一个易误报的门禁（与 §5 元建议 #4 同一取舍）。

## 合并结论

**可合并。** 理由：

1. **改动面小且行为零变化**：新增一个 Go 测试文件 + PR 模板补两条自查项；
   `dshprofile` 包全量测试 rc=0，既有 13 个 Test 无一被影响。
2. **双向变异通过**：
   - 注入真实违反（往 `Bundles` 加 `@deepseek-ai/dsh-web-app`）⇒ rc=1，
     点名「Bundles 含 ... 违反硬约束 #4」并附快照变化提示；
   - 还原 ⇒ rc=0，`bootstrap.go` 与原始**字节一致**。
3. **空转防护**：测试首行 `if len(Bundles) == 0 { t.Fatal(...) }` —— 白名单被清空时报错
   而非静默判绿（round 53/99 vacuous pass 家族的定规）。
4. 约束 #6 的 DataRoot 测试已于 round 120 落地（见 §2 与文件 layout_contract_test.go）；
   约束 #5 的删除路径已在本轮逐点核对完毕（§6），结论是**不建门禁、改补行为测试** ——
   因此「登记不夹带」两项均已走完（#6 落地于 round 120，#5 逐点核对完毕于 round 121）。
