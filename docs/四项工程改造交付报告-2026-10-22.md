## 2. 改造①（P2-4 · 高）：看门狗活跃度纳入「产出文件 mtime」

**上游依据**：river `internal/jobexecutor/job_executor.go:335-378 watchStuck`（以 context 取消响应为观测点）；
asynq `recoverer.go`（按 lease deadline 判定）。

| 项 | 内容 |
|---|---|
| 缺陷形态 | `res.Touch()` 只在 `consume()` 解析到 stdout 事件时刷新；artifact 协议下模型常「先静默写文件、最后才吐 final」，静默写盘期可达数分钟 ⇒ 超过 `StallSeconds`（默认 420s）即被判卡死杀树，**已写出的产物一并丢失** |
| 修法 | 活跃度改**双信号取较新者**：① stdout 事件 ② workspace 产出文件 mtime（`LatestOutputMtimeMs`，扩展名白名单与 `hasWorkspaceOutput` 同口径，目录不可读时退化为「无信号」= 改造前行为）；判定收敛到纯函数 `IsStalled` |
| 落点 | `internal/executor/pure.go`（`LatestOutputMtimeMs` / `stallLimitFor` / `IsStalled`）、`executor.go` 看门狗 goroutine |
| 完成标准 → 实测 | 判据 5 条绿；变异「`IsStalled` 回退单信号」→ **判红**（两条判据同时点名）；executor 覆盖 49.2% → **52.9%** |

## 3. 改造②（P2-1 · 高）：retry 策略非法值 → 撤回退避 + 留痕

**上游依据**：river `job_executor.go:563-571` —— 策略给出非法值（早于当前时间）时
`WarnContext` 并回落到 `DefaultClientRetryPolicy`，而不是静默钳制。

| 项 | 内容 |
|---|---|
| 缺陷形态 | `nextDelay()` 对算出的非正等待一律钳到 **1ms**（热循环配方：高频失败时每秒重试，既打上游又刷台账）；且「配置写坏」与「值本来就小」在日志里完全同形 |
| 修法 | 构造期矛盾（`MaxDelayMs < BaseDelayMs`、抖动越界、退避列表非正项）登记 `Policy.Fixes`；运行期算出非正/低于基准一半的等待时**回落可信默认值**并登记 `Policy.Warnings`（去重）；引擎在 3 处装配点读 `Fixes` 写 WARN |
| 落点 | `internal/retry/retry.go`（`PolicyFix` / `New` / `nextDelay` / `warnInvalid` / `Warnings`）、`internal/engine/helpers.go`（`logRetryPolicyFixes`）、`engine.go` 三处调用点 |
| 完成标准 → 实测 | 判据 18 条绿；变异「删抖动塌陷兜底」→ **判红**（实测抓到 692ms 热循环值）、「删 Fixes 登记」→ **判红**；retry 覆盖 89.1% → **95.7%** |

## 4. 改造③（P2-2 · 高）：config 跨字段一致性校验 + 迁移判据修正

**上游依据**：river `client.go:528-534` —— 一条跨字段判据收敛 `rescueAfter` 与 `jobTimeout` 的关系。

| 项 | 内容 |
|---|---|
| 缺陷形态 | `Normalize()` 有 31 处**单字段**钳制、**零处跨字段**。「每个字段各自合法、合在一起不 work」更隐蔽也更难排查 |
| 修法① | 新增 `normalizeCrossField`，只修**功能不可达**的三条：<br>`StallSeconds >= DefaultTimeout` ⇒ 看门狗永不可能先于硬超时触发（stalled 死配置）→ 钳到超时一半；<br>`ReplanRounds >= RepairRounds` ⇒ 推翻「先用便宜手段」的顺序 → 钳到返工-1；<br>`PlannerMaxMinutes >= DefaultTimeout` ⇒ 方案阶段挤占全部执行预算 → 钳到超时一半。<br>每条登记 `Config.Warnings`（`canonicalizeForCompare` 里抹平，防无谓重写） |

## 5. 改造④（P2-3 · 中）：留痕先于状态生效 + 判死路径补台账

**上游依据**：asynq `processor.go:336-338` —— `errHandler.HandleError` 在 `switch` **之前**调用，
使「任何一条失败路径都留痕」在结构上不可能被跳过。

| 项 | 内容 |
|---|---|
| 缺陷形态 | ① `failTask` 顺序是 `Update`(迁状态) → `Audit`，存在窗口「状态已是 failed，台账查不到为什么」；`Update` 出错时只 emit **瞬时事件（不落盘）**，任务停在 running 既不重试也不统计<br>② `rescueInterrupted` 判死分支**改造前零审计** —— 判死是不可逆终态决策却无任何台账<br>③ `finishCancelled` 只在迁移**失败**时才写审计，正常取消只有瞬时事件 |
| 修法 | 新增 `writeLedgerThenTransition` seam（沿用本仓 `autonomy.writeLedgerThenActivate` 同型范式，单测用注入闭包断言次序）；三处全部改为「先留痕后生效」；`Store.Audit` 由 void 改为**返回错误**（改造前 `_ = s.audit.Append` 把失败全吞）；审计写失败时退到任务事件流，使「至少一处留痕」成为结构保证 |
| 落点 | `internal/engine/ledger_order.go`（新）、`engine.go`（`failTask` / `finishCancelled`）、`stuck_rescue.go`、`internal/store/store.go` |
| 完成标准 → 实测 | 判据 6 条绿；变异「seam 反序」→ **判红**（实测抓到 `[state ledger]`）、「摘掉判死专用审计」→ **判红**；engine 覆盖 74.2% → **75.3%** |

### 5.1 判据强度的一轮返工（关键教训）

第一版判据**只搜审计全文里有没有「判死」字样**。变异「摘掉新增的 kind=error 审计」时它照样全绿 ——
因为 `store.Transition` 自己也会写一条 `kind=transition` 的审计，而它的 note 文案与新增审计高度重合。
加严为**按 `kind=error` 过滤**后才真正抓住（变异实测输出里只剩 6 条 `kind=transition`，无一条 `kind=error`）。

同类返工本轮共三次（另两次见 §7），共同教训：
**变异测试必须先在实现上制造真实回退并确认行为差异；判据要直接调用被测的纯函数/seam，不在测试里重写逻辑。**

## 7. 本轮被自己纠错的 4 处（防重犯）

1. **看门狗阈值方向写反**：首版判据写「`StallSeconds` 必须**大于**超时」（照搬 river 的 `rescueAfter > jobTimeout`），
   被既有测试 `TestMigrationV1AlsoFixesWatchdog` 抓出 —— 本项目的看门狗判**活动停滞**，不是跑得太久，
   关系恰好相反（安全网必须先于硬兜底触发）。教训：**跨项目迁移判据时要先确认被迁移语义的观测点是否同构**。
2. **判据在测试里重写逻辑**：看门狗与台账顺序判据第一版都在测试内重写了一遍判定，变异回退时照样全绿。
   改为直接调用被测纯函数 `IsStalled` / seam `writeLedgerThenTransition` 后才抓住。
3. **变异没真变**：`config` 变异第一版编辑锚点里原调用行仍在注释之后，实现并未回退 ⇒ 假绿。
   教训：**变异后必须确认回退点在编译产物里真的不存在**（本轮靠先读回文件确认）。
4. **判据只看文案不看结构**：判死审计判据被 `Transition` 顺带写的那条审计骗过；
   加严为按 `kind` 过滤才成立。
