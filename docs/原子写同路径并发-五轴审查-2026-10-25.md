# 原子写同路径并发竞态 —— 五轴审查报告（2026-10-25 · round 123）

> 范围：`workbench/internal/config/atomic.go`（`WriteFileAtomic` / `WriteJSONAtomic`）。
> 可直接贴 PR。所有结论有实测出处（含 CI run 号与复现率），未测成的都标明。

## 0. 结论先行

**生产代码缺陷，非测试缺陷。** `WriteFileAtomic` 是「全仓唯一原子写入口」，
但同一目标路径被多个 writer 并发写时**会整体失败**。上一轮（round 121）我在报告里
写「一次消除三缺陷」，**其中「并发」这一项是 over-claim** —— CI 用我的测试把它证伪了。
本轮补锁并更正。

## 1. 正确性（主发现）

- **P1｜同路径并发写全部失败。** 现场 CI run 40127263998（纯净检出 go test）：

  ```text
  --- FAIL: TestWriteDocxConcurrentExportsAllSucceed (0.21s)
      docx_atomic_test.go:59: 第 1 个并发导出失败: 替换目标文件失败（已从备份恢复）:
        rename ... being used by another process
  FAIL  workbench/internal/web
  ```

  机制：`tmp` 名唯一只解决了「临时文件互相覆盖」；**目标文件与 `.bak` 仍是共享名**。
  `rename(path, backup)` 与 `rename(tmp, path)` 在 writer 之间交错 —— A 把目标搬去
  `.bak` 的同时 B 正动同一目标，于是四个 writer 全返回错误。

- **flaky 特征与复现率（实测，不靠印象）**：主 `vet + test (race)` job 通过、只有
  快照 job 红；本机 `-count=30` 重复实测**无锁版 30 轮内至少 1 次失败**（约 1/30），
  带锁版 **30 轮 0 失败**。这条正是「本地绿 CI 红」的时序类形态。

- **修法**：在正确的层（统一入口）加**同路径串行化** —— `pathLocks sync.Map`
  按 `filepath.Clean(path)` 取 `*sync.Mutex`，`writeFileAtomicWith` 入口
  `defer lockFor(path).Unlock()`。不同路径互不阻塞。

  为什么不选另一条路（给 `.bak` 也加唯一名）：那样四个 writer 仍在抢目标文件本身，
  失败只是换个形式；串行化一次同时解决目标与 `.bak` 两处竞态。

- **加锁前的锁序复核**（在册教训：round 111 自己写过的自死锁形态）：
  持锁期间只做文件系统调用，不再取本包或他包任何锁；外部 `Store.Replace` 是
  `s.mu` 到本锁的**单向**顺序，反向不存在 ⇒ 无环。实测 `go test -race` config+web 均 rc=0。

## 2. 可读性

- **P2｜`pathLocks` 不清理条目**（每个写过的不同 path 留一个 mutex，约 100-200B）。
  增长由「不同路径数」而非写次数决定：queue/state/config 是固定名，导出文件名带时间戳
  且是用户触发的低频操作。**不做清理的理由不是省事** —— 在被持锁时删条目，
  后续 `LoadOrStore` 会拿到第二把锁，等于把竞态换个地方复现。已在注释里写明取舍。
- 同处声明边界：`key` 区分大小写而 Windows 文件系统不区分，同一文件写成两种大小写
  仍可能各拿一把锁。本仓路径全部由 `config.BuildLayout` 单点派生（不存在第二种写法），
  为不存在的情形加平台分支归一反而引入新风险面，故不做、但写出来。

## 3. 架构

- 无新增问题，且**这条缺陷本身就是架构收益的证据**：因为全仓只有一个原子写入口，
  一处加锁即覆盖 config/queue/state/导出/面板保存全部路径；若当时保留 docx 的
  自制原子写（round 121 消灭的那条双实现），这个竞态就会在两处独立存在。

## 4. 安全

- **本轴未发现问题**，检查了什么：锁 key 来自内部派生路径，不受外部输入直接影响；
  `-RedirectStandardOutput`、`.bak` 均不落敏感内容（`.bak` 与目标同目录同权限）；
  串行化不改变原有拒绝逻辑（`refuseDangerousPath` 不在此路径上）。

## 5. 性能

- **本轴未发现问题**，实测口径：同路径串行化会让并发 writer 排队，但这是**正确性
  优先的必要代价** —— 修复前的行为是「四个 writer 全部失败」，排队换来的是全部成功。
  不同路径不受影响（key 按 path 分片）。实测 `config` 包全量 2.1s、`web` 包 4.9s（-race），
  与修复前同量级；新判据 60 轮 × 4 writer 仅 0.66s。

## 合并结论

**可合并。** 依据：

1. **双向验证闭合**：无锁版（worktree HEAD `0c55a0e`）第 2 轮即判红并点名
   「同路径并发竞态，pathLocks 未生效？」；带锁版 60 轮 × 4 writer 全绿、无 `.bak`/`.tmp` 残渣。
2. **判据加在缺陷所在的层**：新增 `config/atomic_concurrent_test.go`（性质一：全部成功；
   性质二：内容不撕裂 —— 四个等长同字节载荷，混合一眼可辨）。web 层那条并发测试
   只是撞它的下游；不在 config 层钉住，将来别的使用者踩同一坑没人报警。
3. `-race` 两包 rc=0、vet rc=0、gofmt clean、BOM 0、纯 LF、反斜杠差 0（我没引入新的）。
