# 经验固化：本机「个人 AI 工作台」两大现场问题的根因模型与防复发清单（2026-10-20）

> 触发：老大连续两轮现场反馈 ——
> ① 「怎么后台显示有这么多个人ai工作台在运行」→ 已修（实例回收）
> ② 「我这里看到的是什么,关不掉」→ 已修（托盘窗样式 + explorer 缓存）
> 本件不是事后感想，是把**可复用的判据、工具、检查项**固化下来，防止同型问题第三次出现。

---

## 一、两个现场其实是「同一族缺陷」的两张脸

| 现场 | 表象 | 容易被误判成 | 真实根因层 |
|---|---|---|---|
| ① 后台一堆实例 | 任务管理器 ~24 个同名进程 | 程序自己重复启动/死循环 | **生命周期**：四条拉起链 + 零回收者 |
| ② 任务视图一堆卡片 | Win+Tab 里十几张空白卡，关不掉 | 进程没关干净 / explorer 卡了 | **窗口收录语义**：托盘消息窗缺 WS_EX_TOOLWINDOW + Shell 缓存不清 |

共同点：**都发生在「进程/窗口的生命周期末端」，而系统的所有设计只覆盖「创建端」** ——
拉起有 4 条路径（注册表 Run、计划任务、SelfHeal、探针），但枚举 / 回收 / 取消收录一条都没有。

> **可迁移判据（P0）**：一个资源如果有 N 条创建路径，就必须有 1 个**独立的、机器级枚举**的回收者；
> 否则任何一条路径的漏收都会线性累积成「越用越多」。

## 二、根因模型

### 2.1 实例只增不减（四层）

| 层 | 机制 | 为什么自然兜底失效 |
|---|---|---|
| L1 拉起路径多 | HKCU Run / WorkBenchKeepAlive / supervisor.SelfHeal / 各探针脚本 | 四条互不知情 |
| L2 单实例锁按目录 | internal/single 锁的是 layout.RuntimeDir；RuntimeDir 由 EXE 所在目录推导 | --dir 不同 = 不同实例域，锁天然允许 N 个并存 |
| L3 无人回收 | keepalive.ps1 只判 Select-Object -First 1（至少一个在跑） | 从不判重、从不清理 |
| L4 关键放大 | Win32_Process.Create 让子进程 PPID 落到常驻 WmiPrvSE | 「父死子退」失效，孤儿可无限期存活 |

### 2.2 幽灵卡片（三层）

| 层 | 机制 | 证据 |
|---|---|---|
| L1 窗口样式 | tray 的 CreateWindowExW(dwExStyle=0, ...) 缺 WS_EX_TOOLWINDOW(0x80) | 实测 ex=0x00000100 TOOLWINDOW=False |
| L2 Shell 缓存 | 任务视图条目由 explorer 维护，进程死亡/强杀不清缓存 | 全机 ghost 扫描：进程层 ghost_count=0，但卡片仍在 |
| L3 关联 | 每个实例一张卡 × 实例只增不减 = 卡片数等于历史实例数 | 清理前后对账一致 |

## 三、修法（已落地）

### 3.1 实例侧：tests/instance_guard.ps1（机器级盘点 + 有界回收）

家族判据 = 产物 ProductName = 个人AI工作台（含改名副本）。六条裁决：

| 裁决 | 规则 |
|---|---|
| A | 生产实例最多 1 个（优先留 runtime/workbench.lock 登记的 pid） |
| B | user-quit.flag 在册且 age 大于 max(宽限,300s) → 回收 |
| C | 探针超过自身 --seconds 预算 + 宽限 → 回收（违约未退） |
| D | 探针无预算且 age 大于 TTL(10min) → 回收 |
| E | **全局硬上限 MaxInstances=6**，超限从最老探针回收（绝不碰生产实例） |
| F | 探针父进程已死且过宽限 → 回收 |

接入点：tests/keepalive.ps1 在 Repair-IntegrityLabel 之后调用 -Apply -Quiet；
WorkBenchKeepAlive 计划任务**每分钟**一跳 ⇒ 每分钟一次机器级清场。
退出码 0=干净 / 1=有动作；每次真清理留痕 runtime/instance-guard.log。

### 3.2 窗口侧：workbench/internal/tray/tray_windows.go

| 项 | 改成 | 为什么 |
|---|---|---|
| dwExStyle | 0 → WS_EX_TOOLWINDOW (0x80) | 不进 Alt-Tab / 任务视图 |
| dwStyle | 0 → WS_POPUP | 配合工具窗语义 |
| 创建后 | SetWindowPos(..., SWP_HIDEWINDOW) | 双重保证永不显示 |
| 窗口标题 | 个人 AI 工作台（内部消息窗口，请忽略） | 万一被第三方 Shell 插件收录，用户能认出是内部窗 |
| 类名 | 提常量 trayWindowClassName | 取证工具与单测按它定位，改名必须同步 |

**刻意不加 WS_EX_NOACTIVATE**：托盘右键菜单依赖 SetForegroundWindow(自身) 才能弹出与失焦收起；
加了会让菜单卡在屏上 —— 那本身就是另一个「关不掉」。

### 3.3 已存在的老卡片：重启 explorer

任务视图缓存属于 explorer 进程，重启即重建（explorer 自动重启，桌面/任务栏几十秒恢复，不丢文件）。
本次执行：explorer pid=12128（已跑 28.5h）→ 强杀 → 系统拉起 pid=38208；之后任务视图仅剩 DSH 一张卡。

## 四、防复发清单（下次改动直接照跑）

### 4.1 新增/修改任何「拉起进程」的路径时
- [ ] 新进程会被 instance_guard.ps1 的家族判据识别吗？（ProductName 是否被改）
- [ ] 是否带了能区分「探针/测试」的子命令？（ProbePattern 是否覆盖新子命令）
- [ ] 是否可能脱离父进程作业对象（Win32_Process.Create / DETACHED_PROCESS）？
      是则必须确认有机器级回收，别指望「父死子退」
- [ ] 是否声明了自己的 --seconds 预算？（有预算才能被 C 裁决精准回收）

### 4.2 新增/修改任何「窗口」时
- [ ] 它是**功能窗口**还是**消息窗口**？消息窗口必须带 WS_EX_TOOLWINDOW
- [ ] 它会被 Alt-Tab / 任务视图收录吗？用 EnumWindows 按类名枚举自查（模板见 xtmp/trayverify.ps1）
- [ ] 窗口类名/标题被外部工具引用了吗？改名要同步取证工具与单测
- [ ] **样式值有没有经过一个「可被测试调用」的函数**？（见 4.4，本轮加固的核心教训）

### 4.3 每次收到「越用越多」类反馈时 —— 三层定位法
1. **进程层**：Get-CimInstance Win32_Process 按 ProductName 枚举（不要只看进程名）
2. **窗口层**：EnumWindows 按类名/标题枚举，**含不可见**（可见性不是判据）
3. **Shell 缓存层**：扫「属主进程已死」的窗口句柄（ghost windows）
> 不要拿「进程数=0」当「问题已解决」—— ② 的现场就是进程为 0 但卡片仍在。

## 五、可复用命令（本机直接跑）

```powershell
# 1) 机器级实例盘点（只读，退出码 0=干净 / 1=有动作）
powershell -NoProfile -ExecutionPolicy Bypass -File D:\workdesktop\tests\instance_guard.ps1

# 2) 真清理（keepalive 每分钟自动跑这条）

# 3) 托盘窗口样式取证：TOOLWINDOW 必须 True、visible 必须 False

# 4) 首页契约门禁（产物页面 = 当前源码页面）
powershell -NoProfile -ExecutionPolicy Bypass -File D:\workdesktop\tests\check_homepage.ps1 -Exe D:\workdesktop\dist\workbench.exe

# 5) 全家桶预检（子系统 + 实例唯一 + 首页契约 + spawn 静默）
powershell -NoProfile -ExecutionPolicy Bypass -File D:\workdesktop\tests\check_all.ps1
```

## 五之二、防止复发的四道机器闸（不是靠自觉）

> 2026-10-21 第二轮加固后，从三道增至四道。新增的「窗口运行期闸」补上了原来的真空：
> 原来的窗口闸只覆盖单测里的常量契约，**没有任何一条判据看真机上跑着的那个窗口**。

| 闸 | 文件 | 判据 | 谁在跑 |
|---|---|---|---|
| 实例闸 | `tests/instance_guard.ps1` | 家族枚举 + 六条裁决 + 全局上限 6 + 留痕 | `keepalive.ps1` 每分钟自动 `-Apply` |
| 窗口单测闸 | `internal/tray/tray_window_style_test.go` | 7 条守护，含**可测入口取值**与**调用点存在**（第二轮补） | `go test ./internal/tray/` |
| 窗口源码闸 | `tests/check_tray_window.ps1` | Run 必须经 `trayWindowExStyle()`、必须调 `hideTrayWindow`、首参非 0 | `tests/check_all.ps1` 第 5 段 |
| 窗口运行期闸 | `tests/check_tray_window.ps1 -CheckLive` | EnumWindows 按类名取证：必须带 TOOLWINDOW 且不可见；**取不到 = FAIL** | 现场取证时显式跑 |
| 产物闸 | `tests/check_homepage.ps1` | 新页锚点 + 无旧页锚点 + probe 通道 + 真探针 HTTP | `setup/build.ps1` 与 `tests/check_all.ps1` |

全部已接入现有链路（不是新增人工步骤）：keepalive 本来就是每分钟计划任务，build.ps1 本来就是构建必经，
check_all.ps1 本来就是预检入口。**新增判据不增加任何人工动作** —— 这是「防止复发」能不退化的前提。

> **本轮新增的方法论（比任何单条判据都重要）**：守护测试写完必须做变异测试 ——
> 故意把代码改回缺陷形态，看测试是否红。第二轮就是这样抓到「测试注释声称的运行期判据
>> 根本不存在」和「删掉 hideTrayWindow 调用后 11 个测试全绿」两个真实缺口的。
> **不红的测试等于没有测试。**

## 六、仍然存在的边界（如实记账）

- **老卡片清理只能靠 explorer 重启**：Windows 无公开 API 定点删除任务视图历史条目。
- MaxInstances=6 是**机器级总上限**，并行压测超 6 个会被回收，需显式抬 -MaxInstances。
- B 的宽限取 300s：用户双击拉起后 5 分钟内没点「开始」，会被判残留回收。
- 若第三方 Shell 插件强行收录工具窗，仍可能出现卡片 —— 此时标题已自述「内部消息窗口，请忽略」，可按类名精杀。
- 单元测试覆盖的是**常量与窗口类名契约**，不是「Shell 一定不收录」（后者无法在单测中断言，只能现场取证）。

## 四点五、第二轮加固（2026-10-21）：把「守护测试」本身也验一遍

> 触发：老大确认「现在没了」，然后说「防止这种错误再犯」。
> 第一轮的 4 个守护测试看着齐全，复核时发现**注释声称的运行期判据根本不存在**，
> 而且那 4 个测试全部防不住最常见的回退方式。本轮把缺口逐个补上，并用变异测试证明真的能拦。

### 4.4 第一轮守护测试的三个真实缺口（都是实测抓到的，不是推理）

| # | 缺口 | 为什么是缺口 | 本轮怎么补 |
|---|---|---|---|
| 1 | 注释声称「运行期判据（本文件末尾）」 | 文件里只有 4 个常量断言，**根本没有那个测试** —— 注释在说谎 | 补 `TestTrayWindowExStyleFromCallablePath` 等 3 个真运行期测试 |
| 2 | 只断言常量 `wsExToolWindow == 0x80` | 防不住「常量没变、调用点改回 0」—— 那种回退在常量断言面前全绿 | 把实际传值提成 `trayWindowExStyle()` 函数，测试直接调用它 |
| 3 | `hideTrayWindow` 调用可被整行删除而测试全绿 | 实测：删掉 `Run` 里的 `hideTrayWindow(hwndMain)`，11 个测试**全过** | 补源码级调用点判据（Run 函数体内必须含该调用） |

### 4.5 变异测试记录（证明判据有牙，不是摆设）

对 `tray_windows.go` 逐一注入回退，观察测试是否抓住。**全部 4 种都被抓住**：

| 变异体 | 模拟的回退 | 结果 |
|---|---|---|
| `trayWindowExStyle()` 返回 0 | 2026-10-20 原始缺陷复现 | 2 个测试 FAIL ✅ |
| 返回 `wsExToolWindow \| 0x08000000` | 手滑加上 WS_EX_NOACTIVATE（会让右键菜单关不掉） | FAIL ✅ |
| 删除 `Run` 里的 `hideTrayWindow(hwndMain)` | 函数还在、调用被删 | 补判据后 FAIL ✅（补之前是全绿） |
| 调用点改写字面量 `uintptr(0)` | 绕过可测入口 | 2 个测试 FAIL ✅ |

> **方法论（可迁移）**：写完守护测试必须做变异测试 —— 故意把代码改回缺陷形态，
> 看测试是否红。不红的测试等于没有测试。本轮第 3 个缺口正是这样抓到的：
> 变异体一注入，测试全绿，当场证明判据有形无实。

### 4.7 运行期门禁的判据设计（防「假通过」）

| 设计点 | 为什么 |
|---|---|
| 取不到窗口 = FAIL，不是 SKIP | 「取不到数」≠「取到 0」。实例没跑/类名漂移时静默跳过，等于门禁不存在 |
| 只做源码判据进 check_all | 运行期需要有实例在跑，CI/无头环境会假红；源码判据保证处处可跑 |
| 运行期单独入口 `-CheckLive` | 现场取证时显式加，两不耽误 |
| 首参判据剥掉 `uintptr(...)` 包装 | 首版只匹配 `^0,`，`uintptr(0)` 被漏判成 PASS —— 实测抓到的漏报 |

### 4.9 仍然存在的边界（如实记账）

- 运行期判据依赖**当前有实例在跑**；若守护进程也被回收，`-CheckLive` 会 FAIL（这是故意的，见 4.7）
- 单测环境不建真窗口：建窗是有副作用的外部动作，CI 无头会话里断言它只会假绿/假红。
  运行期真值只能靠 `-CheckLive` + 现场 EnumWindows 取证闭环
- explorer 缓存清理仍只能靠重启 explorer（Windows 无公开 API 定点删任务视图历史条目）
