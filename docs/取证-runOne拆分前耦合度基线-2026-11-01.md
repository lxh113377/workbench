# 取证：runOne / runApp 拆分前的耦合度基线（2026-11-01 · round 199）

> 为什么留这份：五轴报告 P1-1 把「超长函数」列为可维护性问题，并明确建议 `runOne`/`runApp`
> 「**单独一轮**做，别和别的改动混一批」（报告第 71 行原话）。本轮（round 199）刚交付两条模板
> 教训，属混批风险，故**不拆**；但拆分的前置条件——「它到底有多耦合」——此前只有一句定性判断
> （「不是纯机械」），没有实测数字。这份卡把它变成可复算的基线，供下一轮单独拆时对照。

## 结论

- **P1 可维护性（不阻断合并）**：`runOne` 362 行、内部 **48 处阶段注释**、**16 个 return**、3 个 `defer`、1 个 goroutine。
- **拆分前置结论：不是纯机械拆**。失败处理段同时依赖 **8 个循环状态变量**（实测词频：`res` 26、「runErr」13、
  「attempt」16、「lastErr」14、「actualModel」10、「lastKind」9、「pol」4、「elapsed」5），且体内含 `break` 控制循环
  ⇒ 抽成独立函数要传 8 个状态并把 `break` 改成返回值。这解释了报告为何要求单独一轮。
- **安全网比预想强（推翻我最初的误判）**：`internal/engine` 有 **238 个 Test**，其中 13 个文件触及 `runOne`/attempt 路径；
  `retry.Decide` 的重试决策链**覆盖良好**（`engine_test.go:20-50` 逐个断言 Delay 与 Action，另有 `retry_test.go`
  等 8 个测试文件）。⇒ 拆分有真回归网可用，不需要先补大量测试。
- **建议下一轮的最小第一刀**：先把「失败处理段」（`engine.go:1290-1344`）作为**唯一**改动抽出来，
  用「传入 8 状态 + 返回是否继续重试」的形态，靠既有 238 个 Test 兜住；**不要**同时动方案阶段/成功阶段。
