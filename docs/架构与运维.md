## 一、整体架构

```
┌─────────────────────────────────────────────────────────────┐
│  workbench.exe（单进程，7.7MB，纯 Go 标准库）                │
│                                                              │
│  ┌────────────┐   ┌──────────┐   ┌───────────────────────┐  │
│  │  Engine    │──►│  Queue   │──►│  Executor (N 并发)    │  │
│  │  (调度闭环) │   │ 调度器    │   │  ↓ 每任务独立 DSH_HOME│  │
│  └─────┬──────┘   └──────────┘   └──────────┬────────────┘  │
│        │                                     │               │
│        ├──► Evaluator（三维评估 + 硬门禁）    │               │
│        ├──► Chain（后继生成）                 ▼               │
│        ├──► Judge（语义判分/自评/摘要）   ┌────────────────┐ │
│        └──► ModelRouter（健康度轮换）     │ DSH Desktop.exe│ │
│                                           │ (headless)     │ │
│  ┌────────────┐   ┌──────────┐            │ + our-free-    │ │
│  │ HTTP+SSE   │   │  Tray    │            │   model        │ │
│  │ 本地面板    │   │ 系统托盘  │            └────────────────┘ │
│  └────────────┘   └──────────┘                               │
│                                                              │
│  ┌────────────┐   ┌──────────┐                               │
│  │ Supervisor │   │  Store   │  ← 原子 JSON + JSONL          │
│  │ 资源自愈    │   │ 持久化    │                               │
│  └────────────┘   └──────────┘                               │
└─────────────────────────────────────────────────────────────┘
```

**进程模型**：工作台自身是单进程（约 15-20MB RSS），每个任务派发一个 DSH Desktop 子进程（用 Windows Job Object 绑定，可靠杀树）。

## 三、关键设计决策（及为什么）

### 1. 为什么用隔离的 DSH_HOME？
用户的 `~/.dsh/our-free-model/settings.json` 里 `tokenSaver.prompts.caveman = "ultra"`，这会让模型强制用"电报体"回答。实测同一任务：
- 共享 HOME：inputTokens **23976**，输出被压成极简风格
- 隔离 HOME（caveman=off）：inputTokens **76**，输出完整高质量正文

同时隔离 HOME 也保证了工作台不会改动用户桌面端的任何配置。

### 2. 为什么每个任务一份 DSH_HOME？
实测在**同一个** DSH_HOME 下并发跑两个 headless 进程会互相阻塞（OFM 的会话映射与凭据刷新是单写者语义），两个任务都会卡死。

解决：每任务 `runtime/dsh-home/tasks/<taskId>/`，其中：
- `profiles` → **junction** 指向共享实体（必须共享，否则 OFM 插件的 junction 失效，报 `no adapter registered for provider our-free-model`）
- `our-free-model/` → 复制账号态文件，但 **settings.json 独立写**（避免并发写同一个 stats.json）

### 3. 为什么禁用全部工具？
our-free-model 的 sealed 车道在**工具调用之后的第二步**会卡死（事件流停在 `step_start(step=2)` 无后续，实测 100% 复现）。

因此工作台的执行策略是：**模型一步直接输出完整成果文本**，由工作台负责落盘。实测 55.6 秒产出一篇结构完整的 400 字文章。

> 这条约束写在 profile 层（`- id: tools config: {only: []}` + 逐个 disabled），新增工具时需要显式打开。

### 3.5 为什么把「出方案」拆成独立的一次模型调用？

老大立规（2026-10-21）：**思考模型只出方案，agent 模型负责执行**。

改造前每个任务只调一次模型，任务 prompt 原样喂过去。两个后果：
- 有推理优势的模型被当写稿机，没有机会先把方案想清楚；
- 擅长执行落地的模型拿不到任何结构化指令，只能自己从一句话里猜交付物。

关键点是**不能只靠一条 prompt 说"先规划再执行"**。实测小模型会把规划写成开头一段废话
然后直接开写 —— 规划没有约束力。只有把方案固定成一次独立调用的输出，它才能被：
1. 机器校验（交付物路径安全、验收命令解释器白名单）；
2. 落盘审计（`tasks/<id>/plans/blueprint-<n>.json`，"真的出过方案"的物证）；
3. **回灌重规划**（验收失败时把失败证据交给方案模型改前提）。

闭环因此分三级，顺序写死在 `completeTask`：

```
验收失败 + 返工有余量            -> repair（方案不变，改实现；便宜，先用）
验收失败 + 返工用尽、重规划有余量  -> replan（回到方案层改前提；贵，后用）
两者用尽                          -> degraded（有产出但不计今日产出）
```

顺序反了会让每个实现小错都触发一次完整重规划，吞吐直接塌。

方案层自身失败（429 等通道故障）**不判任务死刑**：退化直执行 + `PlanDegraded=true` 落盘。
面板能看出"这一轮方案层挂了"——否则退化会安静地变成常态，而面板一切正常，
那正是"无法闭环"最典型的样子。

### 4. 为什么选 `web-desktop` 这个 profile 名？
our-free-model 的 `vault.js detectSealedHost()` 只在白名单内解锁 "sealed 协付车道"（真正的无限额度）：
```js
if (profileName === 'desktop' || profileName === 'tauri') return FLAVOR_HARNESS
if (profileName === 'web' || profileName === 'web-desktop') return FLAVOR_WEB
return null  // sealed 车道隐藏，只剩匿名免费额度
```
命名为 `web-desktop` 既命中白名单，又不与 Electron 独占的 `desktop` 冲突。

### 5. 为什么绝不挂 dsh-web-app？
`@deepseek-ai/dsh-web-app` 会启动常驻 HTTP 服务器，headless runner 永远拿不到退出信号 → 进程永不退出（实测卡死 150s+）。工作台 profile 的 bundles 只有三个：
```
@deepseek-ai/dsh-base
@deepseek-ai/dsh-headless
dsh-our-free-model
```

### 6. 为什么用文件锁做单实例？
Windows 命名互斥体在 `Global\` 前缀下需要额外权限，而普通互斥体只在当前 session 命名空间有效。WMI 启动的进程（session 0）与交互会话的进程互相看不见对方的互斥体 —— 实测第二个实例照样能起来并抢占另一个端口。

改用 `LockFile` 对 `runtime/workbench.lock` 加独占锁：文件锁是全局的，跨 session 有效。实测第二实例启动后进程数仍为 1。

## 四、数据格式

### config.json
```jsonc
{
  "schemaVersion": 1,
  "autoResume": true,            // 启动时是否恢复上次运行状态
  "autoStart": false,
  "eval": {
    "weights": { "value": 0.5, "cost": 0.2, "feasibility": 0.3 },
    "threshold": 60,             // 自动批准阈值
    "semanticOn": true,          // 是否启用 LLM 语义判分
    "repeatGate": true,          // 重复任务硬门禁
    "similarityCap": 0.9,        // 相似度达到多少判定为重复
    "dailyCap": 200,             // 每日任务上限
    "diversityCap": 0.4
  },
  "models": [
    { "model": "z-ai/glm-5.3", "provider": "our-free-model", "tier": "balanced",
      "enabled": true, "weight": 100, "maxFail": 3, "cooldownM": 30 }
  ],
  "executor": {
    "concurrency": 2,            // 并发任务数 1-6
    "defaultTimeout": 30,        // 默认超时（分钟）
    "maxRetries": 3,
    "retryBackoffMs": [5000, 20000, 60000],
    "maxOutputMB": 32,           // 单任务事件流上限
    "stallSeconds": 180,         // 无进展判定阈值
    "profileName": "web-desktop"
  },
  "chain": { "enabled": true, "maxDepth": 5, "fanout": 2, "minQuality": 6, "contextChars": 2000 },
  "server": { "host": "127.0.0.1", "port": 17890 },
  "supervisor": { "enabled": true, "memLimitMB": 700, "handleLimit": 3000,
                  "goroutineLimit": 1500, "sampleSeconds": 30, "strikesToRestart": 3 }
}
```

### queue.json（任务快照）
完整保留所有任务（含终态）。这是权威数据源，崩溃恢复靠它。

### audit.jsonl（审计流水，只追加）
```jsonl
{"at":1792325488157,"taskId":"task-xxx","from":"queued","to":"running","actor":"engine","kind":"transition","message":"开始执行"}
```
`actor` 取值：`engine`（自动）/ `user`（面板操作）/ `system`（崩溃恢复）

### tasks/&lt;id&gt;/events.jsonl
DSH `--json` 的原始事件流 + 工作台自己塞的 `start` 事件。用于完整追溯每次执行。

## 五、状态机

```
candidate ──► evaluating ──► approved ──► queued ──► running ──► done
     │            │             │           │           │
     │            │             │           │           ├──► failed
     │            │             │           │           ├──► timeout
     │            │             │           │           ├──► cancelled
     │            │             │           │           └──► interrupted ──► queued（重启恢复）
     │            │             │           └──► cancelled
     │            │             └──► rejected
     │            └──► rejected
     └──► cancelled
```

**迁移校验**：`model.TransitionAllowed(from, to)` 是唯一权威，任何非法迁移在 store 层被拒绝并返回错误。这样能防住"已完成任务被误改回运行中"这类数据损坏。

## 六、运维手册

### 日常检查
```powershell
workbench.exe --status          # 快速看状态
workbench.exe --diagnose        # 完整自检（通道、profile、配置）
```

### 备份
直接复制整个 `workbench-output\` 目录即可（配置 + 队列 + 全部产出 + 日志）。

### 迁移到另一台机器
1. 复制 `dist\` 整个目录
2. 目标机需装 DSH Desktop + our-free-model
3. 双击运行，工作台会自动重建 `runtime\dsh-home`

### 升级
1. 停止旧版（托盘 → 退出）
2. 用新 `workbench.exe` 覆盖
3. 启动，`config.json` 的 `schemaVersion` 会自动迁移

### 排障数据在哪儿
| 想知道什么 | 看哪个文件 |
|---|---|
| 任务为什么被拒 | `tasks/<id>/` 里的队列记录 + `audit.jsonl` |
| 任务执行时模型说了什么 | `tasks/<id>/events.jsonl`（完整事件流） |
| 谁把状态改了 | `logs/audit.jsonl` |
| 内存/句柄是否泄漏 | `logs/metrics.csv` |
| 是否发生 panic | `logs/crash.log`（正常应为空） |
| 是否自愈重启过 | `logs/supervisor.log` |

### 实例与窗口生命周期（2026-10-20 现场两连后新增）

**为什么单独立一节**：本机曾出现「后台 ~24 个同名的个人AI工作台」与「任务视图十几张关不掉的空白卡片」，
这两个现象都不在原有排障表覆盖范围内 —— 它们是**创建端有 N 条路径、末端零回收**的产物。

#### 实例
| 想知道什么 | 怎么做 |
|---|---|
| 现在到底有几个实例 | `tests\instance_guard.ps1`（只读盘点，退出码 0=干净 / 1=有动作） |
| 它们分别是谁拉起的 | 看命令行：无子命令=生产实例；带 `--ui-probe/--soak/--acceptance` 等=探针 |
| 谁在回收 | `tests\keepalive.ps1` 每分钟一跳内嵌 `-Apply -Quiet`；计划任务 `WorkBenchKeepAlive` |
| 清理历史 | `runtime\instance-guard.log`（每次真清理一行 REAPED） |

规则：生产实例最多 1 个；探针超自身 `--seconds` 预算 / 无预算超 10min TTL / 全局总数超 6 → 回收（绝不碰生产实例）。
用户主动退出（`runtime\user-quit.flag` 在册）超过 300s 的实例视为残留回收。

#### 窗口（任务视图 / Alt-Tab）
| 现象 | 判据 | 处置 |
|---|---|---|
| 任务视图里出现空白「个人 AI 工作台」卡片 | `EnumWindows` 找类名 `PersonalWorkbenchTrayClass`，看 `GWL_EXSTYLE` 是否含 `WS_EX_TOOLWINDOW(0x80)` | 缺则升级到 v1.2.1+ 产物（已修）；已有卡片重启 explorer |
| 卡片关不掉 | 托盘消息窗是**纯消息窗**，没有关闭语义；任务视图条目是 explorer 缓存 | 重启 explorer（自动重启，桌面/任务栏几十秒恢复，不丢文件） |
| 托盘图标没了 | `logs/workbench.jsonl` 搜「托盘图标注册失败」 | 见 §托盘自愈（Low 完整性级别） |

> 注意：**不要拿「进程数为 0」当作「卡片已消失」**。任务视图缓存独立于进程，进程死光卡片仍可能在。

#### 性能调优对照表

| 症状 | 调整 |
|---|---|
| 内存占用高 | 降低 `concurrency`（每个任务一个 DSH 进程，约 200-400MB） |
| 任务老是超时 | 提高 `defaultTimeout`；或检查模型健康度 |
| 产出太慢 | 提高 `concurrency`；或把模板 `params.modelTier` 改成 `fast` |
| 任务被判卡死 | 提高 `stallSeconds`（默认 180s；某些复杂任务首 token 可能更慢） |
| 磁盘增长快 | `tasks/*/events.jsonl` 是主要占用；可定期归档已完成任务目录 |

## 七、资源自愈机制

```
每 30 秒采样：HeapInuse / 进程句柄数 / goroutine 数
         ↓
任一超阈值（700MB / 3000 / 1500）连续 3 次
         ↓
记录 supervisor.log → 优雅停止引擎 → 拉起新进程 --silent → 旧进程退出
         ↓
新进程启动 → 读 state.json → 自动恢复运行 → 读 queue.json → 中断任务重新入队
```

**panic 兜底位置**（三处）：
1. 调度循环 `loop()` —— 挂了会导致整个引擎停摆
2. 任务执行 goroutine —— 挂了会泄漏并发槽
3. 各 HTTP handler —— stdlib net/http 自带 recover，但日志不友好，仍单独处理

## 九、如何改它

### 加一个新模板（最简单）
面板 → 模板 → 新建。不需要改代码。

### 加一个新领域
1. `internal/templates/defaults.go`：加模板，设 `Domain: "新领域"`
2. `internal/chain/chain.go`：在 `topicsByDomain` 加该领域的选题池
3. 前端 `app.js` 的领域下拉框加一项

### 换执行通道
只需要改 `internal/executor/executor.go` 的 `Run()` 方法 —— 它是工作台与外部世界**唯一**的耦合点。

### 加一个面板 API
1. `internal/web/server.go` 的 `routes()` 注册
2. 用 `s.guard(...)` 包一层（自动校验 token）
3. 前端 `app.js` 里调 `api('/api/xxx')`

## 九点五、可观测性（v1.2.0 新增）

### 9.5.1 结构化日志

全部引擎/治理/自愈日志统一写 `<DataRoot>/logs/workbench.jsonl`，**一行一条 JSON**（标准库 `log/slog`，无第三方依赖）：

```json
{"time":"2026-10-19T07:21:55+08:00","level":"INFO","msg":"引擎已启动","component":"engine","concurrency":2,"phase":"running"}
{"time":"2026-10-19T07:21:58+08:00","level":"INFO","msg":"尝试开始","component":"engine","taskId":"task-4663a03e1b93c665","model":"z-ai/glm-5.3","attempt":0}
```

| 约定 | 说明 |
|---|---|
| `component` | 来源子系统（engine / supervisor / panic） |
| `taskId` / `model` / `kind` | 任务维度字段，可按 taskId 串联整条生命周期 |
| 凭据打码 | `logging.Redact` 命中 token/secret/password/apikey/credential 且值长 > 4 时替换为 `***redacted***` |
| 级别 | `-log.level` 由 `logging.Options.Level` 控制；桌面程序默认 Info，前台调试可下调 |

**已下线**的旧裸日志：`engine-debug.log`（engine.debugf）、`supervisor.log`（自愈）、`crash.log`（panic）。三者内容现在都能在 `workbench.jsonl` 里按 `component` 与 `level` 检索。

### 9.5.2 执行钩子（executor.Hooks）

对标 river 的 `HookWorkBegin`/`HookWorkEnd`，执行器在每次尝试前后回调：

```go
type BeforeRunFunc func(ctx context.Context, task *model.Task, modelID string) error
type AfterRunFunc  func(ctx context.Context, task *model.Task, modelID string, res *Result, err error)
```

- 任一 `BeforeRun` 返回错误 ⇒ 本次尝试不启动，按 `boot_failed` 回传；
- `AfterRun` 在 `Run` 返回后**必然**执行（含失败路径），单个钩子 panic 被 recover、不影响其余钩子；
- 引擎通过 `executor.RunnerContract` 接口依赖执行器（不再绑死具体结构体），
  `Engine.SetRunner` 可注入测试桩——这是"引擎单测不必真拉 DSH 子进程"的前提。

### 9.5.3 指标与失败分布

| 接口 | 返回 | 用途 |
|---|---|---|
| `GET /api/metrics` | 堆内存/Alloc/goroutine/句柄/GC + 任务聚合 + 最近 30 条尝试台账 + 阈值上限 | 面板「运行时指标」卡片；前台轮询 |
| `GET /api/failures` | 按 `ErrorKind` 聚合的失败分布（count / lastAt / samples）+ `empty` 标志 | 面板「失败原因分布」卡片 |
| `logs/metrics.csv` | 每 5 分钟的采样（沿用 v1.0，供长时间趋势） | 压测取证 |

> 零数据语义：失败分布为空时返回 `{"empty": true, "total": 0, "buckets": []}`，
> 面板显式显示「暂无失败样本」，**不伪造 0 条失败柱状图**。
