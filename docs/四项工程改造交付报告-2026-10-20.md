## 3. 改造②（L5）：执行层抽象真正收敛

- **问题**：`engine.SetLogger` 原先断言 `e.runner.(*executor.Runner)` —— 接口签名里带具体类型等于没脱离结构体；`main.go` 用 `FailoverRunner` 包住真实执行器后该断言不匹配，尝试日志对模型池路径静默失效（功能正常、只是没日志，运行期发现不了）。
- **做法**：`executor.Runner.AttachHooks(*Hooks)` + `modelpool.FailoverRunner.AttachHooks`（透传内层）；引擎改用能力接口沿 `Inner()` 链下探（`attachHooksToRunner`），找不到不报错（钩子是观测面，不得影响执行）。
- **完成标准 → 实测**：`engine.go` 无 `.(*executor.Runner)` 断言（仅注释引用历史形态）；4 条守护测试绿（装饰器链下探 / 普通执行器 / nil 链不 panic / BeforeRun 中止归 `boot_failed`）；变异测试把函数体回退成具体类型断言 → 2 条判据立刻点名，恢复后绿。

## 5. 改造④：P1-3 指标导出 + L8 性能护栏

### 5.1 `GET /metrics`（Prometheus exposition v0.0.4，纯标准库）

| 指标 | 类型 | 落点 |
|---|---|---|
| `workbench_tasks_total{state=...}` | gauge | 零任务时每个合法状态仍出 0 值序列（采集端可预先建面板） |
| `workbench_attempts_total` | counter | 尝试台账（P0-1 成果）对外投影 |
| `workbench_task_failures_total{kind=...}` | counter | **D2 的最终落点**：错误分类进指标，12 个 `executor.Kind` 基线全列出 |
| `workbench_task_duration_seconds_sum/_count` | summary | 规范形态（不是两条同名样本） |
| `workbench_goroutines` / `_heap_alloc_bytes` / `_gc_pause_total_seconds` | gauge/counter | `runtime` + `runtime/metrics` 双口径交叉 |

三条硬约束写在**结构里**而非靠自觉：样本只能挂已登记族（HELP/TYPE 成对、重复登记复用同族）；浮点经 `promSanitizeFloat` 兜底不产 NaN/±Inf；标签名白名单 + 标签值按规范转义、非法 UTF-8 先修正、超长按 UTF-8 边界截断。

判据强度（8 条测试）：**逐行校验** exposition 合法性 + **同 (name,labels) 重复序列检测**。后者是本轮自己踩出来的：子代理 v1 用两条同名样本输出求和与计数（`TYPE summary` 却重复序列 ⇒ Prometheus 判 duplicate sample、整次抓取作废），我第一版判据放过了它；加强后先验红（实现仍在缺陷态）再修实现，并用变异证明「改回同名样本」必被抓住。

## 7. 本轮被实测纠正的自身错误（7 项，防重犯）

1. **推测当结论**：看到 20+ 个 DSH 进程就先判「测试拉起子进程」，但受控单跑 DELTA=0；真判据是 `t.TempDir` 残留目录（要整套并行跑才复现）。
2. **修 A 引入 B**：把 `eventsFile` 关闭完全交给 `consume` 后，早退路径永久泄漏句柄（executor 包 2 用例红）。正解是 `sync.Once` 双向保证。
3. **判据测错对象**：`limiter_integration_test` 断言「单次 Run < 2s」，把 `linkDir` spawn `cmd.exe` + 宿主排队算成限流等待（全量并行实测 4.12s 假红）⇒ 改测两次连续 Run 的**相对差**。
4. **旧断言为缺陷背书**：`limiter_snapshot_test` 原断言「未装闸门=零值」，把 D9 当正确行为 ⇒ 必须改判据方向而不是改回实现。
5. **测试桩缺能力面洗绿**：桩不支持 `SetLimiter` 就 `t.Skip`，把「从未接线」变成「本用例不适用」⇒ `noopTestRunner` 与真实 Runner 能力面对齐。
6. **写源码的转义层坑**：子代理产出把换行/制表/NUL 的转义序列写成真控制字符，致 `invalid character U+FF0C in identifier`；我第一轮修复又漏判 `summary` 的 `_sum/_count` 规范形态 ⇒ 新增判据必须先做一次「它能抓住我刚犯的那个错」的变异验证。
7. **凭猜写 API**：给 L6 写测试时先按记忆写了不存在的 `logging.New(...)`（另一次是 `filepathSep` 臆写），与真实 `Open(Options{Handler})` 不符。规则「严禁猜标识符」不是装饰 —— 每次都要先 grep 签名再落笔。

协作纪律一次完整执行：本提交按仓内规矩「HEAD + 仅我的改动」组装 —— 7 个与并行会话混改的文件逐件从 HEAD 重放并断言他人符号零泄漏，提交后立刻把 worktree 还原为双方合并版并做三方合并（`CHANGELOG.md` 相对 HEAD 只增 229 行、删 0 行）。自洽性验证还抓出我漏纳 `limiter_snapshot_test.go`（缺它必 CI 红），补入后在独立 worktree（`HEAD` + 仅本提交改动）跑 vet + 30 包全绿才提交。
