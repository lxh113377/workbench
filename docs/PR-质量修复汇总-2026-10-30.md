### 2.1 交付物类型门禁（`37db39c`）
```
问题：报告里 8 条 pass 中 0 条是报告级交付，3 条 done 任务只交了一个 explore.py。
     模型在 manifest 里自报验收命令（python explore.py），跑通即 pass ⇒ 计数在涨、目标要的五轴分级报告一条没产出。
证据：T66/T67 只在有 docs/*.md 时生效、T74 只管"自称报告的文件没落 docs/"、T73 只挡代码体量
     ⇒ "一个 .md 都没交"这种结构性失败，三道门全部沉默。
修法：门只在「引擎自己注入过交付要求」时生效 —— 触发器 = model.DeliverableGateMarker（"## 交付物门禁"，
     注入侧两处共同前缀），**不用任务标题词族**：实测词族命中 1,120 条任务而真缺陷只 5 条 ⇒ 收益≈0、误杀面大两个数量级。
     只判结构（有没有任何 .md），内容合格性与落点仍归 T66/T67 与 T74，不越权。
判据：TestDeliverableKindGate（3 该拦 + 6 不许误杀，含容器 E2E 形态与大小写）+ TestDeliverableGateSingleSource。
负控：① 永远当作已交 .md ⇒ 正向红；② 忽略触发器 ⇒ 误杀半边红；③ 注入侧退回字面量 ⇒ 单源守卫红。
误杀面实测：走到交付 20 条 ⇒ 带 marker 8 条 ⇒ 带 marker 且无 .md 6 条 ⇒ 当前 pass=true 只 3 条会被拦，正是"该拦没拦"的那 3 条。
```

### 2.2 返工环两处（`395c28f` + `d3f5cf8`）
```
问题 A（按轮数翻倍）：实测同一任务 prompt.repair-1.md = 690,935 B → prompt.repair-2.md = 1,379,069 B（比值 2.00）。
     根因：repairPrompt 把「### 原始任务」写成 task.Prompt，而 scheduleRepair 又把新 prompt 写回 task.Prompt
     ⇒ 每轮的"原始任务"装着上一轮整份返工 prompt（含上一版产出）。
     修法：新增 model.Task.OriginalPrompt，首轮登记一次原文；repairPrompt 取登记值，空值回退 task.Prompt（旧任务行为逐字不变）。
问题 B（单文件穿透预算）：旧 readPrevArtifacts 是"先 append→累加→再判 break" ⇒ 单文件整份穿过 limit，
     天花板 = 200KB + 上游单文件闸(8MiB) ≈ 8.19 MiB/轮；线上该段占 prompt 99.7%、最大单文件 277,803 B。
     修法：limit 当预算执行 —— 每个 body 压到剩余预算内（截断 + 显式标记），预算耗尽即停 ⇒ total ≤ limit 成为不变量。
判据：TestRepairPromptDoesNotNestPreviousRound + TestOriginalPromptFallsBackForLegacyTasks
     + TestReadPrevArtifactsRespectsBudget + TestReadPrevArtifactsKeepsFailureEvidence（截断不许剪掉"退出码/命令"证据）
     + TestTruncateWithMarkerNeverExceedsBudget。
负控：退回嵌 task.Prompt / 去掉 round==1 / 退回无预算约束 / 截断不留标记 —— 四向均判红，还原字节一致。
⚠️ 判据当场抓到我自己的 bug：把"按字节限流"写成借 truncateRunes（第二参是 rune 数）⇒ budget=10 返回 24 B。
```

### 2.3 池与重试交互（`cb6a54e`）
```
问题：任务因「模型池重投次数到顶，判死以解锁自主供料」失败时，事件明写「可在面板重试」；
     但 RetryTask 只清 Attempts/Error ⇒ PoolWaits 仍=48、PoolWaitCeil 仍=48，下一次池不可用里
     `waits >= budget` 立刻成立 ⇒ 重试瞬间又死。属"承诺与实现不一致"。
修法：RetryTask 一并复位 PoolWaits/PoolWaitCeil。语义划界：那两个是**自动重投**的预算；
     RetryTask 是**人**的决定 ⇒ 重试从零重新计时，自动封顶逻辑下一轮照常生效。
判据：TestRetryTaskResetsPoolWaitBudget（状态+计数复位 + 行为层"封顶条件不许立刻成立"）。
负控：只留 Attempts 清零 ⇒ 判红。
```

### 2.4 队列可用性（`1372048`）
```
问题：Queue.Len() 计全部条目，而 Pop 对非 queued 只 continue 不删除；Remove 全仓只有 CancelTask 一处调用
     ⇒ 已入队后又被改成终态的任务永久留在队列里：取不走、却让 q.Len() 恒 > 0
     ⇒ `q.Len()==0` 的供料门被**永久关死**，只能等重启。
修法：Pop 遇到终态条目先 delete 再 continue（终态永不可再派发）；非终态的中间态一律不动
     （approved→queued 路上的任务若被删会永远不被派发）。剔除发生在 Pop 内 ⇒ 最迟下一 tick 供料门恢复。
判据：TestPopPrunesTerminalResidue + TestPopKeepsNonTerminalNonQueued（保守面单独成判据，防"顺手全删"）。
负控：移除终态分支 ⇒ 判红。
```

### 2.7 工程化规则（本轮 CI 实证，建议写进团队约定）
```
**测试替身同样受并发契约约束**：被替身的组件是线程安全的，不能推出替身是线程安全的。
本轮实证：生产日志器并发安全，但内存版 Handler（captureLogs）append 无锁 ⇒ 一旦被测代码异步起 goroutine，
测试读、goroutine 写就构成 DATA RACE，被 `go test -race` 拦下。
配套两条：① 替身按接口契约加锁；② 断言前用生产自带 seam 等后台排空（如 WaitInflight），
不要自己起 goroutine 等（本仓注释记录过该坑：helper 返回前起等 ⇒ 那一刻计数为 0 ⇒ 排空形同虚设）。
```


### 2.8 验收路径的"输出洪泛"误分类（T97）
```
线上现场：验收命令 `pwsh -NoProfile -File probe.ps1` → exit=-1、skipped=「启动失败: short write」，
  stdout 是海量文件列表（远超 MaxOutputBytes=64KB）。
机制：os/exec 经 io.Copy 搬运子进程输出，而 io.Copy 有 `if nr != nw { err = io.ErrShortWrite }`；
  limitedWriter 旧实现在超限时"截断后返回短计数、err=nil" ⇒ ErrShortWrite ⇒ cmd.Run() 的非 ExitError
  ⇒ verify 记成「启动失败」。后果：① 诊断误导；② **验收假阴性**（本该 exit 0 的命令因刷超 64KB 被判失败）。
修法：Write 永远报告全额 len(p)，超限部分丢弃（截断上限本意不变）。
判据：契约层（Write 必须报全额 + io.Copy 不许报错）+ 端到端（真起进程刷 4 万行，断言不被记成启动失败、exit==0、pass）。
负控：退回旧 writer ⇒ 两条判据同时红，且逐字复现线上那句 skipped="启动失败: short write" exit=-1。
```


### 2.9 台账的"出口不服务"被写成「启动失败」（T98）
```
量化：agent 根 attempts.jsonl 2109 行中，kind=boot_failed 共 191 行，其中 190 行（99.5%）的 error 正文是
  `dsh: SERVER: our free model does not serve "combo:auto-free" on this egress` ⇒ 同一句原文还被分进 not_served 桶（53 行）。
机制：上游把类别预置成通用 boot（engine.go:1283 的兜底），而 failover 的补偿 bootAttributionKind(T17②) 会按 not_served 记**车道账**
  （not_served = oneStrike + 1800s 冷却；boot = 只有 probeCannotCure、不冷却）⇒ 行为早对；错的是写回：
  res.ErrorKind 非空时旧逻辑不回填 ⇒ 台账/面板/报告读者看到的全是「启动失败」。
修法：补偿命中时把补偿后的类别也写回 res.ErrorKind（写回条件改为"空值 或 类别被改准"）；重试行为不变（NotServed 与 Boot 同列可重试）。
判据：TestLedgerRecordsAttributedKind（必须记 not_served）+ TestLedgerKeepsBootForGenericFailure（泛化启动失败必须保持 boot，防误杀车道）。
负控：把补偿赋值改回 kind ⇒ 判据红并逐字复现台账症状。
```


### 2.10 额度耗尽被降级成瞬时限流（T100）
```
量化（对 attempts.jsonl 用分类器文本规则**逐行复算**再与台账对比）：可判定 1201 行中 306 行不一致，聚类三处 ——
  191 boot_failed→应为 not_served（T98，已修）、**114 rate_limited→应为 quota_exhausted（本轮）**、1 unknown→应为 no_artifact。
机制：额度原文带 `RATE_LIMIT:` 前缀 ⇒ 上游结构化字段先定性成 rate_limited；而 classify 的**结构化短路**位于
  额度原文判定之前 ⇒ 账号级事实被降级。次序原则（"额度耗尽必须先于通用限流判定"）在注释里早写明，是短路把它破了。
修法：把额度原文判定提到短路之前，并同时探 res.LastError（文本可能只落一侧）。
影响：**行为级**而非显示级 —— engine.go:1220/:1253 对 quota_exhausted 有专门长等待路径，判成 rate_limited 会走短冷却，
  免费车道被反复秒试（T76 当初修的正是这个：现场 409 次、单分钟最多 13 次空转）。
判据四条：正面两条（结构化已是 rate_limited + 正文额度原文 ⇒ 必须升级；正文只在 LastError ⇒ 同样升级）
  + 保守面两条（真瞬时限流必须保持 rate_limited；429 通用外壳 `Provider returned error` 必须保持 rate_limited）。
```

### 2.13 交付通道的一处可用性发现（本轮实测，与代码无关但与交付可靠性有关）
```
现象：`git push` 连续 5 次失败，错误 `TLS connect error: error:0A000126:SSL routines::unexpected eof while reading`；
      `git fetch` 此前也出现过同类（本会话更早一次推送也是"先失败、重试即通"）。
定性：不是凭据问题（同一 remote 用 HTTP/1.1 立刻成功），而是 HTTP/2 协商/代理层把连接切断。
对策（已实测有效）：`git -c http.version=HTTP/1.1 push origin master`；此后本会话推送一律带该参数。
⇒ 这条与报告 E11 的 TLS 抖동（自签证书/`unexpected eof`）同族，但**发生在交付通道而非模型出口**；
  记录在此以免后来者把"推不上去"误判成仓库或凭据故障。
```


### 2.14 无产物块在文本路径上无法归因（T102）
```
现场：agent 根 attempts.jsonl 里同一句原文「执行失败: no_artifact」共 4 行 —— 3 行走 judge 的**结构**判定正确记为 no_artifact，
      **1 行记为 unknown**（2026-10-26 19:00:53，action=retry）。
机制：`classify` 此前没有任何 no_artifact 分支 ⇒ 该文本落进 `dsh:`/ExitCode 兜底或 Unknown。
双重代价：① 台账/面板把它显示成「未知错误」（no_artifact 本有处置：oneStrike + 600s 冷却）；
```
