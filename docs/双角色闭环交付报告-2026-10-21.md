# 双角色闭环交付报告：思考模型只出方案，agent 模型负责执行

日期：2026-10-21 | 端：DSH Desktop（ds 端）| 范围：workbench 引擎

## 零、老大立规原话

> 「思考模型只出方案，agent 模型负责执行，不然只出方案没有执行落地的模型无法闭环」

这句话有两层意思，本项目以前**两层都没做到**：

| 层 | 缺口（改造前实测） | 后果 |
|---|---|---|
| 分工 | `runOne` 每个任务只调一次模型，`task.Prompt` 原样喂过去 | 有推理优势的模型被当写稿机；擅长执行的 agent 模型拿不到任何结构化指令 |
| 闭环 | 验收失败只走 `repairPrompt`（把报错塞回同一模型重做） | 方案层面错了就永远错 —— 重做一百遍也修不掉前提 |

## 一、改了什么（一句话）

把"一次模型调用"拆成**方案 → 执行 → 验收回灌**三段，并让失败在"改实现"与"改方案"两级之间正确归位。

```
任务
  │
  ├─► ① 方案阶段（思考模型，只出方案，不产出文件）
  │     输入：任务 + 项目目标 + 上一轮失败证据
  │     输出：结构化 Blueprint（思路/交付物/步骤/验收命令/风险）
  │     ↓ 渲染成执行指令（不是原样转发方案）
  ├─► ② 执行阶段（agent 模型，负责落地）
  │     按方案把文件真正做出来，并让 verify 命令真实通过
  │     ↓ 工作台真跑验收
  └─► ③ 闭环归位
        验收通过 ────────────────► done（计入今日产出）
        失败 + 返工有余量 ────────► repair（方案不变，改实现）
        失败 + 返工用尽、重规划有余量 ► replan（回到①重新出方案）
        两者都用尽 ──────────────► degraded（有产出但不计产出）
```

## 二、决策记录（为什么这么定）

### 2.1 为什么方案必须是独立调用，而不是一条 prompt 说"先想再做"

实测（2026-10-21，见 `docs/缺陷-运行中但产出为0`）：单次调用里让模型自己先规划，
小模型会把规划写成正文开头一段废话然后直接开写 —— **规划没有约束力**。
只有把方案固定成一次独立调用的输出，它才是可校验、可回灌、可审计的中间件。

### 2.2 为什么返工优先于重规划（RepairRounds=3 > ReplanRounds=2）

改方案 = 推翻重来。若每个实现小错都触发重规划，吞吐会塌。
判据顺序写死在 `completeTask`：先 `shouldRepair`，再 `shouldReplan`。
边界由 `replan_boundary_test.go` 两条用例钉住（返工优先 / 中间档进 replan）。

### 2.3 为什么方案层失败要退化直执行，而不是判任务死刑

方案调用会撞 429（免费车道按 session 统计速率）。通道故障不是任务的错。
退化时：任务继续执行 + `PlanDegraded=true` 落盘 + 审计记 `action=degraded`。
面板上能直接看出"这一轮方案层挂了"，而不是安静地变成常态。

### 2.4 为什么方案与执行是两次选型，而不是共用一个模型

- 方案是"想清楚"，值得用最好的模型（默认 `PlannerTier=quality`）；
- 执行是"动手"，用性价比高的（模板 tier，默认 balanced）；
- `plannerModels` 可显式钉死方案模型；为空时按 tier 从路由表选。

`plan_stage_test.go::TestPlanModelDiffersFromExecutorRole` 直接断言两次调用的模型 id 不同。

它存在的意义与 `--autonomy selftest` 同级：若只能靠跑真模型验证"闭环还通不通"，
那就没人会天天验，最后只能凭"看起来在跑"下判断。

### 5.2 契约测试的边界更新（不是放宽断言）

`TestCompleteTaskDegradedOnVerifyFail` / `TestRepairExhaustedFallsToDegraded`
原先只设满 `RepairRounds` 就期望 degraded。新增 replan 后"用尽"是两维的，
故补 `PlanRounds` 到满额；断言（degraded / Verified=false / FailReason 含退出码 / 不计今日产出）**一条未改**。

### 5.3 本会话踩到并修掉的两个真缺陷（自我暴露，留档）

| 缺陷 | 形态 | 根因 | 修法 |
|---|---|---|---|
| 自锁死锁 | 测试挂 120s，栈停在 `sync.RWMutex.RLock` | 在 `store.Update` 的 mutator 里调 `store.Get`（RWMutex 不可重入） | mutator 内不读 store |
| 迁移漏字段 | `ReplanRounds` 迁移后仍为 0，`shouldReplan` 恒 false | `NormalizePlan` 只补了 tier/timeout，没补轮数 | 零值一律补默认 2 |

这两条都是"先写测试才发现的"，也说明一件事：**闭环逻辑不写判据就一定会静默断在某一段**。
