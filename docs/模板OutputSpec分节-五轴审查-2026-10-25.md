# 模板 OutputSpec.Sections —— 五轴审查报告（2026-10-25 round 115）

> 范围：`workbench/internal/templates/defaults.go` 的 29 条内置模板 + `model.OutputSpec`。
> 按 `review-five-axis` 模板格式产出（可直接贴 PR）。所有发现都有实测证据与复核记录。

## 0. 触发与结论先行

审计动机：round 113-116 修完 `{prev}` 空洞后，用同一思路复查「模板声明的产出契约
是否被 prompt 真正要求」。审计结果**不构成本轮改动**，理由见「合并结论」——
这是一份登记性报告，不是一份修改说明。

## 1. 架构（本次的主发现）

- **P2｜`Sections` 是「有定义、有写入方、零读取方」的装饰性元数据。**
  实测（`git grep -n Sections` 全仓 + web 前端）：
  | 位置 | 角色 |
  |---|---|
  | `model/types.go:155` `Sections []string \`json:"sections"\`` | 唯一定义 |
  | `templates/defaults.go:22` `mkSpec(...)` | 写入（29 条模板，每条 2-4 项）|
  | `web/assets_script.go:735` `sections: []` | 写入（面板新建模板时硬编码空数组）|
  | 其余仅 2 处**同名但无关**：`gov` 包的 `TestFormatSummaryContainsAllSections` / `TestGovRecomputeReturnsAllSections`（治理汇总的分节，与本字段无关）|
  ⇒ **没有任何代码读取它**。对比同结构的兄弟字段：`MinWords` 非测试 19 处、`OutputFormat` 10 处，均有真实消费方；`Sections` 为 0。
  验收准则枚举（`autonomy/types.go`）也只有 `minWords` / `minQuality` / `tasksDone` 等，**无 section 类准则**。

## 2. 可读性

- **P2｜97 个声明 section 里有 15 个（涉及 13 条模板）字面未出现在自己的 prompt 中，其中真不一致仅 4 处**
  实测规模（**运行时权威值**：Go 端遍历 `templates.Defaults()` 用 `strings.Contains` 判定）：
  对这 15 个逐条人工核对：
  | 类别 | 数量 | 说明 |
  |---|---|---|
  | 字面命中（无问题）| 82 / 97 | prompt 里直接写了该章节名 |
  | 字面缺、语义已覆盖 | 11 / 15 | 如 `quality-verify/实测输出` ← prompt ②「记录注入前后的完整输出」|
  | **字面缺、语义也未要求** | **4 / 15** | 见下表 |
  | sections 为空的模板 | 0 | 29 条都声明了分节 |

  真不一致的 4 处（**全部是他人所写的模板，我新增的 quality/review 系列 5 处经核对均为语义已覆盖**）：
  | 模板 | 声明章节 | prompt 实际要求 |
  |---|---|---|
  | `code-review` | 结论 | 「按严重程度列出问题…给出重构优先级」，未要求「结论」节 |
  | `knowledge-playbook` | 准备 | 「目的、具体操作、检查点、失败怎么补救」，无「准备」|
  | `data-analysis` | 背景 | 「计算脚本与结果…结论必须可执行」，无「背景」节 |
  | `data-metrics-design` | 目标 | 「北极星/一级/二级指标…定义、公式、数据来源、误读」，无「目标」节 |

  危害等级为何只到 P2 而非 P1：**因 §1 的零消费方，这个不一致不会造成任何运行时故障**
  —— 它只误导读模板的人（以为产出会分这些节）。若将来给 Sections 加了校验消费方，
  这 4 处会立刻从「文档不一致」升级为「产出必然验收失败」。

- **P2｜面板新建模板时 `sections: []` 硬编码**（`assets_script.go:735`）：用户经面板创建的模板
  一律空分节，与内置 29 条普遍声明分节的做法不一致 —— 是「装饰性字段无人维护」的必然结果。

## 3. 正确性

- 本轴未发现问题。检查了什么：模板 JSON 往返（`RegistryRoundtrip`）、`Validate` 对占位符白名单
  的校验、`Render` 五字段填充（round 116 已修 `{prev}` 空洞，本轮复查两处生产构造点均已填满 5 字段）。

## 4. 安全 / 5. 性能

- 两轴均未发现问题，且**不是「没看」**：`Sections` 不进任何鉴权/注入路径（它只被序列化成 JSON
  随模板存盘），也不在任何热路径上被读取（零读取方）—— 一个没有读取方的字段不可能有性能问题。

## 附：这个数字我量错了两次（方法论教训）

同一件事我先后得到 **83 / 68 / 82** 三种「字面命中」数：

| 尝试 | 方法 | 结果 | 为什么错 |
|---|---|---|---|
| 1 | Node 正则解析 Go 源码，按 `mk("` 切块取字符串 | 83 | 块边界与字符串归属判断错，把非 prompt 的串也算进 prompt |
| 2 | 同上但改为「取最长字符串」 | 68 | 多段 `"…" +` 拼接的 prompt 只取到最长一段，漏了后续 |
| 3 | **Go 端运行时**遍历 `Defaults()` + `strings.Contains` | **82（采用）** | 唯一读取真实 `PromptTemplate` 字段值的方法 |

**结论**：凡「字段值是否满足某条件」的判断，**必须执行程序读运行时真值**，不能靠解析源码文本 ——
解析器要重做一遍 Go 的词法与拼接语义，出错面远大于收益。本仓同类前例：round 92 用 git grep
ERE 校验自己的 import 正则（因为 .NET 正则与 POSIX 不同）、round 116 用行为测试而非静态扫
判 `esc()` 是否漏字符。三次都在「换到真实执行层」后才发现前一版测量是错的。

另外：探针（`cmd/sectionsprobe`）**用完即删**，并复验 `check_untracked_go` rc=0 ——
未跟踪的 `.go` 会被我自己的门禁算成「未入库生产文件」，留下它就是污染基线。

## 合并结论

**本轮不改代码（NO-OP，登记性结论）。** 三个候选动作都被实测证据否掉：

1. **不去补那 4 条 prompt** —— 那是在给一个零消费方的字段补一致性，为不存在的需求做改动；
   且 `knowledge-playbook`/`data-analysis` 的 prompt 是他人所有、经过调优的产出契约文本。
2. **不删 `Sections`** —— 它是 `model.OutputSpec` 的 API 契约面（JSON 标签），前端与导入导出
   都在传它；删除是跨接口改动，且「有消费方」可能是未来的正当设计，属产品决策非工程清理。
3. **不加「prompt 必须提及每个声明 section」的门禁** —— 实测会把 5 处语义已覆盖的判成红
   （我的同义词核对就是为避开这个坑才做的），而且等于把 §1 的死字段冻结成契约。
   这正是本仓第 9 类失效「判据本身误报」与 round 64/108 的在册教训。

**若将来要让 Sections 真正生效**（推荐路径，按序）：先在 `autonomy` 加 `CriterionSections`
消费方 → 消费方上线后，本报告的 4 处不一致立刻变成阻塞项，须逐条补 prompt → 面板
`sections: []` 同步改为可编辑。顺序不能反：先有消费方再谈一致性。
