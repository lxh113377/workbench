## Q2 这些 queued 任务是「parked」还是「可派发」

### 2.1 取件链条（代码事实）

一次取件要顺序穿过 6 道：

1. **tick 互斥**：`tickBusy.CompareAndSwap(false,true)`（engine.go:784-788），上一轮没跑完就跳过。
2. **池冷却闸门**（engine.go:810-812）：`if until := e.poolWaitUntil.Load(); until > now { return }` —— **在 Pop 之前直接返回**。
3. **供料门**（engine.go:835）：`if e.q.Len() == 0 { supplyCandidates }`，非空则只记 WARN，不补货。
4. **并发槽**（engine.go:847-851）：`case e.slots <- struct{}{}`（容量 = `Executor.Concurrency`，config.json = 6），拿不到槽就 return。
5. **Pop 本体**（queue.go:141-165）：遍历排序后的候选，`if t.State != model.StateQueued { continue }`（150 行）、`if t.ChainID != "" && q.chainBusy[t.ChainID] { continue }`（153 行）；命中则从 items 删除并置 `chainBusy[chainID]=true`。
6. **取走之后**（engine.go:1862-1866）：`if avail := e.router.AvailableLanes(); len(avail) > 0 { ... 立即重调度 } else { 设闸门 + 退回 queued }` —— 全部车道不可用时，任务**被退回**，不是被执行。

### 2.2 逐条对照（拿重放结果 + 日志 + 代码逐条核）

## Q4 结论

1. **队列里有 1 条任务**，不是 0。queue.json 的 `queued=0` 是 15:28:36 的旧快照；把 1239 行 WAL 叠上去，真值是 `task-1793359141350-56a4` / state=queued / attempts=0 / poolWaits=42 / poolWaitCeil=48 / errorKind 空 / createdAt 19:19:01 / 最后一次状态变更 20:42:52。
2. **它不是「一直 parked 没人管」**：86 分钟里被取走 42 次，queued 累计 61.1 分钟、running 累计 22.7 分钟，单段最长 queued 仅 5.0 分钟。
3. **不跑的直接原因有两层**：① 每轮尝试都被上游限流 —— 台账里 rate_limited 26 + quota_exhausted 8，0 条 done；② 全车道不可用时 `requeueForPoolWaitKind` 把整池闸门推到「最早可用 + 5 秒」并封顶 5 分钟（engine.go:1868-1880），闸门关着时 tick 在 engine.go:810 就 return，连 Pop 都不走，于是 `e.q.Len()` 恒为 1、`inflight` 恒为 0 —— 这正是 WARN 每 5 分钟一条的成因。
4. **附带伤害**：供料门 `if e.q.Len() == 0`（engine.go:835）被这条 queued 顶死，5 小时 14 分里 WAL 只出现 4 条 `create`（且都是同一条链的第 4-7 次推进），自主规划与模板补货全部停摆。按现有预算，poolWaits 到 48 会走 `failTask(...PoolWaitCapped)`（engine.go:1841-1850），距采样还剩 6 轮 ≈ 30 分钟，届时才会解锁供料。
5. **判定取舍**：Pop 层条件（state=queued、链不忙）全部满足且实测被取 42 次 ⇒ 排除 `ELIGIBLE-BUT-NOT-DISPATCHED`（派发器停摆不成立）；重放非终态=1 条 ⇒ 排除 `NO-QUEUE-ITEMS`。存在明确的、代码写死的取件前置条件不满足（池冷却闸门 `poolWaitUntil<=now`，以及取走后的 `AvailableLanes()>0`），故判 **PARKED-BLOCKED**。注意语义边界：这是「每 5 分钟一段的 parked」，不是死锁。

### 未取证 / 边界（不把推测写成事实）

- 引擎**内存里的 `poolWaitUntil` 数值无法直接读取**（无 pprof/HTTP 状态接口，且禁止重启进程）。文中闸门值是同进程自己打的日志字段 `untilMs`（E12），不是推断值。
- `tickBusy`、`chainBusy`、`slots` 三项无法直接观测，判据是「行为证据」：129 条 WARN 均匀分布（tick 在跑）、42 次 queued→running（槽位与链均未卡死）。
- 未读取进程内存、未附加调试器、未调用任何会改变状态的接口；WAL 与 queue.json 全程只读。
