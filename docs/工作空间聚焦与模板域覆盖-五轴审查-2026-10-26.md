   ② 观察期临时停用计划任务（`schtasks /Change /TN WorkBenchKeepAlive /DISABLE`，回滚 `/ENABLE`）。
2. **新登记 T14**：round 2 我把运行根放在 `D:\workbench-agent`（仓外）—— 在**产物族判定**（VersionInfo `ProductName=个人AI工作台`）下它同样算「生产实例」，
   于是被规则 A/B 当作残留回收；而仓库自己的生产实例固定在 `D:\workdesktop\dist\workbench.exe`。
   但 canonical 实例**又选不了本仓**（`Validate` 禁止选 exe 自身目录的父目录）⇒
   「自动任务真正跑起来且长期存活」的前置是：**canonical 实例 + 一个位于仓外的目标项目目录**（否则只能停在 project 模式）。

### 1.14 T15 实测闭环（round 14）：首进展预算从「空转」到真正生效

**第二版（`b40be85`）**：新增 `IsSubstantiveEvent`（`final/text/thinking/tool_call/error` 算；`status` 带 usage 或
`phase=turn_end/step_end` 算；握手不算），首进展判定改用独立信号 `lastProgress`（不再复用「任何事件」的活跃度）。

**真跑读数**（同一 live 实例、同一目标「提升工作空间项目的全栈工程质量 · 体检」、keepalive 临时停用、观察后已复原）：

### 1.15 T15-② 实测闭环（round 15）：探测不再抹掉执行侧失败，首路由不再永远落在零产出模型上

**缺陷（有账本数据）**：`ApplyProbe` 的 StateHealthy 分支原先无条件 `ConsecFail = 0; Success++; CooldownTo = 0; LastErr = ""` ——
探测只证明「端点可达」，却被当成「模型会产出」。实测健康账本：`deepseek-ai/deepseek-v4.1-flash`
`succ=17 fail=3 **consec=0** cooldownTo=0 state=healthy`；同一时刻 `model-status.jsonl` 里是
`probe: from degraded to healthy（探测状态变化）` + `本轮探测 36 个：可用 36 / 下线 0` ⇒ **每轮探测把执行侧刚记下的失败擦掉**，
于是每个新任务的首个路由永远落在实测跑不出东西的模型上（round 8/9/11/13/14 五次尝试全是它）。

**修法**：新增 `isExecutionFailureKind(kind)` —— 结构性故障（unreachable / missing_credential / bad_endpoint …）可由探测恢复；
执行侧失败（stalled / bad_exit / timeout / upstream_failed）只能由**执行成功**清除。`ApplyProbe` 的 healthy 分支据此分流，
可达性信息（ProbeOK / LatencyMs / State）照旧更新（冷却期内仍被调度器跳过：State=Healthy 但 `CooldownTo > now`）。

**真跑读数**（同一 live 实例、同一目标、keepalive 临时停用，观察后已复原）：

```

（其间一轮探测：可用 36 / 下线 0）
after : deepseek succ=18 fail=4 consec=1 cooldownTo=0 state=healthy     ← 连续失败不再被探测清零
16:20:25 尝试 z-ai/glm-5.3        → 16:21:54 stalled（~149 s 早回收）→ 轮换 openai/gpt-oss-20b
16:22:34 尝试 openai/gpt-oss-20b  → bad_exit → 轮换 z-ai/glm-5.3-flash
```

⇒ **首路由不再永远落在实测零产出模型上**（本次任务首个模型是 `z-ai/glm-5.3` 而非 deepseek），且 T15-① 的早回收（~149 s）继续生效。

**顺带实测到的设计选择（记录，不作缺陷）**：`bad_exit` 在 failover 里被标为 `skip — 任务级失败，不计入模型健康度`，
即只有 `stalled` 一类会进健康账本；与 `isExecutionFailureKind` 的列表不冲突（bad_exit 只是备而不用）。

### 1.16 T15-③ 结论（round 16）：预算被遵守，残差 = 判定粒度 + 回收耗时

round 14 的残差（首进展预算 120 s、实测 `elapsedMs` 152.8 s）本轮用**插桩**读开了：零进展回收的文案现在同时给出
「首进展预算」与「看门狗判定时刻」，于是 `elapsedMs`（= 启动 → `cmd.Wait` 返回）可以拆成两段。真跑读数：

```
16:39:36 尝试开始  model=deepseek-ai/deepseek-v4.1-flash   task=…2110-plan-r0
16:42:01 尝试结束  kind=stalled elapsedMs=144128
         reason="启动后零进展（首进展预算 2m0s，判定于 2m7.653s 且无任何实质进展），已提前回收并轮换下一个模型"
```

分解：预算 120 s → **判定于 127.653 s**（+7.65 s，正是看门狗 5 s ticker 粒度 + 调度抖动）→ `cmd.Wait` 于 144.128 s 返回
⇒ **判定→回收完成 = 16.5 s**（杀 DSH 子进程树 + 关管道 + 等 Wait）。
即：**「预算没被遵守」被否定**；残差 = 判定粒度（≤ ~8 s）+ 回收耗时（~16–25 s）两部分。

**由此产生的新登记 T15-⑤**：这 16.5 s 被算进尝试时长，直接推迟了下一次轮换；若要贴近预算，
可在 kill 之后**异步**等待回收（下一模型的尝试不必等上一进程树完全消失）—— 这是「失败快速轮换」的最后一格。

### 1.17 T16 实测（round 17）：零产出的直接成因 = 上游额度耗尽被当成健康

**取证链（三条独立读数，互相印证）**：

1. **子会话缓存（DSH 自己的遥测）**：`tokenUsage.totals = uncachedInputTokens=0; outputTokens=0`、
   `contextPressure.surfaceTokens=623` ⇒ **一个 token 都没产出**，且 prompt 很小（否定了「提示词过大撑爆上下文」的猜想）；
   另有 `turnBoundary: lastStepBoundary=start`（只到 step 起点就再无进展）。
2. **`our-free-model/availability.json`**（16:42:06 探测，egress CN）：**1 个 region-blocked + 7 个 throttled**，
   throttled 的 detail 全是「Free usage limit reached…」。
3. **代码**：`probeSpecs` 原先只把 `unavailable / region-blocked / deprecated` 判为不可用 ⇒ **throttled 被当成健康**，
   调度器继续把额度已耗尽的免费车道当可用 ⇒ 每次尝试白烧 120–150 s 且必然零产出。

**修法**：新增纯函数 `upstreamVerdictState(verdict)`（`unavailable/region-blocked/deprecated` ⇒ down/`model_unavailable`；
**`throttled/rate-limited/quota-exceeded` ⇒ down/`model_throttled`**），`probeSpecs` 改调它；11 条边界单测（含大小写/空格不敏感、
「上游无判定不得判 down」）。恢复路径保留：throttled 判 down 后仍走既有周期探测与冷却，上游恢复即回调度队列。

**真跑读数**（部署后，keepalive 临时停用，观察后已复原）：

**遗留限制（如实标 · 新登记 T16-②）**：availability 的键是 OFM 车道 id（`*-free`），而池里 36 条路由用的是另一套 id
（如 `deepseek-ai/deepseek-v4.1-flash`、`z-ai/glm-5.3`）⇒ 本轮只有 **8 个 id 对得上**，其余 28 条「healthy」里很可能仍有
上游同样耗尽的孪生 id。下一步：把两套 id 空间做**显式同族合并**（同一上游模型的多个别名共享判定），否则限流判定会从别名缝里漏回来。

### 1.18 T16-② 实测（round 18）：上游判定按「同族」合并 —— 别名 id 不再从限流缝里漏回调度

**缺口（round 17 遗留）**：availability.json 的键是 OFM 车道 id（`*-free`），池里 36 条路由是另一套写法，
