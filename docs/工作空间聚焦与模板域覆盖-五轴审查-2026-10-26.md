两次「真跑」都在**数分钟内**被环境回收，且**不留任何停机痕**（这正是把「环境回收」误读成「产品静默死亡」的陷阱）：

| round 9 | 13:51:11 | 13:54:13（模型路由表已更新） | ≤14:04 | state.json 仍 running、stoppedAt=0 | 永远 running（无尝试结束） |

日志里**没有** panic / 自愈 / 停机记录，面板端口 refused ⇒ 既不是优雅停机，也不是产品自愈路径。
最可能成因：引擎由**本 harness 的 shell** 用 Start-Process 拉起，进程树绑在宿主作业对象上，

故 T11 与「被回收的进程树」同源的概率高，降级为**待确认观察项**，不再当确证缺陷。

### 1.11 深度取证（round 11）：workbench 进程「静默硬终止」—— exit code -1、stderr 全空（登记 T13）

round 8/9 只看到「进程消失」。本轮改用**控制台子系统**构建（去掉 -H=windowsgui）并把 stdout/stderr 重定向到文件，
再以 .NET 探针 `WaitForExit` 取退出码，才拿到进程终止时的**真实读数**：

| 实验 | 通道 | 结果 |
|---|---|---|
| 1 | 现场 exe（GUI 子系统），WMI/CIM + cmd 启动 | 14:30:37 起 → 最后日志 14:33:38（≈start+181 s）→ 进程消失；任务无收尾 |
| 2 | 控制台 diag（stderr 重定向到文件） | 同上；`diag-err.txt` **0 字节**、`diag-out.txt` **0 字节** |
| 3 | .NET 探针（`WaitForExit` 取退出码） | `exitCode=-1`、`elapsedSec=308`、stderr **空**、stdout **空** |

结论与排除项（全部实测）：

1. **不是 Go panic** —— panic 会向 stderr 打印栈；控制台构建下 stderr 是 **0 字节**。
2. **不是自愈重启** —— 日志里没有「资源自愈触发 / 自愈停机」；`state.json` 停在 `running`、`stoppedAt=0`。
3. **不是并行轮次会话的清扫** —— `gate-readings.jsonl` 最后写入 11:18:07，此后 3.5 h 无活动。
4. **不是「我的 shell 作业对象随调用结束回收整树」** —— 经 WMI/CIM + cmd 启动（父进程是 WmiPrvSE/cmd、不在我的进程树里）
   同样在 ~3–5 分钟内死亡；同一时刻 shell 子进程并不受影响。
5. **对照实验未取得可信读数**（如实标）：中性长进程探针的启动路径没跑起来（探针日志为空，匹配到的进程其实是我自己的工具壳），
   故「环境是否会回收任意长驻进程」这一问**仍未定论**，不得据此下结论。

⇒ 新登记 **T13（P0）**：**谁在 ~3–5 分钟处终止 workbench？** 已知形态 = 外部强制终止或无声 exit（退出码 -1、零 stderr、零 app 级记录）。
下一步判据（可执行）：① 先在**与 AI 工具链无关**的通道（计划任务 / 独立会话）跑通中性对照，观察 ≥10 min；
② 对死亡时刻做秒级定点（3 s 轮询记录消失时刻）并在那一刻快照进程表，抓 taskkill/pwsh/node 等候选；
③ 给 app 加「退出即留痕」（任何 exit 路径写一条 `process_exit` + 退出码）；
④ 若确认为外部终止，则 T10 的复现必须在**作业对象之外且非本工具链**的通道里做。
