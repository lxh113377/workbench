# 缺陷报告：多实例端口互相抢占，后起者静默自我了断（2026-10-19 15:5X · ds 端）

## 现象
生产实例（dist\workbench.exe）进程不在、面板打不开，而守护脚本（keepalive）反复"拉起"无效。
现场：17890 被另一个实例（Lead 的 fixtest/wf.exe，独立数据根）占着，我方实例 count=0。

## 根因（代码级）
`cmd/workbench/main.go:108-124`：

```go
lock, alreadyRunning, err := single.Acquire(...)   // 我方拿到锁（对方已死或未持锁）
...
if p, ok := single.ProbeRunning("127.0.0.1", basePort, 10); ok {
    openPanel(...)          // 打开别人实例的面板
    fmt.Println("工作台已在运行：...")
    return nil              // ← 直接返回，不启动自己的服务
}
```

**锁与端口探测是两个独立判据**：锁能拿到（说明没有同数据根实例），但端口被**不同数据根**的
实例占着（Lead 的 fixtest/soak 都用 config.server.port=17890 或 ProbeRunning 避让后的端口）。
于是新进程误判"已有实例在跑"，打开别人面板后退出 ⇒ 生产实例永远起不来。

## 影响
- 24×7 场景下，任何同机第二个实例（验收/压测/修复验证）都会把生产实例挤掉；
- 守护脚本无法修复（它不杀别人进程，也不该杀）；
- 用户看到的是"工作台打不开"或"打开的是别人的面板"，极难排查。

## 修复建议（Lead 定）
1. **启动时若 ProbeRunning 命中但锁在自己手里** ⇒ 说明端口被异源实例占用，应报错退出
   （明确告诉用户"端口 17890 被其他实例占用"），而不是静默打开别人面板；
2. **端口自动避让**：锁拿到但端口被占时，自动换 17891/17892…（ProbeRunning 已有避让逻辑，
   但只在锁拿不到时走；应扩展到"锁拿到但端口占"的场景）；
3. **fixtest/soak 类测试实例用不同端口**（配置里显式指定），从使用侧规避。

## 复现
1. 起一个实例 A（数据根 X，端口 17890）；
2. 再起一个实例 B（数据根 Y，同端口配置）；
3. B 打印"工作台已在运行"并退出，A 继续跑 —— 若 A 先死，B 再起同样起不来。

## 边界
只读定位 + 现场取证；未改 workbench/ 与任何他人文件。本轮 keepalive 表现符合设计
（幂等、不杀别人进程），缺陷在产品侧。

## 更新（16:1X）：端口避让兜住了部分场景

实测：17890 被 wbsoak26 占用时，生产实例自动起到 **17891** 并正常服务
（面板可达、引擎 running、26 任务/20 成功）⇒ 生产与压测实例并存运行。
ProbeRunning 的避让逻辑在"锁能拿到但端口被占"时也生效。

**仍建议修**：main.go:118-124 的"静默打开别人面板后退出"路径具有误导性，
应改为显式报错（"端口 17890 被异源实例占用，已避让到 17891"）。
