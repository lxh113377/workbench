# 缺陷修复：托盘「退出工作台」关不掉

> 取证与修复时刻：2026-10-19 22:14–23:10
> 老大原话：「程序怎么我点退出工作台关不掉了?修好」
> 附截图：托盘右键菜单（打开面板 / 启动引擎 / 暂停 / 继续 / 停止引擎 / 退出工作台）
> 快捷方式：`个人AI工作台.lnk` → `D:\workdesktop\dist\workbench.exe`

## 一、先说结论

点「退出工作台」后进程确实退了，但**不超过 60 秒就被外部守护重新拉起并自动开跑** ——
所以用户看到的是「关不掉」。

根因是**生产者与消费者各缺一半**：

| 角色 | 位置 | 缺什么 |
|---|---|---|
| 生产者 | `workbench/cmd/workbench/main.go` 托盘回调 | 退出时**不表达**「这是用户主动退出」，只落 `stopped` |
| 消费者 | `tests/keepalive.ps1` + 计划任务 `WorkBenchKeepAlive` | 把 `stopped`/`idle` 一律当「该拉起来」，**不看**用户意愿标记 |

产品侧其实早就铺好了表达能力（`engine.MarkUserQuit` 会落 `state.json` 的 `userQuit`
与 `runtime/user-quit.flag`），但**只有 `--quit`/面板 `/api/engine/quit` 这条 HTTP 路径在用**，
托盘这条不经 HTTP 的入口漏了；同时守护脚本创建至今从未读取过该标记。

> 一句话：**产品说了话，但没从这个入口说；守护有耳朵，但从来没听。**

## 二、现场复现（修复前，真实运行态）

在被替换前的旧二进制上，用**真实托盘菜单命令**（`WM_COMMAND 1006`，等价于用户点
「退出工作台」）打到当前实例：

```
22:32:59  pid=31068  flag=False  state={ "phase": "running", ... }        <- 基线
>>> 发送真实托盘菜单命令 WM_COMMAND 1006 到 hwnd=723144
22:33:09  pid=none   flag=False  state={ "phase": "stopped", ... }        <- 已退出，未标记
22:34:00  pid=34348  flag=False  state={ "phase": "running", ... }        <- 被拉起并开跑
22:34:10  pid=none   flag=False  state={ "phase": "stopped", ... }        <- 又被停（外部）
22:35:01  pid=22404  flag=False  state={ "phase": "running", ... }        <- 再次被拉起
```

即：退出后 **60 秒**被拉起、**120 秒**又被拉起 —— 与守护「每分钟一次」的节奏完全吻合。

## 三、机制链（逐跳可核）

```
用户点托盘「退出工作台」
  → wndProc 收 WM_COMMAND(1006)          tray_windows.go:258-259
  → handleCommand → go currentOpts.OnQuit()   tray_windows.go:323-326
  → OnQuit: 旧实现 = eng.Stop() + srv.Close() + os.Exit(0)   main.go:358-362（旧）
  → state.json: phase=stopped                                     ← 但**没有** userQuit
  → 进程结束
  → ≤60s 计划任务 WorkBenchKeepAlive 触发 tests/keepalive.ps1
      Get-WorkbenchProc 判「进程不在」→ 拉起 --silent 新实例          keepalive.ps1:144-163
      新实例读 panel.url → 面板 data-state=stopped
      → 判「stopped 就拉回 running」→ POST /api/engine/start          keepalive.ps1:192-193
  → state.json: phase=running、Engine.Start 清掉一切标记
  ⇒ 用户观感「关不掉」
```

两个结构性事实（实测）：

1. 托盘退出**不经 HTTP**，所以 `web/server.go` 里 `handleEngineQuit` 的
   `MarkUserQuit`（server.go:402）根本没机会执行；
2. 守护脚本全文（grep `user-quit|UserQuit`）**0 命中** —— 标记落盘也没人读。

## 四、修复

### 4.1 生产者：托盘退出补上「用户意愿」（`workbench/cmd/workbench/main.go`）

新增 `quitByUser`，作为「用户主动退出」的唯一实现：

```go
quitByUser := func() {
    if err := eng.MarkUserQuit(); err != nil {
        logger.At("tray").Warn("记录用户主动退出标记失败", "err", err)
        hub.Emit(model.Event{Type: "warn", ..., Msg: "记录用户主动退出标记失败: " + err.Error()})
    }
    gracefulQuit()
}
```

托盘回调改为 `OnQuit: quitByUser`。

**边界（刻意区分，不是遗漏）**：`signal.Notify(SIGINT/SIGTERM)` 路径**仍然只走**
`gracefulQuit`，不落标记 —— 那是「被动中断」（被杀/关机/自愈），重启后**理应**接续，
落标记反而会破坏 7x24。用户意愿只由**用户自己的入口**表达。

### 4.2 消费者：守护尊重用户意愿（`tests/keepalive.ps1`）

新增 `Test-UserQuit`：主判据 `runtime/user-quit.flag`，回退判据 `state.json` 的 `userQuit`。
两处「拉起来」的判定都加上 `-not $userQuit` 守卫：

- 进程不在 → 拉起（`keepalive.ps1` 启动分支）
- `stopped`/`idle` → `POST /api/engine/start`（`keepalive.ps1` 续跑分支）

**刻意不做的事**：本脚本**绝不自己清标记**。清除点在产品侧（`Engine.Start`）——
守护若替用户清标记，等于「替用户改主意」，会把「用户想停」又变回「被拉起」。

> 修复过程中自测抓到一个真实错误：守卫第一版被写成**只打印消息的独立 if**，
> 紧随其后的 `if (-not $proc)` 仍无条件拉起 ⇒ 用户主动退出后照样被拉起（验收 4.1 判红）。
> 已改为把守卫并进**条件本身**，并由变异测试钉住。

### 4.3 安全阀

- 用户想恢复运行：点托盘/面板「启动引擎」→ `Engine.Start` 清标记 → 守护恢复正常。
- 想彻底停掉守护：停掉计划任务 `WorkBenchKeepAlive`（属运维动作，不影响本修复）。

## 七、给后续会话的三条铁律

1. **凡「主动停机类」入口，必须同一语义**：托盘 / 面板 / CLI 都是用户意图，必须落
   `MarkUserQuit`；信号（SIGTERM）与自愈停机是**被动中断**，**不得**落标记。
   —— 反例后果：落错方向会把「用户想停」变回「被拉起」（现象照旧），
   或把被动中断当用户退出（7x24 断链）。
2. **守护脚本的每条拉起判定都必须过用户意愿守卫**。只加在一条分支上等于没加 ——
   本项目已实测踩过（只打印消息的那版守卫）。
3. **判据必须与被断言对象同域**：验收别用「源 EXE 路径」匹配进程（会匹配到别处的实例），
   也别让 `Check` 写函数局部变量当计数器（会打印 `0 PASS / 0 FAIL` 把结果洗没）。
   本轮两个都踩了，已修。
