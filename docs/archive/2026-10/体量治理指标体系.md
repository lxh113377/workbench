# 体量治理指标体系

> 版本 1.1.0 ｜ 机器实现：`workbench/internal/gov`（`Budget` 阈值 / `Evaluate` 指标 / `Adjust` 自适应）
> 阈值落盘：`<数据根>/governance/budget.json`（面板可在线调整并留痕，改后回显生效值）
> 判据入口：`workbench.exe --governance status` ｜ `/api/gov/budget`

## 1. 三域指标体系（13 项量化指标）

### 1.1 业务体量（business）— 我们接多少活

| 指标 key | 名称 | 单位 | 默认警示线 | 默认红线 | 方向 |
|---|---|---|---|---|---|
| `tasksDaily` | 日产出任务数 | 个/日 | 160（80%） | 200 | 越高越差 |
| `contractsActive` | 在履约契约数 | 份 | 96（80%） | 120 | 越高越差 |
| `contractAmount` | 单契约金额 | 元 | 4,000,000 | 5,000,000 | 越高越差 |
| `outputBytes` | 产出区总量 | MiB | 4,096 | 5,120 | 越高越差 |

### 1.2 资源承载体量（resource）— 机器扛不扛得住

| 指标 key | 名称 | 单位 | 默认警示线 | 默认红线 | 方向 |
|---|---|---|---|---|---|
| `memMB` | 常驻内存 | MB | 560（80%） | 700 | 越高越差 |
| `handles` | 句柄数 | 个 | 2,400 | 3,000 | 越高越差 |
| `goroutines` | 协程数 | 个 | 1,200 | 1,500 | 越高越差 |
| `concurrency` | 并发执行数 | 个 | 4.8 | 6 | 越高越差 |
| `eventsBytes` | 单任务事件流 | MiB | 25.6 | 32 | 越高越差 |

### 1.3 运营规模体量（operation）— 跑得好不好

| 指标 key | 名称 | 单位 | 默认警示线 | 默认红线 | 方向 |
|---|---|---|---|---|---|
| `backlog` | 待处理积压 | 个 | 48 | 60 | 越高越差 |
| `throughputDaily` | 日吞吐量 | 个/日 | 9.6（120%） | 8 | **越低越差** |
| `avgCycleSec` | 平均单任务耗时 | 秒 | 720 | 900 | 越高越差 |
| `failureRate` | 任务失败率 | 比例 | 0.07 | 0.10 | 越高越差 |

> 警示线统一取红线的 80%（低方向指标取 120%），集中定义在 `gov.DefaultBudget()`。
> 改阈值三种方式：① 面板 `POST /api/gov/budget`（在线、留痕、回显）② 直接改 `budget.json`
> ③ `--set` 等价的一次性覆盖。**改完必须回显生效值**，防「改了没生效」。

## 2. 三态判级（ok / warn / red / unverified）

- **ok（绿）**：低于警示线
- **warn（黄）**：达到警示线但未破红线 → 只观察、不自动动
- **red（红）**：达到/突破红线 → 触发调整建议与预警
- **unverified（未验证）**：**取不到数与取到 0 是两件事**

两条「未验证」硬规矩（都有测试锁定）：

1. **零活动态**：当日任务 0 且积压 0 时，`throughputDaily` 记 unverified 而非红。
   新装环境没任务是「没数据」，不是「产能不足」；一旦有任务或积压，0 吞吐立刻判红。
2. **资源域 v ≤ 0 恒记 unverified**：真实进程的内存/句柄/协程/并发不可能为 0，
   取到 0 只可能是没测到（例如 CLI 单跑无 supervisor），记绿就是假账。

> **零数据不得记 PASS**：总等级在无采样时输出 `unverified`，CLI 退出码 3（不是 0）。

## 3. 动态监控机制

```
调度循环/监控循环（默认 300 秒）
   ↓ 采集
Sample{业务4项 + 资源5项 + 运营4项}
   ↓ 追加
governance/samples.jsonl（保留最近 5000 条，超限自动截断——体量治理自身也守体量纪律）
   ↓ 计算
Evaluate → 13 项 Eval（value/warn/red/level/ratio）
   ↓ 汇总
DomainSummary ×3 → 域等级 + 峰值占用率
   ↓ 落盘
alerts.json / adjustments.json / linkage.json（原子写）
```

采样周期 `gov.sampleSeconds`（默认 300，允许 5..3600）。面板「立即采样」不改变周期，只补一个点。

## 4. 自适应调整机制（滞回 + 步长上限，防抖）

| 参数 | 值 | 含义 |
|---|---|---|
| `HysteresisRedStreak` | 2 | 连续 2 个样本红才升级为 escalate 建议 |
| `HysteresisGreenStreak` | 3 | 连续 3 个样本绿且占用 <50% 才给 relax 建议 |
| `MaxAdjustPct` | 20% | 单轮建议变动上限 |

- **escalate（收紧/扩容）**：连续 2 红 → 输出「扩容 或 降负载」二选一的具体动作（带当前值与建议方向）
- **relax（放宽/回收）**：连续 3 绿且占用 <50% → 输出「回收预算 或 加负载」建议
- **黄区不动**：只观察，避免阈值附近抖动导致反复调整
- 每条建议带 `Basis`（连续 N 样本的依据）与 `Confidence`（样本越多越高），面板与 CLI 直接展示

**调整不自动改配置**：`AutoEscalate` 只把红区建议写进 `logs/governance.jsonl` 审计流，
真正的阈值变更必须走 `POST /api/gov/budget`（有人签字、有留痕）。理由是自动放宽阈值等于自废判据。

## 5. 体量治理自身的体量纪律

| 面 | 上限 | 机制 |
|---|---|---|
| `samples.jsonl` | 5,000 行 | 追加时内存裁剪 + 读取时尾部截断 |
| `contracts.json` | 无硬上限（业务数据） | 按到期日排序，单文件原子写 |
| `alerts.json` / `adjustments.json` | 覆盖式快照 | 只保留最近一次计算结果 |
| `archive.jsonl` | 只追加（审计流水） | 审计不可裁剪 |

## 6. 阈值配置示例

```json
POST /api/gov/budget
{
  "taskDailyMax": 200, "activeContractMax": 120, "contractAmountMax": 5000000,
  "outputBytesMax": 5368709120,
  "memLimitMB": 700, "handleLimit": 3000, "goroutineLimit": 1500,
  "concurrencyMax": 6, "eventsBytesMax": 33554432,
  "backlogMax": 60, "throughputDailyMin": 8, "avgCycleSecondsMax": 900, "failureRateMax": 0.1
}
```

非法值会被 `Normalize()` 拉回默认并**回显生效值**（例如 `memLimitMB=-5` → 700，`failureRateMax=9` → 0.1）。
