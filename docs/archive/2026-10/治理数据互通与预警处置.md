# 治理数据互通与预警处置

> 版本 1.1.0 ｜ 机器实现：`workbench/internal/gov/linkage.go` + `alerts.go`
> 数据落盘：`governance/linkage.json` / `alerts.json` / `adjustments.json`
> 入口：`/governance` 控制台「联动分析」区块 ｜ `GET /api/gov/summary` 的 `linkage` 字段 ｜ `POST /api/gov/recompute`

## 1. 为什么要打通（问题定义）

契约治理与体量治理如果各看各的，会出现两类典型误判：

1. **契约单看都很健康，但体量已经压垮执行链**：在履约契约数量和任务耗时强正相关时，
   单份契约的合规分仍然漂亮，直到失败率突然飙升才被发现。
2. **体量指标全绿，但合规在偷偷烂**：资源没超限不代表承载健康——低合规契约越多，
   同样的体量对应的返工、争议、履约风险越高。

打通的判据不是"两个模块都读得到数据"，而是**能产出跨线的协同决策信号**。

## 2. 数据链路结构

```
契约侧                          体量侧
contracts.json ─┐              samples.jsonl ─┐
（阶段/金额/履约质量）           （业务/资源/运营 13 指标）
                ↓                              ↓
        activeContract() 过滤         最近 12 点时间窗口
        （signed + performing）               ↓
                └──────→ BuildLinkage ←──────┘
                              ↓
              ┌───────────────┼────────────────┐
         Series[]        Signals[]        Allocations[]
      （时间序列）     （协同决策信号）    （风险分摊/承载评级）
                              ↓
                    LinkageToAlerts → 统一预警面
```

对齐口径：契约侧只取 `activeContract()`（签署 + 履约），起草/审核/归档不计入负载。
样本侧取最近 12 个点；**不足 3 点时相关系数照算但显式登记数据缺口**（不把不可靠结论当结论）。

## 3. 联动指标与阈值

| 指标 | 含义 | 预警阈值 |
|---|---|---|
| `loadRatio` | 契约负载率 = 在履约数 / 上限 | ≥ 80% 预警 |
| `corrCycle` | 契约负载 × 平均执行耗时的皮尔逊相关系数 | ≥ 0.6 且负载 ≥80% ⇒ critical |
| `corrFailure` | 契约负载 × 任务失败率的相关系数 | ≥ 0.6 ⇒ warn |
| `complianceAvg` | 在履约契约平均合规分 | < 70 ⇒ critical |
| `deliveryAvg` | 平均按期交付率 | < 80% 且有在履约契约 ⇒ warn |

## 4. 五类协同决策信号

| ID | 触发 | 严重度 | 决策 |
|---|---|---|---|
| `LK-1` | 负载 ≥80% 且 corrCycle ≥0.6 | critical | 优先压降在履约契约数（目标 ≤80% 上限），复核高金额契约交付节奏 |
| `LK-1b` | 负载 ≥80%（相关性不足） | warn | 启动存量结项排期；新增契约改走审批加签 |
| `LK-2` | 在履约平均合规分 <70 | critical | 冻结新增体量 2 周，集中补齐权责/要素/留痕三块合规缺口 |
| `LK-3` | 平均交付率 <80% 且有在履约契约 | warn | 下调该批契约的体量承载评级，把交付能力纳入下轮产能评估 |
| `LK-4` | corrFailure ≥0.6 且有在履约契约 | warn | 排查资源承载阈值，优先看内存/句柄/并发三项 |
| `LK-0` / `LK-OK` | 无在履约契约 / 未见异常 | info | 不产生处置动作，只留痕 |

## 5. 体量风险分摊（Allocation）

对每份在履约契约算一个**承载负载分**（0-100）：

```
负载分 = 金额占比 × 60 + (100 - 合规分) × 0.4
```

即「占用的业务体量份额」为主（60%），「合规质量缺口」为辅（40%）。评四档：

| 评级 | 负载分 | 含义与动作 |
|---|---|---|
| A | <30 | 低承载，可承接新增业务体量 |
| B | 30-50 | 正常承载，按常规节奏监控里程碑 |
| C | 50-70 | 偏高承载，纳入季度重点抽查 |
| D | ≥70 | 高风险承载，冻结新增同类契约，30 天内整改或降额 |

分摊结果在控制台「联动分析 → 体量风险分摊」直接可见，是"把体量风险算到具体契约头上"的落点。

## 6. 统一预警面与处置闭环

三类预警合并为一个面（`MergeAlerts`，按 ID 去重、红优先生）：

| Scope | 来源 | 条数上限 |
|---|---|---|
| `contract` | 单契约六类风险 | 每契约 ≤6 条 |
| `volume` | 13 指标中黄/红项 | 每指标 ≤1 条 |
| `linkage` | 五类联动信号（info 不入预警面） | ≤5 条 |

**处置闭环（考核项 K5/K6 校验）**：

1. 预警产生 → 面板可见（`/governance` 与 `/admin` 治理页签）
2. critical 级 → 自动写 `logs/governance.jsonl` 审计流（`AutoEscalate=true`）
3. 处置动作：契约类走阶段迁移（回退需填原因），体量类走阈值调整（需回显生效值）
4. 复算：`POST /api/gov/recompute` 或等下一个采样周期，预警消失即闭环
5. 考核：K5 校验 escalate 建议是否都有落点，K6 校验 critical 是否归零

## 7. 数据缺口声明（反自欺条款）

以下情况必须在输出里显式登记，**禁止静默当 0 处理**：

- 无体量采样（`samples=0`）⇒ 联动等级 unverified，总等级 unverified
- 采样 <3 点 ⇒ 相关系数照算但标注"不可靠，只作观察"
- 契约数与体量样本对不齐（窗口内无同步采样）⇒ 保留最近可用窗口并标注

落点：`Summary.DataGaps` 数组，控制台底部「数据缺口（必须显式声明）」区块，CLI 末行输出。
