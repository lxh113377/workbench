# 自主闭环死锁修复回执（2026-10-19 08:0x）

> 本文是 `docs/自主运行方案.md` §5 验证标准的**运行时排障证据**，不是设计叙述。
> 采集方式：隔离实例（临时目录 + 改名二进制 `wbaudit.exe`）+ 真实模型通道，
> 脚本 `tests/e2e_autonomy_loop.ps1`。

## 1. 发现方式

首轮真实闭环运行（隔离实例 wb-auto-e2e-31df266b，07:50 起）在第 2 个阶段之后**彻底卡死**：

```
decisions.jsonl 统计： plan=47  accept=2   （47 条 plan 全部被评估拒绝）
goals.json:           progress=69.8  stages=2/4
目标最后 12 条决策：   "reason":"评估拒绝：与最近任务高度相似（0.92）"
产出：                0（后续 45 分钟无任何新 final.md）
```

即：引擎在「规划 → 评估拒绝 → 3 秒后再规划 → 再拒绝」的空转里烧了 45 分钟，
自主闭环再也推进不动。这正是目标要求 3 里「确保自主运行全过程的稳定性」要防的失效模式。

## 2. 两处根因（都已修，带回归用例）

### 2.1 规划器重复判定口径过宽（`internal/autonomy/planner.go`）

`duplicated()` 用「归一化后前 12 字相同即重复」。而自主任务标题的构造是
`<目标标题> · <阶段焦点>`，同一目标下所有阶段天然共享前缀：

| 标题 | 前 12 字 | 旧判定 |
|---|---|---|
| 持续产出与能力沉淀 · 立框架 | 持续产出与能力沉淀 · | 重复 |
| 持续产出与能力沉淀 · 补证据 | 持续产出与能力沉淀 · | 重复 |
| 持续产出与能力沉淀 · 成文 | 持续产出与能力沉淀 · | 重复 |

后果：阶梯分支永远被跳过，只能走兜底；而兜底标题固定为 `目标标题 · 阶段N`，
同样被判重 —— 死锁。

**修复**：改为比较「最后一个 `·` 之后的焦点段」。焦点相同 = 同一任务；
焦点不同 = 不同阶段任务。无分隔符的短标题保留全文/前缀判定。

### 2.2 评估器重复门禁不区分同目标（`internal/evaluate/evaluate.go`）

评估器的重复门禁用 3-gram Jaccard 相似度比较 `标题 + Prompt`。自主任务的 Prompt
都带同一段「项目核心目标 + 已完成阶段」，标题又共享目标前缀，三维相似度长期 0.9+
（实测 0.92），超过 `similarityCap=0.9` ⇒ 第 3 个阶段起必然被拒。

**修复**：`recentItem` 增加 `GoalID`；门禁对「同目标的历史条目」跳过相似度比较
（同目标的阶段推进本来就是同一个工程的连续步骤）。**跨目标**的相似产出仍照常拦截，
有反向用例守护。

### 2.3 附带：模型路由表日志去抖（`internal/engine/engine.go`）

模型池按模型逐个回调路由表，启动阶段单轮同步写 20-30 行
「模型路由表已更新」，24h 运行下会把任务/切换日志挤出可读窗口。
改为「清单指纹变化 或 距上次记录 ≥2s」才记一行，信息量不减。

## 3. 修复后实测（隔离实例 wb-auto-e2e-bd6ee0b3）

修复前卡在 stages=2/4 再无进展；修复后同一脚本连续推进：

```
decisions: plan=4  accept=2
stages:    #0 持续产出与能力沉淀 · 立框架   q=8  words=1729 passed=True
           #1 持续产出与能力沉淀 · 补证据   q=10 words=2213 passed=True
progress:  62.5
criteria:  c-done 2/4 | c-quality 9/6 PASS | c-words 3942/3000 PASS | c-verified 0/2.4
```

关键差异：**阶段 1→2 的梯级推进恢复了**（立框架 → 补证据 → 成文），
不再出现「高度相似」拒绝。故障转移同时有实证：隔离实例 `model-status.jsonl`
记录了 14 条 `kind=switch`（模型失败自动切换）。

## 4. 修复后的完整闭环实测（20 分钟一轮）

修复后同一脚本（`tests/e2e_autonomy_loop.ps1 -WaitMinutes 20`）跑出：

```
decisions: plan=4  accept=3
stages:    #0 立框架 q=8  #1 补证据 q=10  #2 成文 q=9   (3/4)
progress:  68.8
criteria:  c-done 3/4 | c-quality 9/6 PASS | c-words 4912/3000 PASS | c-verified 0/2.4
failover:  model-status.jsonl 记录 14 条 kind=switch（真实故障转移）
repair:    ⚠ 排入返工 round=1（真实验收失败 → 返工 1 轮）
```

**结论**：`plan → accept → 下一阶段规划` 的闭环在真实模型通道上连续推进了 3 个阶段
（立框架 → 补证据 → 成文），并且真实触发了「产物验收失败 → 排入返工」链路
（`verify-round-1.json` + `prompt.repair-1.md` 落盘，第 2 轮通过）。

## 5. 仍未打通的一段（如实记录，不得宣称已达成）

`goalDone / nextGoal` 在真实通道上仍未出现，卡在一条验收标准上：

```
c-verified: 0 / 2.4   （至少 2.4 个阶段的产出通过真实执行验收）
```

根因链（有实测证据）：

1. `planner.DefaultCriteria` 新增了 `c-verified` 硬判据，要求阶段产出必须过真实执行验收；
2. 真实执行验收要求模型按 `<<<ARTIFACTS>>>` 产物协议输出（文件清单 + 内容 + 验收命令）；
3. 实测中模型的协议遵从率不稳定：
   - stage#0 / stage#1：只输出纯 Markdown → `materializeArtifacts` 返回 nil → `Verified=false`；
   - stage#2：输出协议但不自洽 → `python tool.py --help` 退出码 1 → 排入返工 → 返工后
     产出退回纯 Markdown（`article.md`），`Verified` 仍为 false。
4. 因此 `c-verified` 恒为 0，目标永远无法完成 ⇒ `goalDone/nextGoal` 不会出现。

**这是产品缺口，不是代码死锁**：`c-verified` 判据的意图（"只有真做出来的才算完成"）是对的，
但当前模型协议遵从率不足以稳定满足它。两条可行路线（下一轮候选）：

| 路线 | 做法 | 风险 |
|---|---|---|
| A 降低判据权重 | 把 `c-verified` 改为 `CriterionVerifiedRatio`（比例制）或降为 advisory | 会削弱"真做出来"的价值锚 |
| B 提高协议遵从率 | 在 planner 的 prompt 里直接内联协议要求的**最小示例**；返工 prompt 强调"必须重写完整产物块" | 需要实测验证遵从率提升 |

判据（达到即可勾掉）：`decisions.jsonl` 同时出现 `plan/accept/goalDone/nextGoal`，
`goals.json` 出现 `status=completed` 的旧目标且 `activeId` 指向新目标。
