# 缺陷：「网关错误：端口未监听 8326」——根因与修复（2026-10-20）

## 用户可见症状（老大实报）

工作台「模型池」总览卡红字：

```
网关错误：端口未监听: dial tcp 127.0.0.1:8326: connectex: No connection could be
made because the target machine actively refused it.
```

## 根因（两条，均有实测证据）

### 1. 措辞错位：把「正常环境态」渲染成「红色故障」

8326 是 OFM 渠道网关，属主随 DSH 桌面端起停 / 任务隔离 HOME 轮换而变。
它没在监听时，池子本来就有**设计好的兜底**：`SyncNow` 退回 catalog.json
数据面继续纳管模型（`service.go:212-224`），DSH 走 OFM provider 不依赖该端口。
但 `checkGateway` 把 Go 的裸 dial 错误原样塞进 `Detail`
（修复前 `gateway_check.go:44`），面板又一律用红色 danger 渲染
（修复前 `assets_pool.go:68`）⇒ 可自愈的环境态被显示成故障。

### 2. 缺陷放大：预算判据恒假 + 同址重复拨号

```go
// 修复前 gateway_check.go:112
if time.Now().After(time.Now().Add(budget)) {   // 右边恒 > 左边 ⇒ 恒假
    break
}
```

预算形同虚设，函数退化成「候选全试一遍」。而候选是 **base × key 的笛卡尔积**：

- 本机网关只有 1 个 base；
- 任务隔离 HOME 实测积累 **225 份 api-key**（`dist/runtime/dsh-home/tasks`）；
- 端口没开时，旧逻辑仍为每把 key 重复拨同一个端口。

实测量级：单实例 `model-status.jsonl` 里 `gateway-fail` **143 条**，
且是**每 600 秒一条连续成片**（`1792478450962` → `1792483292173` 连续 9 个周期）。
一次环境态被放大成持续的失败噪音。
