# 首页「重试」与桌面反复弹窗 —— 根因与修复（2026-10-19）

老大现场反馈两件事：
1. 快捷方式打开首页仍显示「重试」（红色按钮）；
2. `wbsoak26.exe` 在桌面上反复弹黑窗，问「可不可以不要」。

两件都不是「前端页面写得不对」，是两个各自独立的**运行时配置/代码缺陷**。

---

## 一、首页「重试」的根因：窗口指向了**已经死掉的端口**

### 现场取证

```
workbench 真实实例： pid=37568  port=17890  /api/status 连续 10 次 10~12ms   phase=running
老大看到的窗口：     --app=http://127.0.0.1:17893/   ->  17893 连接被拒绝（DEAD）
```

把真实实例 17890 用无头浏览器打开，连续采样 4.8 秒：

```
t0 400ms 800ms ... 4800ms   全部 state=running / label=运行中
```

**即：真实工作台是好的（首页稳定显示「运行中」）。「重试」来自那个 URL 已经失效的窗口** ——
页面里所有 `fetch` 都连不上，自动响应连续失败 3 次后按钮落进 `error` 态，
文案变成「重试」。前端这条失败收敛逻辑本身是**正确的**（它诚实地反映了「连不上服务」），
错的是有人把一个死地址交给了浏览器。

### 代码缺陷（两处，都在「二次启动」路径上）

**缺陷 1 —— `single.ProbeRunning` 顺延扫描邻居端口**
```go
// 修改前：从 basePort 起连扫 10 个端口，任何一个在监听都当成「工作台面板」
func ProbeRunning(host string, basePort, attempts int) (int, bool) {
    for i := 0; i < attempts; i++ {
        p := basePort + i
        if conn, err := net.DialTimeout(...); err == nil { return p, true }
    }
}
```

语义错误在于：**端口号相邻 ≠ 同一个实例**。现场实测 17890 是主实例、
17891 是压测副本（`wbsoak26.exe`），于是二次启动把浏览器指向了压测副本；
该副本一被停掉，窗口 URL 立刻变成死端口 → 首页「重试」。

修复：删除顺延扫描，改为**精确端口**探测 `ProbeExactPort(host, port)`。
回归用例 `internal/single/instance_test.go`：
`TestProbeExactPortDoesNotScanNeighbors`。

**缺陷 2 —— 二次启动不读 `panel.url`，且无视 `--silent`**
```go
// 修改前（cmd/workbench/main.go alreadyRunning 分支）
if p, ok := single.ProbeRunning("127.0.0.1", basePort, 10); ok {
    openPanel(fmt.Sprintf("http://127.0.0.1:%d/", p))   // ← 扫到谁就是谁
    ...
}
return nil   // ← 完全没看 silent，也不看实例自己写的 panel.url
```

修复：
- 新增 `resolveRunningPanelURL()`：**优先读运行实例自己写下的 `runtime/panel.url`**，
  并做 HTTP 存活校验；只有该路径失败时才回落到「配置端口的精确探测」。
- 新增 `panelAlive()`：**「端口在监听」≠「面板可用」**，必须真的返回 200 才认。
- `alreadyRunning` 分支补上 `if !silent { openPanel(url) }` ——
  压测/看护进程走 `--silent` 时不得在用户桌面上弹窗。

回归用例 `cmd/workbench/panel_url_test.go`：
`TestPanelAliveRejectsDeadPort` / `TestResolveRunningPanelURLPrefersRecordedURL` /
`TestResolveRunningPanelURLRejectsStaleRecord`。

### 修复后实测

```
$ dist\workbench.exe              # 二次启动，不带 --silent
工作台已在运行：http://127.0.0.1:17890/     ← 正确指向活着的实例，且不再产生死端口窗口
```

## 二、桌面反复弹 `wbsoak26.exe` 的根因：计划任务的**保活**逻辑

现场抓到的是完整链条（不是「工作台自己在弹窗」）：

```
计划任务 WorkBenchSoakKeepAlive（每 2 分钟触发一次）
   └─ powershell -File ...\soak-24h-v2\keepalive_tick.ps1
        └─ pythonw ...\spawn_hidden.py
             └─ Popen("wbsoak26.exe", "--silent", DETACHED_PROCESS | CREATE_NO_WINDOW)
```

证据：
- `keepalive.log` 里是连续多行 `spawned pid=...`；
- 任务定义 XML：`Repetition Interval=PT2M, Duration=P3650D`（每 2 分钟、持续 10 年）；
- 任务日志显示 15:16 / 15:18 / 16:25 等多轮重启。

**为什么会弹可见黑窗**：`workbench.exe` 的 PE 子系统是 `WINDOWS_CUI`（控制台程序），
一旦由**会分配控制台**的方式拉起就会弹窗。脚本注释里也记录了这条实测结论。

### 处置（按老大的明确诉求「不要」）

| 动作 | 结果 |
|---|---|
| `Disable-ScheduledTask WorkBenchSoakKeepAlive` | Disabled |
| `Disable-ScheduledTask WorkBenchKeepAlive` | Disabled |
| 停掉在跑的 `wbsoak*` 进程 | 归零 |
| 中和启动脚本（`keepalive_tick.ps1` / `spawn_hidden.py` / `start_hidden.ps1`） | 改为 `exit 0`，即使任务被误启用也拉不起实例 |

**原始脚本已保留备份**（不删文件，遵守「改动可回滚」）：
`*.stopped-by-user-162918`、`watchdog.ps1.DISABLED.OFF`、`watchdog_hidden.ps1.OFF`。
soak 的**证据数据（约 38MB，含 metrics.csv / audit.jsonl / governance.jsonl）原样保留**。

### 修复后实测

```
t+5s / t+10s / t+15s / t+20s    wbsoak=0   ports=17890
```

20 秒观察窗口内不再复活。

## 四、给后续会话的提醒（避免再犯）

1. **不要再启用 `WorkBenchSoakKeepAlive` / `WorkBenchKeepAlive`** ——
   `workbench.exe` 是控制台子系统，任何保活拉起都会在用户桌面弹窗。
   要做长时压测，请在**独立窗口站/会话**里跑，或改用真正的 GUI 子系统包装器。
2. **面板地址只有一个权威来源：`runtime/panel.url`**。
   不要用「端口扫描」「相邻端口有监听」推断实例归属（本轮就是这么错的）。
3. `--silent` 必须覆盖**所有**分支，包括「已在运行」分支 ——
   服务化/压测实例绝不能弹窗。
4. 端口 17891 曾被压测占据，导致 17890 与 17891 同时存活；
   若再出现「打开是重试」，先确认窗口 URL 是否指向了非 17890 的端口。
