## 根因判定

single.Acquire 的 defer lock.Release()（main.go:126）会 truncate 清空锁文件。
锁文件仍带 pid ⇒ **Release 未执行 ⇒ 进程未走正常 defer 链** ⇒ 属
「优雅停机后进程被外部终止」或「主 goroutine 在 Stop 之后直接退出而未返回」。

engine.Stop() 之后 main 的路径只有：
1. 托盘 OnQuit → eng.Stop() + srv.Close() + os.Exit(0)（**os.Exit 跳过 defer**）；
2. signal.Notify → eng.Stop() + os.Exit(0)（**同样跳过 defer**）；
3. supervisor 自愈 → eng.Stop() + os.Exit(0)（**同样跳过 defer**）；
4. main 正常返回（会跑 defer）。

⇒ 三条停机路径里有 3 个 os.Exit(0)，都会跳过 defer ⇒ 锁残留是**这些路径的必然产物**，
不能据此断定"被外部杀"。但**无论哪条路径，进程都会退出**。

## 24×7 需求的硬缺口（结论）

1. **进程退出后没有任何拉起机制**：开机自启只在开机时有效；进程一旦退出
   （托盘退出 / 崩溃 / os.Exit 路径 / 被别的会话按名杀进程），桌面端不会回来。
   今天是"优雅停机后进程消失"，若换成"panic 崩溃"场景，7x24 同样断。
2. **锁残留无自愈**：进程被强杀后 lock 文件残留 pid，虽然后来的 Acquire 用文件独占锁
   （旧 pid 死了锁自动释放，所以不会真的卡住第二次启动），但"无人在场重启"才是问题。
3. **429 期间没有任务可跑时，进程空转但不会退**（今天不是这个问题——是停机）。

## 建议（Lead 写入口，我不动 workbench/）

最小改动 = 加一个 watchdog：主进程内起 goroutine 或独立小守护，检测到
「engine 已 Stop 且配置 autoResume=true」时重新 Start（而不是让进程活着等托盘）。
更稳的方案：Windows 计划任务 schtasks 每 1 分钟 `workbench.exe start`，
单例锁天然保证只有一个实例（已有 Acquire 逻辑），成本近零。

## 修复方案验证（本轮实测）

**方案：Windows 计划任务每分钟探活拉起**（不改一行 workbench 源码）。

实测步骤与结果（13:53:48）：
1. 确认进程已死（Get-Process workbench 无输出）；
2. `Start-Process D:\workdesktop\dist\workbench.exe`（等价于计划任务动作）；
3. 6 秒后新进程 PID 8968 存活；
4. 面板 17890 恢复，**首页按钮 data-state=running**（autoResume 自动恢复运行，无需人点）。

为何与现有架构天然兼容：
- 单例锁（single.Acquire 独占文件）保证「已在跑时再启动」只会打开面板、不 fork 第二个实例；
- autoResume=true（config 实测）+ state.Phase=stopped 让新进程把引擎拉回 running；
- 探活命令可以是纯 PowerShell：`if (-not (Get-Process workbench -EA SilentlyContinue)) { Start-Process ... }`。

   final-check/soak-24h-v2/ui-probe 多个 workbench 实例，按名匹配会误判）；

## 踩到并记下的坑
1. **PS 5.1 对「HTTP 200 + 空响应体」抛 Object reference not set** —— /api/engine/start
   成功返回 204/200 无 body 时 Invoke-WebRequest 抛异常，**不能只凭异常判断成败**，
   必须调用后复查 data-state。脚本已容错 + 复查。
2. **端口会漂移**：17890 被 TIME_WAIT 占时 ProbeRunning 漂到 17891。脚本从
   `dist/runtime/panel.port` 动态读端口（面板自己会写这个文件）。
3. **DSH 沙箱下 pwsh 工具的 stdout 会丢**（管道 EPERM）：诊断手段是让脚本
   `Out-File` 写文件再读，或用 node child_process stdio 重定向。
4. **同机多实例**：Lead 的验收套件同时跑 final-check/soak/ui-probe 实例，
   进程名都是 workbench。任何"按进程名"的逻辑都会误伤，必须按 CommandLine 路径匹配。
