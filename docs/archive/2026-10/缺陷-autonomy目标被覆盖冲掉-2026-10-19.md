# 缺陷报告：autonomy 目标被引擎全量覆盖冲掉（多进程 store 竞态，2026-10-19 · ds 端）

## 现象
用 CLI 设的项目目标会**消失**：`workbench.exe --autonomy goal <标题> <意图> <领域>` 执行成功、
落盘可见（T+0 在册、active），但一段时间后 goals.json 里再也找不到它，decisions.jsonl 却留着
"人工设置项目目标"的记录（15:02:20、15:09:00 两次，goals.json 里对应目标均不存在）。

## 根因（代码级定位）
`internal/autonomy/store.go`：

- `persistLocked()` 用 `config.WriteJSONAtomic(goalsPath, s.file)` —— **整文件全量覆盖写**；
- `s.mu` 只是**进程内**互斥，跨进程没有共享锁（文件锁/事务）；
- CLI 子命令（`cmd/workbench/main.go:747` 新建 Manager）与常驻引擎是**两个进程、两份内存副本**。

于是时序：
1. CLI Upsert(manual goal) + SetActive(manual) → 落盘（含 manual 目标）；
2. 引擎在它**自己启动时**加载的旧副本上继续跑（副本里没有 manual 目标）；
3. 引擎下次任何一次 persist（任务完成/阶段推进/Bootstrap）→ 用旧副本全量覆盖 →
   **manual 目标被冲掉**，decisions.jsonl 的"人工设置目标"成了孤儿记录。

实测吻合：15:02 设的目标约 5 分钟后丢失（引擎完成一个任务后 persist）；
本轮（15:2X）引擎卡在 429 无完成任务 ⇒ 6 分钟仍稳定在册 —— **覆盖时机完全对应引擎的 persist 时机**。

## 影响
- 老大/AI 通过 CLI 或任何外部手段设的目标**不可靠**，会被静默冲掉；
- 只留下 decisions 痕迹，goals.json 无目标 ⇒ 排障时以为"设目标失败"；
- 与"人工可干预自主线"的设计意图相悖。

## 修复建议（Lead 定，两档）
| 档 | 做法 | 代价 |
|---|---|---|
| A（治本） | persist 前**重读磁盘**合并：`persistLocked` 里先 `ReadJSON` 当前文件，把"本地没有而磁盘有的 active/open 目标"合进来再写（last-write-wins 只对同一 ID 生效） | 约 20 行；需处理合并冲突（同 ID 以磁盘为准还是本地为准） |
| B（治标） | CLI 设目标后**通知引擎重载**：给面板加一个 `/api/goals/reload`，CLI 写完调它；引擎收到就重新 OpenStore | 约 30 行 + 一条路由 |
| C（规避） | 文档写明"设目标前先停引擎" | 零成本，但体验差 |

推荐 A：它同时保护"两个 CLI 并发设目标"和"CLI 与引擎并发"两类场景。
