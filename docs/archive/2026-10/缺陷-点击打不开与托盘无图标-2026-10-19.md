# 缺陷修复：「点击运行后打不开」+「状态栏没有图标」

> 取证与修复时刻：2026-10-19 21:0X–21:3X · ds 端
> 老大原话：「修复点击运行后打不开了,状态栏也没有图标的问题」
> 附截图：`打开文件 - 安全警告 / 无法验证发布者` 对话框

## 一、先说结论

两个现象是**四条独立根因**叠加出来的，没有一条是"前端写错了"：

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 双击快捷方式后桌面什么都不出现 | 快捷方式写死 `--silent`，而 `--silent` 的语义是"服务化实例：不弹面板" | 快捷方式去掉 `--silent`；启动脚本每次校验并自动纠正；两处面板调用点统一经 `shouldOpenPanel()` |
| 2 | 状态栏（托盘）没有图标 | 安装目录 `D:\workdesktop` 被沙箱打上 **Low 完整性标签**，从它启动的进程继承 Low IL，被 UIPI 拒绝向 Medium 的 Explorer 注册托盘图标（`NIM_ADD` → `Access is denied`） | 目录标签提升为 Medium（已实测生效）+ 三道自动自愈（构建门禁 / 守护脚本 / 进程内自检上报） |
| 3 | 双击时弹「无法验证发布者」安全警告 | 产物带 **MOTW**（`Zone.Identifier` 备用数据流），Windows 附件管理器拦截未签名 EXE | 清除 MOTW + 构建门禁（带 MOTW 直接判红） |
| 4 | 隔一段时间又"打不开"（复发性） | `isCanonicalExe` 只判「文件名 + 同目录数据根」，任何**在临时目录里造出的同形状副本**都会被当成正式安装位置，把桌面快捷方式改写到随时会被清掉的临时路径 | 判据加第三条"不在临时目录内"（`underTempDir`），并拆成两条正交判据分别可测 |

另修一条隐藏缺陷：`--silent` 只被"首次启动"分支尊重，**"已在运行"分支无条件弹面板** —— 守护/压测/自愈在桌面上反复弹窗的真正来源。

> 缺陷 4 是本轮**自己踩出来的**：改完前三条后跑全量测试，发现桌面快捷方式被指到了
> `D:\app-cache\temp\TestNonSilentDeclaresPanel1850797107\002\workbench.exe`。
> 也就是说：只要机器上跑过一次隔离 e2e，老大双击就又会"打不开"。
> 这解释了为什么这个现象此前"修好了又复发"——它不是同一个 bug 反复，而是**两个 bug 轮流生效**。

## 二、根因 1：`--silent` 语义被用反了

### 取证

快捷方式属性（修复前）：

```
Target=D:\workdesktop\dist\workbench.exe
Args=[--silent]          ← 罪魁
WindowStyle=7
```

实测复现（全新启动，两个方向各跑一遍）：

| 启动方式 | 新可见窗口 | 进程 | 端口 |
|---|---|---|---|
| `workbench.exe --silent` | **0 个**（桌面毫无反应） | 起来了 | 17890 在听 |
| `workbench.exe`（不带） | `个人 AI 工作台`（Edge --app 窗口） | 起来了 | 17890 在听 |

即：**进程一直是好的，是"不许弹面板"这个参数被写进了给用户点的快捷方式里。**

### 修复

`workbench/internal/shortcut/shortcut_windows.go`
- 快捷方式 `Arguments = ""`（原来写死 `--silent`）
- `WindowStyle = 1`（GUI 子系统产物不需要靠最小化掩盖黑窗）
- 回读校验从"只看 TargetPath"升级为 **TargetPath + Arguments 双校验**（只看 Target 查不出 `--silent` 残留）

`workbench/cmd/workbench/main.go`
- `ensureShortcuts` 从"跑过一次就永远跳过（`runtime\shortcut.ok` 标记）"改为**每次启动都校验并修复** —— 否则当年写坏的快捷方式永远不会被自动纠正
- 新增 `shouldOpenPanel(silent bool) bool`：两处面板调用点（首次启动 / 已在运行）**统一经它判断**，禁止各自判断
- 新增 `panelOpenedMarker = "已打开面板："`：凡真要弹面板先打这一行，让黑盒判据能抓"该弹没弹 / 不该弹却弹"

`workbench/cmd/workbench/main.go`（已在运行分支）
- 补上 `if !silent { openPanel(...) }` —— 这是"守护进程反复弹黑窗"的真正来源

## 三、根因 2：Low 完整性标签导致托盘图标永远注册不上

### 取证链（逐步排除，每步都有命令与输出）

**第 1 步 — 托盘窗口存在，但图标没注册上**

```
PersonalWorkbenchTrayClass hwnd=1836688 visible=False
Shell_NotifyIconGetRect → rc=0x80004005 (E_FAIL)   ← 图标根本没注册成功
```

**第 2 步 — 逐行复刻生产代码的注册路径，抓真实错误码**

```
RegisterClassExW ok
CreateWindowExW ok hwnd=2558722
LoadIconW icon=65579 ok
NIM_ADD #0 ret=0 err=Access is denied.     ← 不是代码问题，是权限裁决
```

**第 3 步 — 同一二进制换目录跑（唯一变量 = 所在目录）**

| 二进制所在位置 | NIM_ADD |
|---|---|
| `C:\...\Temp\` | ret=1 OK |
| `C:\Users\37533\Desktop\` | ret=1 OK |
| `D:\` | ret=1 OK |
| `D:\app-cache\...` | ret=1 OK |
| **`D:\workdesktop\**`** | **ret=0 Access is denied** |

**第 4 步 — 差异在目录的完整性标签**

```
D:\workdesktop            → Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)
D:\workdesktop\dist       → Mandatory Label\Low Mandatory Level:(I)(OI)(CI)(NW)
D:\workdesktop\dist\workbench.exe → Mandatory Label\Low Mandatory Level:(I)(NW)
```

机制：可执行文件带 Low 标签 ⇒ 即使由 Medium 的 Explorer 启动，新进程也被降为 **Low IL**；
Low IL 进程不允许向 Medium IL 的 Explorer 托盘注册图标（UIPI 强制），报错就是 `Access is denied`。

**第 5 步 — 确认 Low 进程自己修不了（决定修复位置）**

在 Low 目录里跑一个 Medium 权限的提标签尝试：

```
icacls <dir> /setintegritylevel (OI)(CI)M
→ exit status 1299
→ "Indicates a particular Security ID may not be assigned as the label of an object"
```

⇒ Low 进程**不能**给自己目录提标签，必须由已经是 Medium 的进程来修。

### 修复（三层，全部实测）

1. **立即修**：`icacls D:\workdesktop /setintegritylevel (OI)(CI)M`（Medium ⇒ 立即生效，托盘图标当场出现）
2. **进程外自愈**：`tests/keepalive.ps1` 每分钟检查并修复（它由计划任务以用户身份运行 = Medium，天然是修复位）
   - 实测：人为把 dist 打回 Low → 跑 keepalive → 输出「完整性标签 Low -> Medium（托盘图标修复）」，标签确实回到 Medium
3. **进程内自检 + 上报**：新增 `internal/tray/integrity_windows.go`
   - 注册失败时读自身目录标签与自身 IL；是 Medium 及以上就自动提标签后重试一次
   - 自身是 Low 就**不做无意义的重试**，而是把原因经 `tray.Options.OnWarn` 上报到日志与事件流（"静默少一个图标"是最难排查的形态）
   - 踩坑记录：`TOKEN_INFORMATION_CLASS.TokenIntegrityLevel` 是 **25**（18 是 TokenElevationType，用它会"成功"返回 4 字节 0x03，把级别误判成"读不到"）
4. **构建门禁**：`setup/build.ps1` 新增第 7 步 —— 产物目录若是 Low 标签，先尝试提升，仍 Low 则**构建判红**（坏标签不带进下一轮）

补充：托盘图标此前只有 `IDI_APPLICATION` 兜底（一张通用白板图），现改为 `ExtractIconExW` 取 EXE 自带图标，并与「图标被 Explorer 重启冲掉」的 `TaskbarCreated` 广播重注册一起补齐。


⇒ 有 MOTW 的产物在无人值守场景**会把启动直接卡死**，且属于"必须人工点一下"的步骤。

（`dist` 里现存 8 个历史副本 + 我本轮新增的备份）。已做：

- 清除现有产物的 MOTW（实测 `clean`）
- `setup/build.ps1` 新增第 6.5 步 MOTW 门禁：带标记即 `Unblock-File`，清不掉就**构建判红**

## 五之二、根因 4：临时目录副本劫持桌面快捷方式（复发性根因）

### 取证

改完前三条后跑全量测试，随后读快捷方式：

```
快捷方式 TargetPath = D:\app-cache\temp\TestNonSilentDeclaresPanel1850797107\002\workbench.exe
该目录存在? False        ← 测试框架已经把它清掉了
```

即：**只要跑过一次隔离 e2e，桌面快捷方式就指向一个已不存在的文件**，双击自然"打不开"。

### 机制

`isCanonicalExe` 原判据只有两条：文件名是 `workbench.exe` + 同目录有 `runtime/` 或 `workbench-output/`。
而 `cmd/workbench` 的黑盒测试为了模拟真实实例，**正是**在 `t.TempDir()` 里造出这个形状
（复制二进制 → 建 `runtime/` 与 `workbench-output/`），于是"形状判定"完全通过，
实例启动时 `ensureShortcuts` 就把用户桌面改写到测试目录。

这与早前 `wbsoak24.exe` 劫持是同一类事故，只是换了伪装：那次靠"改文件名"躲过，
这次形状一模一样，只能靠**位置**识别。

### 修复

`workbench/internal/shortcut/shortcut_windows.go`

```go
func isCanonicalExe(exe string) bool {
	return hasInstallShape(exe) && !underTempDir(filepath.Dir(exe))
}
```

拆成两条正交判据分别可测（合成判据在测试里必然恒假 —— 所有测试目录都在临时目录内）：
- `hasInstallShape`：文件名 + 同目录数据根
- `underTempDir`：从 `os.TempDir()` 起算的前缀排除（大小写不敏感、路径 Clean）

### 验证

- 变异测试：去掉 `underTempDir` → `TestIsCanonicalExe` **FAIL**（实测）
- 回归：连跑 **两轮全量测试**，快捷方式始终指向 `D:\workdesktop\dist\workbench.exe` ✅

## 七、给后续会话的两条铁律

1. **`--silent` = 服务化实例**（不弹面板、不污染桌面）。给用户点的入口**永远不带它**；
   守护/压测/自愈**必须带**它。两处面板调用点都必须经 `shouldOpenPanel()`，不要各自判断。
2. **`D:\workdesktop` 的完整性标签必须是 Medium**。它是可继承的驻留改动，
   一旦被沙箱打成 Low，从该目录启动的任何进程都注册不了托盘图标，而且 Low 进程自己修不了。
   已在三处布防（构建门禁 / keepalive / 进程内自检），发现 Low 就按上述路径修。
