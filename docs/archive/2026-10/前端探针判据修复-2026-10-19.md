# 前端探针判据修复（2026-10-19 · task-2 交付）

> 一句话：`tests/ui/cdp_probe.mjs` 此前**只判「探针脚本有没有抛异常」**，页面越界、页签半激活、
> console 报错一律判 `ok` —— 这叫**假绿**。本轮把它改成**按读数契约断言**，并补了
> 「故意错的期望必须红」的反证通道。

## 1. 假绿根因（改动前的一手证据）

改动前 `cdp_probe.mjs` 的结果处理段形如：

```js
results.push({ name: c.name, status: "ok", ... });   // 无条件 ok
...
const bad = results.filter(r => r.status !== "ok").length;   // 只有异常才算 bad
process.exit(bad > 0 ? 2 : 0);
```

后果：跑出 `ok=15 unverified=0` 的「全绿报告」，但实际**零断言** ——
它证明的只是「15 个探针脚本没有抛异常」，不证明任何一个页面契约成立。

## 2. 断言层（改动后）

每个用例带 `contract` 字段，由 `tests/ui/assertions.mjs` 按契约给出期望值，
探针返回的读数与期望逐字段比对；不达标 `status:"fail"`，探针自身异常 `status:"unverified"`。

| contract | 覆盖用例 | 关键断言 |
|---|---|---|
| `home` | home-desktop / 360 / 740x360 / 1920 | buttons=1、anchors=1、divs=0、images=0、inputs=0、textVisibleLen 受限、btn.insideViewport、overflowX=0 |
| `flow` | home-flow | 自动触发只发生一次（burstStartCalls<=1）、final.state ∈ {running,busy}、stopped 态无旋转环 |
| `rings` | home-rings | `stoppedTimeline` 末值 spinner=0、arc=0；`loadSettled` 非空 |
| `busy` | home-busy | 稳定 busy 态 aria-busy=true、spinner>0.5 |
| `tabs` | admin-desktop / admin-390 | finalActiveTabs=1、finalActivePanes=1、errors=[]、overflowX=0、各页签 anomalies 为空 |
| `metrics` | governance-390 / modelpool-390 / modelpool-desktop | overflowX=0、clipped=0 |
| `interact` | interact-admin / -modelpool / -governance | 各页面自己的控件动作有反馈（toast/状态变化） |
| `subnav` | subnav-hash-admin | `#logs` 深链 → 点 queue 写 `#queue` → `history.back()` 回 `#logs`；三态 activeTabs=1、activePanes=1 |
| `navlinks` | navlinks-admin / navlinks-governance | admin 须有 /governance、/modelpool、/? 三链接；governance 须有 /admin、/modelpool、/? |

**退出码语义**（与门禁一致）：有 fail ⇒ 2；只有 unverified ⇒ 3；全绿 ⇒ 0。
「没测成」永远不等于「通过」。

## 3. 基线红证据（改动前的旧口径 vs 新口径）

旧口径（无断言）：`ok=15 unverified=0`、`PROBE_RC=0` —— 全绿，但什么都没判。
新口径首次运行（页面尚未改到位时）：`ok=0 fail=18` —— 全部倒在 `data-not-object`（见 §5.1）。
说明判据层确实在**读数值**，而不是在数「脚本有没有抛异常」。

## 4. 反证（判据层可证伪，硬要求）

命令（故意把首页 `divs` 期望篡改成 1、`textVisibleLen` 篡改成 9999）：

```
node tests/ui/frontend-gate.mjs --selftest-expect-fail --md D:\workdesktop\xtmp\selftest-receipt.md
```

实测原文（节选）：

```
[selftest] 读数已篡改（home.divs=1, textVisibleLen=9999）：要求 exit=2（判据层能证伪）
报告: ...\gate-2026-10-19T11-38-00\cdp-report.json | ok=6 fail=4 unverified=8
[gate] 判定=SELFTEST-PASS（判据层可证伪）
GATE_RC=0
```

读法：**4 个 home 用例在读数被篡改后全部转 fail** ⇒ 断言层真的在比对读数。
（同一轮另有 8 条 `Target.createTarget 超时` 属通道侧 unverified，与页面无关，见 §5.3。）

## 5. 本轮实测抓出并修掉的三个判据层缺陷（都是自己抓的）

### 5.1 `data-not-object`：读数被当对象用，18 条全判 fail

探针脚本用 `ascii()/JSON.stringify` 返回**字符串**，断言层却按对象取字段。
修法：断言入口先 `JSON.parse`，解析失败才落 unverified，原始串保留进报告备查。

### 5.2 契约作用域错位（两处）

- `rings` 用例被套上 `spinnerInStoppedState` 期望 —— 那个字段是 metrics 系的，rings 只有 `stoppedTimeline`。
- `navlinks-governance` 被套上 `tabCount>=1` —— 治理控制台是独立单页，本来就没有页签。
修法：通用期望只保留「对任何页面都成立」的（如 `runtimeErrors===0`），其余一律进各自契约分支。

### 5.3 「没测成」不得冒充「测得差」

被测实例不可达 / 浏览器崩掉 / CDP target 超时 → 一律 `unverified`，
且门禁在结果集不完整时自判 UNVERIFIED（退出码 3），**绝不因「没有 fail」判 PASS**。

## 7. 与前端门禁的关系

`tests/ui/frontend-gate.mjs` 是**一条命令**的入口（自起自停隔离实例、自挑空端口、
自动从 `ui-probe.url` 取 token、跑完自动 taskkill），探针与断言是它的内核。
判据与退出码完全共用 §2 的语义，因此「门禁 PASS」= 「18 条断言全部成立且没有一条是没测成的」。
