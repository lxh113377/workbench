# 缺陷-排队14但0正在执行-根因与修复-2026-10-22

> 老大原话：「排队 14 但是 0 正在执行」。
 本轮定位到**两个**根因：一个是真停摆（本机把上游秒级限流拖成 20 分钟），
 一个是说不清（服务端握着能解释的字段却什么都没输出）。两处都已修复并部署。

## 现场取证（一手，可复跑）

活实例 `http://127.0.0.1:17890/`，watcher 每 10 秒一条采样（`xtmp/queuelane-watch*.jsonl`）：

```
22:31:04 q=14 r=0 done=10 rl=True/442  stall=      <- 用户看到的就是这两行
22:35:52 q=14 r=0 done=10 rl=True/58   stall=
22:39:14 q=14 r=0 done=10 rl=True/8    stall=
22:39:15 q=8  r=6 done=10 rl=False/0    stall=      <- 闸门到点后才恢复
```

同期引擎日志（`dist/workbench-output/logs/workbench.jsonl`）的冷却轨迹：

```
22:18:21 consecutive=1 wait=300
22:19:20 consecutive=2 wait=600
22:19:26 consecutive=3 wait=1200   <- 闸门落在 22:39，14 条任务 20 分钟一条没跑
```

## 根因一：退避层级永远涨不上去的恢复（真停摆）

`setPoolCooldown` 按 5min→10min→20min→30min 递增，而层级只在**成功一次**时清零。
但整池闸门按住的恰恰是唯一能产生成功的那条路：

```
429 → 闸门按住 → 没请求 → 不可能成功 → 层级不清零 → 下次 429 继续升档 → 30 分钟档永久钉死
```

后果不是"等得久一点"：每次开闸后的第一批请求必然又吃 429（上游窗口还没滑出），
于是层级只会单调上升，最多 4 次就顶到 1800 秒 cap 并停在那。
现场把上游秒级的限流窗口人为放大成"每 20~30 分钟才探一次、次次撞墙"。

**修复**（`engine.go` tick 0.5 步 + `ratelimit.go`）：

- 闸门到点即视为本轮冷却窗口走完，`endCooldownEpisode()` 把层级归零；
- 归零只清 `consecutive`、保留 `lastAt`（与"成功一次"的 `clearRateLimit` 分工明确）；
- 真退避不变：同一窗口内连续 429 仍按指数递增，cap 仍是 30 分钟。

代价账：每轮冷却窗口多付一次探测请求（一次 `Pick` + 一轮请求）。
换来的是：上游若已恢复，最多 3 秒（tick 间隔）就能接上，而不是等 20 分钟。

## 根因二：有排队任务时一律不说原因（说不清）

`StallReason` 的早退条件是：

```go
if stats.TodayDone > 0 || stats.RunningTasks > 0 || stats.QueuedTasks > 0 {
    return StallReason{}   // "只是还没轮到"
}
```

而 `StallPoolCooling`（模型池整体冷却）排在早退**之后** —— 于是"队列里明明有活、
闸门却把它们全按住"这个最常见形态，既不报停摆、也没有任何读数解释。

**修复**（`stall_reason.go`）：新增 `StallQueuedNoLane`，判据三条同时成立：

1. 队列里有任务（QueuedTasks > 0）；
2. 一条都没在跑（RunningTasks == 0）；
3. 整池闸门仍生效（poolWaitUntil > now）。

文案同时给出排队条数、等待时长、退避档位，例如：

> 模型池冷却中：14 个任务在排队，一个都没在跑；约 442 秒后自动重试
> 整池冷却第 3 次，剩余约 442 秒后自动重试（闸门到点即恢复调度）。

面板首屏总览已渲染 `stallReason`（`assets_script.go` 的 stall-banner），无需改前端。
