## 1. 坏消息：闭环终点跑不过（阻断性回归）

现象：**建了 17 个目标、67 条 plan、50 条 accept、16 条 block，但 0 个目标完成**。

## 2. 根因：验收判据"声明了却没实现"（混合版本树）

容器内 `goals.json` 的判据 `detail` 字段**字面写着**：

```
完成不少于 2 个阶段任务                达到阈值（2 ≥ 2）
阶段自评均分不低于 1.0/10             达到阈值（9 ≥ 1）
阶段产出总字数不少于 150               达到阈值（392 ≥ 150）
至少 35% 的阶段产出通过真实执行验收     未知判据类型，按未通过处理   ← 恒 false
至少 1 个阶段产出通过真实执行验收        未知判据类型，按未通过处理   ← 恒 false
```

静态交叉读码定位（三方对齐）：

| 文件 | 事实 |
|---|---|
| `internal/autonomy/types.go` | 声明了 `CriterionVerified`、`CriterionVerifiedRatio` |
| `internal/autonomy/planner.go` | 默认判据里**会生成** `Kind: CriterionVerifiedRatio` 与 `Kind: CriterionVerified` |
| `internal/autonomy/acceptance.go` | `evalCriterion` 的 switch **只有** TaskDone/MinQuality/MinWords/DistinctDomains/Manual + default |

于是这两个判据落进 `default` → "未知判据类型，按未通过处理" → **恒 false** →
目标永远无法通过验收 → `goalDone/nextGoal` 永不出现 → 跑到预算上限后被 `block`。

**这是混合版本树**：判据的"声明/生成"来自新版本，而"判定实现"是旧版本。
单看任何一个文件都正常，只有把三者交叉比对才暴露 —— 所以它躲过了编译和单测。

（附：`engine_autonomy.go` 里已有的 `tasksOfGoalForAcceptance` 修正说明这部分此前被修过，
但这次恢复的 `acceptance.go` 是**未含**该修正的版本。）

## 3. 修复建议（给 Lead，一行级改动）

在 `internal/autonomy/acceptance.go` 的 `evalCriterion` switch 里补两个分支：

```go
case CriterionVerified:
    c.Current = float64(res.VerifiedCount)
case CriterionVerifiedRatio:
    c.Current = res.VerifiedRatio
```

并确认 `AcceptanceResult` 有 `VerifiedCount` / `VerifiedRatio` 字段，
以及 `Evaluate` 的统计段里累计这两个值（按任务 `Verified` 标记）。
改完跑容器闭环应能回到 `goalDone=1 / nextGoal=1`。

## 4. 新增静态门禁：判据"声明 vs 实现"交叉校验

新增 `tests/docker-autonomy/criteria-coverage.sh`（纯静态、秒级、不依赖模型），
已接入 CI `autonomy-e2e.yml` 的**编译前**步骤。三条判据：

- **A** planner 会生成的判据，acceptance 必须有处理分支（抓本次这类缺陷）；
- **B** types.go 声明的判据（manual 除外）也不得有漏网；
- **C** 反向：acceptance 处理的判据必须在 types.go 声明过（防拼写漂移）。

双向自证（都在容器里实跑过）：

| 输入 | 结果 |
|---|---|
| `src-backup/workbench`（缺实现） | **FAIL**，精准报出 `CriterionVerified`、`CriterionVerifiedRatio` 两项缺失 |
| 人工补齐两个 case 的对照树 | **OK**（`CRITERIA_COVERAGE_OK`），零误报 |

修坑记录：首版用 `grep -oE` 提取声明，在不带换行的实现下会把多行粘成一个 token（误报一堆）；
改用 `awk '{print $1}'` 逐行取后干净。
