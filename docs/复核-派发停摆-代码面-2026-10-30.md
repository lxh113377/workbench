## Q3 自愈路径：有，但只覆盖 running，不覆盖 queued/parked

- 存在的时间驱动自愈：`poolWaitUntil` 到期自动开闸（`engine.go:810`）+ `endCooldownEpisode` 清退避（`engine.go:826-828` / `ratelimit.go:99-103`）。本窗口 55 条 WARN 的中位间隔 **309 秒**（E6），正好等于 `rateLimitCooldownSeconds = 300`（`ratelimit.go:18-21`）+ 抖动 ⇒ 每个 5 分钟窗口都在**真的重探**，不是死锁。
- 卡死救援只认 running：`sweepOrphanedRunning` 的过滤器是 `t.State != model.StateRunning { continue }`（`runtime_rescue.go:105`，函数 `:95`，节流 `:48`），把假 running 回收成 queued（`:167-173`）。
- 崩溃恢复只在**启动期**：`store.Reconcile`（`internal/store/store.go:204`）+ `Recover` 重建队列（`engine.go:679-727`，`interrupted` 走 `rescueInterrupted` `stuck_rescue.go:106`）。运行期没有等价扫描。
- 「取出不来」的兜底是**判死**，不是唤醒：`PoolWaits >= budget` → `failTask`（`engine.go:1841-1849`）。它让一条僵尸任务退出供料，但不会让别的任务被派发。
- **没有任何看门狗/超时会把一条 queued 但 `Pop` 永远跳过的任务唤醒或清出队列**；`queue.Pop` 对不合格条目只 `continue`（`queue.go:150`），也没有运行期 purge 入口。

⇒ 对 queued/parked 任务：**无唤醒自愈**（无 watchdog、无 purge）。本窗口的实际恢复依赖两个外部/时间事件：① 车道 300s 冷却到期（会发生，每次只买到一次重探）；② 上游免费额度复位（**没有发生**，所以重探每次都返回 429/quota）。

## Q4 三个候选根因（按可能性排序）与日志可区分特征

### A（最可能）上游额度/限流长期不满足 —— 有效派发被 429 弹回
- 代码路径：`router.Pick` 成功 → `FailoverRunner` 沿候选链重试 → 每条车道返回 `rate_limited`/`quota_exhausted`/`not_served` → `engine.go:1198-1268` 冷却出问题车道；全池不可用后 `engine.go:1264-1266` 整池冷却；任务 `requeueForPoolWaitKind`（`:1249`），`PoolWaits` 累积到 48 后判死（`:1841-1849`）。
- **应看到**：`尝试结束` 以 `rate_limited/quota_exhausted/not_served/boot_failed` 为绝对多数（本窗口 86/19/28/21，共 154/218）；`上游限流，全部车道不可用，整池冷却`、`模型池限流冷却`；audit 里 `queued→running` 与 `模型池冷却，退回队列` 几乎 1:1（本窗口 106:103）；`models-health.json` 里绝大多数条目 `cooldownTo > now` 且 `lastErr` 前缀 `rate_limited:`。
- **不应看到**：`尝试开始` 缺失（若为 0，则不是这条）。
- 本窗口实测全部吻合（E4/E6/E11/E13），且**完成数 = 0**。

### B 供料门饿死（T70 原假设：q.Len()>0 却取不动）—— 只挡「新任务供给」，不挡「取件」
- 代码：`engine.go:835` 门条件 `e.q.Len()==0` 与 `engine.go:845-851` 取件循环是**两件独立的事**；门只决定是否调用 `supplyCandidates`（`:836`）。
- **应看到（若它同时挡住了取件）**：`供料门被挡` WARN 持续，且**完全没有** `尝试开始/尝试结束`，audit 无 `开始执行`，`queued` 长期 >0 不下降。
- 本窗口**证伪其挡住取件**：WARN 55 条，每一条后面 60 秒内都有一条 `尝试开始`（55/55），`queued` 恒为 1，且 106 次 `开始执行` 把队列取空。它对**供给**的效应是真的：5.27h 只新增 3 条任务（`自主任务已生成` 3 条，`任务已入队` 0 条）。

### C 结构性取不动（队列残留 / 链占用 / 并发槽耗尽）—— NO-RESET 类
- 代码位置：C5 队列残留（`queue.go:150` + `:28`，无运行期 purge）、C6 `chainBusy` 只 `Pop` 置位（`queue.go:157-159`）、C4 槽只由协程 defer 释放（`engine.go:859`）；`ReloadConfig` 换槽时不搬运在飞令牌（`engine.go:2282-2284`）。
- **应看到**：`供料门被挡` 持续 + `queued>=1` **且队列长度不下降** + `尝试开始` 长期为 0 + audit 无新的 `开始执行` + 无 `模型池冷却/退回队列` 行（因为根本没进 runOne）。
- 本窗口**证伪**：`queued` 恒为 1 且每 tick 被取走；`开始执行=106`；`退回队列=103`。C5/C10 是真实但未触发的隐患。

## Q5 结论

派发链路本身完好：tick 每 3 秒推进，队列里唯一的 parked 任务在每个冷却窗口到期时都被 `Pop` 取出并真正交给执行器（本窗口 106 次 `开始执行`、218 条「尝试」）。停摆的**明确条件**是：`router.Pick` 能选出的全部 38 条车道在同一窗口内持续返回 429/额度耗尽并处于冷却，`models-health.json` 快照 38/38 条命中冷却且 `lastErr` 前缀均为 `rate_limited:`；于是每次重探都走到 `isRateLimited` → `requeueForPoolWaitKind`，103/106 次退回队列、3 次判死、**0 次完成**。`endCooldownEpisode`（`ratelimit.go:99`）与 `engine.go:810` 的时间驱动自愈确实在运行（WARN 中位间隔 309s = 300s 冷却），但每次开闸只换来一次必然失败的探测 —— 这是条件长期不满足，不是复位环节缺失。`q.Len()==0` 供料门（`engine.go:835`）同窗口关闭，把「新任务供给」也压到 5.27h 仅 3 条，是并发的次生伤；它不构成「取不动」的证据（55/55 WARN 后立即派发）。另记两处真实但未触发的「只置不复位」：队列内非 queued 残留无 purge（`queue.go:150`+`:28`）、`PoolWaits/PoolWaitCeil` 人工重试不重置（`engine.go:1825-1828` vs `:2087-2091`）。
