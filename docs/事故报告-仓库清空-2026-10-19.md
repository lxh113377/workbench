## 二、结论

**可确证：**
1. 清空发生在 **10:08:14–10:08:39**（25 秒窗口），影响范围 = `workbench/` 内容 + `.git` + `memory/` + `docs/` + `setup/` + `eval/`。
2. **没有**任何会话在窗口内发出可记录的删除命令；**没有**走回收站；**没有** Defender 处置；**没有**计划任务。
3. `workbench/` 目录本身存活（CreationTime 未变），说明是内容级清空。

**不可确证（诚实声明）：**
- **无法把清空归因到某个具体会话或某条命令。** 所有可审计通道（10 份转录的完整工具调用、文件系统元数据、回收站、Defender、计划任务）在窗口内都没有删除痕迹。
- 窗口内确实存在「跨会话并发写同一工作区」的高危条件：10:00–10:10 有 **6 个会话同时活跃**（0828de75 / 4df6aabf / 9c52bbd6 / c6e423cf / e0245f85 / fa2ecfc6），全部在对 `D:\workdesktop` 做写操作。**并发写同一工作区是本次事故的必要条件，但不是充分证据。**
- 我**未提升权限**（`IsInRole(Administrator)=False`），因此无法读取 USN Journal（`fsutil usn readjournal` → Access denied）与 Defender 排除项。**若要做进程级归因，需要管理员权限重跑 USN 查询。** 这是本次取证的能力边界。

## 三、决策（按老大 2026-10-19 授权自行拍板）

- 保留 `src-backup/` 为**文件找回来源**，**不当作可提交的基准**。
- 理由：跨快照拼接必然产生同名文件版本冲突（已实测：`model.Task` 缺失、`newestModTime`/`jsonMarshal`/`AuditPath` 重复定义、`artifact/loose.go` 语法错误）。把这种树当基准会污染后续判断。

## 四、需要管理员权限才能推进的项（能力边界，如实列出）

1. `fsutil usn readjournal D:` —— 可读出窗口内**所有文件操作**（含被删除项），是唯一能做到进程级归因的通道。当前 `Access is denied`。

**在获得管理员权限前，本报告的归因结论停在「并发写 + 内容级清空、无显式命令痕迹」。**
