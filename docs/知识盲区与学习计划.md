## 2. 八大盲区清单（按对改进优先级排序）

### 盲区 B1 — 跨平台测试可移植性（🔴 高，实测复现）
- **表现**：Linux 容器 `go test ./...` 下 **engine / retention / verify** 三包直接 FAIL，共 10 处失败用例。
- **证据**：`TestMaterializeArtifactsPass` 报 `exec: "pwsh": executable file not found in $PATH`；`TestP3PipelineOfflineE2E` 报 `exec: "python": not found`；`TestTrashRefusesDangerous` 在 Linux 上 `C:\\` 未被判危险路径。
- **根因（知识）**：验收/清理逻辑把「被测行为」与「宿主工具链」耦合——测试假设 runner 上一定装 pwsh/python、一定在 NT 文件系统。这是**没有把外部依赖抽象成可注入接口**的典型。
- **对标**：river/asynq 用 build tag（`_linux.go`/`_windows.go`）+ 接口桩隔离平台；本项目 `executor` 已有 `job_windows.go`/`job_other.go` 的分治意识，但测试层没跟上。
- **学习计划**：见 §3-L1。

### 盲区 B2 — 平台绑定包的测试空白（🟡 中）
- **表现**：`tray / single / browser / dshprofile / chain / judge` 六包 **无 _test.go**，覆盖 0%；`shortcut` 有测试但 Windows 门控，Linux 显示 0%。
- **证据**：`git ls-files internal/{pkg}` 实测（附录 B）。
- **根因**：这些包要么调系统 API（托盘/单实例/浏览器拉起）、要么是被 engine 间接覆盖的核心决策（chain 衍生、judge 判分）——**前者可接受低覆盖但要标注，后者（chain/judge）不该 0 覆盖**。
- **对标**：temporal 对 workflow 状态机 100% 反例覆盖；本项目 chain/judge 是「链式衍生/语义判分」的核心闭环，却无守护测试。
- **学习计划**：见 §3-L2。

### 盲区 B3 — 覆盖率「门禁线」与「真实线」的偏差（🟡 中）
- **表现**：commit a1bb475 为 evaluate/modelroute/shortcut 设「诚实基线」50/50/23；实测 evaluate=50.9、modelroute=50.6、modelpool=53.0。基线贴着实测值，CI 一波动就假红。
- **根因**：基线下探是「止血」不是「治病」——真正要的是把这些包的实际分支测到，而不是把阈值调到刚好过。
- **对标**：river 测试文件比 48.8%，靠的是纯函数 + 表驱动，不是靠调阈值。
- **学习计划**：见 §3-L3。

### 盲区 B4 — 卡死救援仅本进程内有效（🟡 中，对标报告 §3.2 在册）
- **表现**：stall watchdog（180s 无事件杀树）只在 workbench 进程活着时生效；进程崩溃后无外部救援。
- **根因**：缺 producer 侧兜底（river `RescueStuckJobsAfter` 由队列侧跨进程生效）。
- **学习计划**：见 §3-L4。

### 盲区 B5 — 执行器抽象未落地（🟢 低，已部分具备）
- **现状**：`internal/executor/hooks.go` 已提供 `RunnerContract` + BeforeRun/AfterRun（P1-2 已交付），但 engine 主路径仍以具体结构体直调为主。
- **学习计划**：见 §3-L5（把 engine 注入点收敛到接口）。

### 盲区 B6 — 结构化日志接线不完整（🟢 低）
- **现状**：`internal/logging` 包 82.8% 覆盖（P1-1 已交付 slog 双写），但部分散落写入点仍在用旧 debugf。
- **学习计划**：见 §3-L6（统一 component 字段 + 清扫散落写入点）。

### 盲区 B7 — 社区协作面为零（⚪ 非代码）
- **表现**：远端仓 lxh113377/workbench 无 issue 模板、无 PR 流程、无 CHANGELOG「Unreleased」段滚动。
- **学习计划**：见 §3-L7（补 issue/PR 模板 + release 流程，对标 CONTRIBUTING.md）。

### 盲区 B8 — 性能基线未进 CI（🟢 低）
- **现状**：对标报告 §3.5 首页 11ms / 7.74MB 为手工单次读数，非 CI 趋势。
- **学习计划**：见 §3-L8（把 --diagnose 与产物体积断言进 build job）。

## 5. 本轮新增实测缺陷 D6：自主闭环测试存在读后写竞态（CI 间歇红）

**取证时刻**：2026-10-19 14:15 · 同一提交 `dcfd999` 两次 CI：首跑 `build + coverage gate` FAIL，重跑 success（`vet + test (race)` 与 Autonomy E2E 两次皆绿）。

| 项 | 实测 |
|---|---|
| 失败用例 | `TestRunOneDrivesAutonomyClosedLoop`，报 `决策台账缺少 nextGoal（实际 map[accept:true goalDone:true plan:true]）` |
| 失败位置 | `workbench/internal/engine/engine_autonomy_test.go:429`（断言四类决策齐全） |
| 根因位置 | `workbench/internal/autonomy/manager.go:467 → 470`：`store.SetActive(g.ID)` **先**执行，`AppendDecision(DecisionNextGoal)` **后**执行 |
| 触发机制 | 测试轮询条件（`engine_autonomy_test.go:404`）是 `cur != nil && cur.ID != g.ID`，即**活跃目标已切换**就退出；此刻 SetActive 已落，但 nextGoal 决策尚未追加 ⇒ 立刻读台账必然偶发缺 nextGoal |
| 性质 | 读后写竞态（非逻辑错误）：功能本身正确（容器与重跑均证明 nextGoal 最终写入），但**退出条件的可观测面**比**被断言的可观测面**先成立 |
| 影响面 | CI 间歇假红；运行时「面板刚切换目标、下一秒才出现决策记录」的同型窗口 |

### 修复方案（两选一，归 Lead 写入口，本会话按分工不动 workbench/）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | `manager.go` `advanceLocked` 内把 `AppendDecision(DecisionNextGoal)` 移到 `store.SetActive()` **之前**，让「台账已含 nextGoal」成为「活跃目标已切换」的**前置**条件 | 根治：可观测面顺序与被断言顺序一致，测试与面板同时受益；改动 3 行，语义仍是「先留痕再生效」，符合本项目「异常/降级绝不静默改状态」的既有纪律 |
| B | 测试侧在退出轮询后再 `for` 等 nextGoal 决策出现（带 deadline） | 只消音 CI，生产窗口仍在；属盲区 B3 反对的「调判据而非治病」 |

**完成判据**：`gh run rerun` 连续 3 次 CI 全绿，且 `go test ./internal/engine -run TestRunOneDrivesAutonomyClosedLoop -count=20 -race` 零失败。

### 归因到盲区

属 **B1 的姊妹形态**：不是「硬编码外部工具」，而是「对异步副作用的**可观测顺序**做了乐观假设」。对标 river `job_executor.go`：attempt 记录与状态迁移在同一临界区内顺序固定，外部查询不会看到「状态已迁、台账未写」的中间态。新增学习项 **L9**：精读 river 的 `Transition` + attempt 落库顺序，把本项目「状态生效」与「决策留痕」的先后统一为「留痕先生效」。

### L4 的关键判断（为什么不是照抄 river）

### 9.3 本轮学到并可复用的三条纪律（反哺记忆）

1. **审计兜底路径要按「异常环境叠加」想**：写「失败时尽力补救」的代码时，先问「补救用的手段在同样的故障条件下会不会也失败？」
   atomic 的 Remove 恰好只在 rename 失败（≈目标被占用/权限异常）时才执行，而该条件下 Remove 与后续 rename 双双失败的概率最高。
   判据：**兜底的每一步都必须有「它也失败了」的分支处理，且失败终态不得劣于操作前**。
2. **有界改动保既有语义**：修饿死没有推翻优先级设计，而是给 aging 设上限——全体饱和时自动退化回旧行为，
   既有测试（TestPopRespectsPriorityAndFIFO）一字不改仍成立。能「加一个有界机制」就不「换一套调度器」，
   这是单机项目吸收大型系统设计的通用姿势：取其**不变量**（等待有上界），不取其**结构**（多通道+权重展平）。
3. **引用 peer 行号必须 read 回原文核对**：本轮报告自纠两处——凭精读记忆写的 prometheus Windows 注释行号（424-428）
