# 轮询器重入与超时缺陷 —— 五轴审查报告

> 变更范围：`workbench/internal/web/assets_script.go`（api() + ping + refreshTop）、
> 新增 `workbench/internal/web/poll_guard_contract_test.go`。
> 本报告按 `review-five-axis` 模板产出，可直接贴进 PR。所有发现都有代码级或行为级证据。

## 1. 正确性

- **P0（阻塞）：高频轮询器无重入守卫，慢响应下状态被过期响应往回拨**
  - 位置：`assets_script.go` 的 `ping`（4s）与 `refreshTop`（5s），以及底 `api()`。
  - 证据（代码级取证链，非推测）：
    1. `handleStatus` 调用 `engine.Phase()` 与 `LastError()`；
    2. 二者都 `e.mu.Lock()`（`engine.go:623` / `engine.go:630`）；
    3. `Engine.Start()` 全程持 `e.mu`（`engine.go:396`），且持锁期间调
       `bootstrapAutonomy`（`engine_autonomy.go:67` → 内含模型调用）；
    4. ⇒ 点「启动」时，面板每 4-5s 一次的 `/api/status` 会**排队等锁**，而 `api()` 无超时。
  - 后果：① 一次卡顿就堆一串在途请求；② 旧响应后到会 `paint()` 覆盖新状态（往回拨）。
  - 建议改法：`api()` 加**可选** `timeoutMs`（AbortController），两个轮询器加 `if (busy) return`
    守卫并在 `finally` 复位。**守卫必须与超时配套**（见 §结论）。

- **P1（应改）：`assets_gov.go` / `assets_pool.go` 的 `load()` 仍无守卫无超时（本轮未动）**
  - 位置：`assets_gov.go:204`（30s）、`assets_pool.go:499`（15s）。
  - 判定：频率低（30s/15s），叠加规模与影响面都比首页 4s/管理面板 5s 小一个数量级；
    且 pool 页可能触发慢端点，超时值需单独论证 —— 按「逐点攻破」留下一轮，不在本 PR 夹带。

## 2. 可读性

- **P2（本轮改动新引入，必须记）**：`api()` 在全仓有**三份独立副本**
  （`assets_script.go` / `assets_gov.go` / `assets_pool.go`，各自 IIFE 内联、不共享）。
  本轮只给 script 那份加了 `timeoutMs`，于是**三份实现开始分叉**：一份支持可选超时、两份不支持。
  分叉本身无害（另两份不传 timeoutMs，`opts.timeoutMs` 为 undefined 即走旧路径），
  但它是「三份复制粘贴的前端基建」这个更大问题的第一次显性化 —— 将来任何一处要改鉴权头、
  错误处理或超时，都得记着改三遍。抽成共享模块要动内嵌结构，本 PR 不夹带；
  登记为门禁建议 #5。
- **P2（建议）：超时为何是「可选」而非默认，代码里有注释说明**。
  关键原因写进了 `api()` 上方注释：`/api/pool/probe` 是**合法慢接口**
  （`service.go:297` `probeSpecs` 串行遍历 base、单模型 client 超时 10s → 整体可达 N×10s），
  一刀切设超时会把能用的功能改坏，那比原缺陷更糟。
- 无阻塞项。

## 3. 架构

- **P1（应改，但需独立评估，不能顺手做）：只读的 `Phase()`/`LastError()` 用排他锁，面板延迟被写侧绑死**。
  这是本轮所有症状的**根因层**：`/api/status` 读的是引擎状态，其延迟却被 `Start()` 的持锁时长决定。
  已核实的三点（决定这不是「改一行」的小事）：
  1. `Phase()`（`engine.go:623`）/ `LastError()`（`engine.go:630`）确为**纯读**（函数体内无 `e.*` 赋值）；
  2. 但 `mu` 的类型是 `sync.Mutex`（`engine.go:57`），**不是 RWMutex**，engine.go 里从未出现 RLock ——
     所谓「改用读锁」得先把类型换掉，牵动 **22 处** `e.mu.Lock/Unlock`（本文件）；
  3. Go 的 RWMutex **非重入**：持写锁的同一 goroutine 再 `RLock` 会**自我死锁**。
     `loop()` 在 L727 调 `e.Phase()`，位置在 L715-717 那个 defer 锁**之外**（当前不嵌套），
     但「全仓所有读路径都不在写锁内被调用」这个前提要覆盖 22 处加锁点逐个核实才成立。
  ⇒ 结论：调用侧的守卫 + 超时是本轮**止血**；引擎侧解耦是独立的架构改动，需要完整的锁图分析，
  **不在本 PR 夹带**（objective「步子不要太大」）。登记为后续项，并附上述三点实测作为起点。

## 4. 安全

- 本轴未发现问题。检查项：`api()` 改动不涉及鉴权（`X-WB-Token` 头原样透传）、
  不引入新的注入面（`timeoutMs` 是本地数字参数，且从 fetch 选项里 `delete` 掉不发给服务端）、
  不改动 `esc()` 转义链（round 91-92 已钉住）。

## 5. 性能

- **P0 的实际收益即性能项**：卡顿期间在途请求从「每 4s 累加」变为「恒定 1 个」。
  行为测试实测：一次 1.2s 卡顿内连续触发 8 次轮询，改后 fetch 只发起 **1 次**
  （对照组去掉守卫则发起 8 次，精确复现原缺陷）。
- 快请求不受影响：30ms 响应 + 8s 超时 ⇒ 正常 resolved，abort 计数 0。

## 合并结论

**可合并（本 PR 是止血，根因层的锁模型改造另开）。** 理由：
- 行为验证六条全过：不传 timeoutMs 时行为与改前逐字节一致（合法慢接口不受影响）、
  传超时则慢/挂起都在超时点 abort、timeoutMs 不泄漏进 fetch 参数、守卫在正常/异常路径都复位。
- 契约测试 4 处变异全部判红（去守卫 / 去超时 / 不剥离 timeoutMs / 新增定时器）。
- 受跟踪的契约测试（`stall_banner_contract_test`、`scale_contract_test`）+ 本 PR 新增的
  `poll_guard_contract_test` 在 CI 会真跑；本地 `go test ./internal/web/` rc=0、`gofmt` clean。
  注：`home_contract_test` 经 `git ls-files` 核实是**未跟踪的并行在途件** —— 本地绿不代表它在 CI 里。
  本 PR 不依赖它：守卫/超时的断言由 poll_guard 承载，且 poll_guard 随本 PR 一起纳入跟踪。
- **守卫与超时必须成对**是硬约束：只加守卫不加超时 ⇒ 一次永久挂起让 busy 永不复位
  ⇒ 轮询永久停摆（比原缺陷更糟）；契约测试同时断言两者，防止后人拆掉一半。
