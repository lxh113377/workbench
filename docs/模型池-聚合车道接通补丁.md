## 1. 现状与证据

面板「添加兼容模型接口」填 BaseURL/APIKey 后：

| 环节 | 现状 | 证据 |
|---|---|---|
| 入池登记 | ✅ | 活体实测 `/api/pool/models` POST → specs 35→36 |
| 真实 HTTP 探测 | ✅ | `probe.go` 打 `GET <BaseURL>/v1/models` 带 Key |
| 投影成路由 | ❌ | `Manager.Routes()` 过滤 `!Routable`，自定义端点进不去 |
| DSH 子进程调用 | ❌ | 见下节根因 |

根因链（逐文件核对，字段名对照 OFM 插件源码，未猜标识符）：

1. `executor.go: taskHome()` 每任务写
   `our-free-model/settings.json`，其中 aggregate 被**硬编码**
   `{"enabled": false, "providers": {}}`；
2. `overlay.yml` 由 `modelOverlay()` 生成，只写
   `provider: our-free-model` + `model: <id>`；
3. OFM 插件 `core/runtime.js: mergeCatalogs()` 用
   `buildAggregateCatalog(settings.aggregate)` 生成 aggregate 行并合并进 catalog；
   第 1 步给了空开关 ⇒ **aggregate 行永远不存在**；
4. `adapter.js: resolveModel()` 按 `entry.id` 查 catalog，查不到就回退成
   「免费车道条目」，最终走 `postStreamed`（OFM 匿名池），
   而不是 `postAggregateStreamed`（用户自己的端点）。

**结论**：用户自填端点会被静默改道到免费车道，绝不会打到用户填的 BaseURL。
所以这类模型的正确标记是 `routable:false`（本轮已在
`Scheduler.Pick/PickChain` 补齐这道过滤，见 commit 7e44267）。

## 2. 接通方案（最小改动，零源码依赖新增）

### 2.1 池 → aggregate 配置的投影

在 `taskHome()` 写 settings 前，收集池内「自定义/聚合车道且带 BaseURL」的 Spec：

```go
// 需要把池的 specs 传进 taskHome（现签名只有 taskID）。
// 建议 Runner 上加一个 provider 回调，避免 executor 反向依赖 modelpool。
type AggregateProviderSpec struct {
    ProviderID string // OFM registry 里的 provider id（见 2.2 校验）
    ModelIDs   []string
    BaseURL    string
    APIKey     string
    Format     string // openai-chat / openai-responses / anthropic-messages
}
```

settings 的 aggregate 段按 OFM 契约写（`src/aggregate.js` 的
`buildAggregateCatalog` JSDoc 逐字段核对）：

```json
"aggregate": {
  "enabled": true,
  "providers": {
    "<providerId>": {
      "enabled": true,
      "apiKey": "<key>",
      "baseUrl": "http://127.0.0.1:18432/v1",
      "models": ["openrouter/free"],
      "addedAt": 1700000000000
    }
  }
}
```

```yaml
# overlay 的 model 用 provider/model 复合 id
- id: agent-default-model
  config:
    provider: our-free-model
    model: open_router/openrouter/free
```

### 2.2 三条硬校验（不满足就别接通，否则会静默失败）

OFM 侧 `resolveProvider` / `authUsable` / `effectiveChatUrl` 的实际约束：

1. **providerId 必须存在于 OFM registry**（`src/providers/registry.json`，实测 75 个）。
   `parseProviderModelId` 用 `BY_ID.has(providerId)` 校验，未知 id 直接判死。
   → 面板新增模型时必须校验 providerId，或引导用户从 registry 选；
   不能像现在这样让用户随便写 `probe/vendor-x`。
2. **baseUrl 不得含 `{...}` 占位符**（`hasPlaceholder`），否则该行不产出。
3. **auth.kind=oauth/adc 的 provider 聚合车道不服务**（`authUsable` 直接 false）。

线协议映射（`CHAT_SUFFIX`）：`openai-chat→/chat/completions`、
`openai-responses→/responses`、`anthropic-messages→/messages`。
面板三种格式都已支持；registry 分布实测
`openai-chat/apiKey=64`、`anthropic-messages/apiKey=3`、
`openai-responses/apiKey=1`、local(auth=none)=3（ollama/lmstudio/llamacpp）。

### 2.3 密钥落盘边界（必须先定策再动手）

现在 `Spec.APIKey` 只在本机 settings 里、API 只回显指纹。接通后它会出现在
**每任务隔离 HOME 的 settings.json**（`runtime/dsh-home/tasks/<id>/our-free-model/`）。
retention 包回收任务目录时会带走它。建议：

- 任务目录里的 settings.json 保持 0600 语义（Windows 上继承 ACL，需实测）；
- 或改成「aggregate 配置只在共享 HOME 写一份，任务 HOME junction 过去」，
  与 profiles 同策略（`linkDir` 已有现成实现）。

## 3. 验证步骤（接通后必须全过）

1. 容器内 mock：`tests/docker/mockofm` 已能当 OpenAI 兼容端点用
   （`/v1/models` + `/v1/chat/completions`，支持 `-key` 鉴权与 down/unauthorized 模式）；
2. 面板加一个 providerId=open_router、baseUrl 指向 mock 的模型，置 `routable:true`；
3. 跑一个任务，断言：
   - mock 的 `/ctl/state` `chatHits >= 1`（**证明请求真打到用户端点**，这是核心判据）；
   - `model-status.jsonl` 该模型有 success；
   - 关掉 mock → 该模型被标 down 并自动切到下一个（故障转移对新车道同样生效）；
4. 反假绿：故意把 providerId 写成 registry 外的值，必须**接通失败并给出明确错误**，
   不得静默回落到免费车道（静默改道是现在最坏的行为，因为用户以为在用自建端点）。
