## 2. 成因链（代码级）

1. 生产 `config.json`：`plan.enabled=true`、`plan.plannerTier="quality"`、`plan.plannerModels` 未配
2. 路由表实测 tiers 只有 `balanced=1 / fast=2`（3 条车道，**没有 quality**）
3. `planModelFor` 兜底「宁可放宽到任意 tier」⇒ 用**执行车道**出方案
   （workbench/internal/engine/plan_stage.go:85-104）
4. 执行型车道不产出方案 JSON ⇒ parse fail / 零输出 / 挂到阶段预算才断
5. 阶段预算 = `plan.stageMaxMinutes=4`（默认），故单次白等上限 240s，与实测 207s 吻合
6. **失败从不 `RecordFailure`**（engine.go 只在执行段记账，plan 路径零记账）⇒
   车道健康度不知道它出不了方案 ⇒ 加权随机下次仍选中 ⇒ 每个任务重付一次 207s

## 3. 为什么本轮不做（关键，别当成偷懒）

候选修法三条：① 方案失败计入车道冷却；② 取消 tier 放宽（无 quality 就跳过方案阶段）；
③ 配置 `plan.plannerModels` 指向实测可出合法 JSON 的车道 / 调小 `stageMaxMinutes`。

**三条都会改变产物内容**，与本轮目标第 1 条「保持原有功能、对外接口和输出结果不变」直接冲突：
plan 失败时系统**本来就走退化直执行**（用 task.Prompt 原文），所以任何"让 plan 变便宜或变成功"
的改动，都会把执行段 prompt 从「原文」换成「渲染后的方案指令」⇒ 模型输出不同 ⇒ 交付物不同。
按 P0.19（当轮命令 > 一切规则），本轮不动它。
